## 1. 背景与问题

**现状**：项目的 Flutter 代码规范 FSD-11 已要求三个严格分析选项、八条 lint 规则，以及不排除 `lib/` 和 `test/` 下手写文件。根目录现有配置仅包含 `flutter_lints` 的默认规则和原有平台、构建目录排除项。原页面需求将这项工作登记为延期事项 FUP-001，页面本身已交付并审查通过。

**问题**：开发者当前执行静态分析时，无法通过 FSD-11 要求的严格配置检查代码。只改配置而不处理由新规则引出的告警，也无法达到 FUP-001 的完成标准。

**为什么现在做**：用户已选择用一份独立需求承接 FUP-001，避免把分析器配置混入页面功能需求。

## 2. 目标

- 开发者在现有本地开发与 `flutter analyze` 入口使用 FSD-11 规定的严格检查。
- 本次配置引出的现有 Dart 代码告警得到处理，同时格式、分析、测试均通过，页面既有行为保持不变。

**成功后能看到的结果**：配置包含规定的三个严格选项和八条 lint 规则；格式检查、`flutter analyze` 和 `flutter test` 通过，现有页面、交互与演示数据不变。

## 3. 用户场景

### 场景 A：本地检查

1. 开发者在现有 Flutter 项目中修改 Dart 代码。
2. 开发者通过已有编辑器分析入口或 `flutter analyze` 获得 FSD-11 所要求的检查结果。
3. 如启用规则使现有代码出现告警，实现者仅调整触发这些告警的代码；现有页面仍按原样工作。
4. 实现者完成格式、静态分析与测试验证后，才把 FUP-001 视为达到完成标准。

### 场景 B：发现无关失败

1. 格式、静态分析或测试检查发现与本次启用规则无关的既有失败。
2. 实现者不把无关修复并入本需求，记录失败及证据并停止宣称 FUP-001 已完成。
3. 用户随后单独决定如何处理该失败。

## 4. 必须做到

- **R1** 项目执行现有分析入口时，根目录配置启用 FSD-11 的 `strict-casts`、`strict-inference`、`strict-raw-types`，以及 `always_declare_return_types`、`avoid_dynamic_calls`、`avoid_print`、`directives_ordering`、`prefer_const_constructors`、`prefer_const_declarations`、`unawaited_futures`、`use_super_parameters`，并继续包含 `flutter_lints`。
  - **反例**：缺少任一严格选项或 lint；某项被设置为 `false`；不再包含 `flutter_lints`。
  - **可观察证据**：检查根目录配置可逐项读到三个启用的严格选项、八条启用的 lint 和原有的 `flutter_lints` 引入；现有分析入口读取该配置。

- **R2** 启用新规则后，项目不通过 `exclude` 排除 `lib/` 或 `test/` 下的手写 Dart 文件，也不通过 `ignore` 压制新增告警；原有 `build/`、`windows/`、`macos/` 排除项保持不变。
  - **反例**：把 `test/**` 加进排除列表；给新告警添加 `ignore`；为了启用严格检查而删除原有 `windows/**` 排除项。
  - **可观察证据**：排除列表仍只保留原有三项；受新规则检查的手写文件中没有为隐藏新增告警而添加的 `ignore`。

- **R3** 如启用 FSD-11 后现有 Dart 代码出现新告警，实现者调整导致告警的代码，直到本次新增告警消除；现有页面的显示、交互和演示数据保持不变。
  - **反例**：启用规则后仍有新增告警；为消除告警改变排序结果、页面文案或演示数据。
  - **可观察证据**：新增告警已消除；既有页面和测试仍覆盖原有行为，演示数据及用户可观察结果没有变化。

- **R4** 本次交付仅在格式检查、`flutter analyze` 与 `flutter test` 均通过后，才报告达到 FUP-001 的完成标准；发现与本次新增规则无关的既有失败时，记录失败并停止，不把无关修复算入本需求。
  - **反例**：只运行静态分析就宣称完成；测试失败仍关闭 FUP-001；把无关的既有失败顺手改掉以便通过。
  - **可观察证据**：三项验证各有通过结果；如存在无关失败，则有失败证据且 FUP-001 仍保持活跃，不报告已完成。

## 5. 明确不做

- 不新增 FSD-11 以外的 lint，也不改变 formatter 配置。理由：用户选择仅落实已生效规范。
- 不新增 CI 工作流或自动提交门禁。理由：用户选择沿用本地开发与现有分析入口。
- 不改变原页面的界面、交互和演示数据。理由：本需求只补分析器配置和必要的告警修复。
- 不修改与新规则无关的既有失败。理由：用户要求记录并另行决定，避免扩大交付范围。
- 不修改 FSD-11 规范文字，也不提前关闭 FUP-001。理由：当前规范已给出目标；待实际配置和三项验证均满足后，才能凭证据关闭待办。

## 6. 风险与取舍

#### 决策 1：独立承接延期事项
- 决策：如何处理原页面需求延期的严格分析器配置。
- 选择：新建独立需求承接 FUP-001，不修改原页面需求条目。
- 理由：原页面已交付审查，本次可按配置与验证结果独立判断。
- 放弃了什么：把配置工作补进原页面交付。
- 何时重新评估：本需求无法独立交付时。

#### 决策 2：严格检查的交付边界
- 决策：配置启用后产生告警时处理到什么程度。
- 选择：调整由本次新增规则触发的现有 Dart 代码，不改变既有用户可见行为；三项验证都通过才完成。
- 理由：只加配置而留下告警或失败，无法满足 FUP-001 的完成标准。
- 放弃了什么：只提交配置、不处理告警；顺手修复无关失败。
- 何时重新评估：发现无法在不改变既有行为的前提下消除告警，或出现无关既有失败时，停止并交用户另行决定。

#### 决策 3：保持原检查范围
- 决策：是否扩大 lint、排除项和检查入口。
- 选择：仅采用 FSD-11 明列的设置，保留原有三个排除项，不新增 CI。
- 理由：项目当前可在已有入口完成检查，不需要引入另一套门禁。
- 放弃了什么：其他 lint、formatter 设置和 CI 自动检查。
- 何时重新评估：用户另行要求扩大检查范围时。
