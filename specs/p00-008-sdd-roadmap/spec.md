# 大需求路线图技能

- Spec：`p00-008-sdd-roadmap`
- 类型：`new`
- 上游：`—`
- 路线图：`—`
- 切片：`—`
- 附带交付：`—`
- Status：`approved`
- 版本：`v1`

## 1. 背景与问题

**现状**：一个需求大到一次交付不完时，现在的做法是直接开 `sdd-requirement`，把需求条目录到上限，再靠 plan 的任务清单推进。项目里已有 7 个 spec，都没有说明「这一批做完算不算完成」。

**问题**：需求超出单个 spec 时，Agent 只有两种做法，两种都会坏。把条目压到 12 条以内，等于把几件事塞进一份 spec，验收时说不清哪条对应哪个交付；或者只做前半段就收工，用户拿到手发现整条流程走不通。没有任何地方记录「先做哪块、后做哪块、全部做完怎样算完」。

**为什么现在做**：`AGENTS.md` 已经规定一个 spec 只解决一个问题，但没有规定大需求怎么拆。缺这一层，拆分的判断只能留在对话里，换会话就丢失。

## 2. 目标

- 用户能把一个大需求拆成若干可独立验收的切片，并在开工前看清推进顺序。
- 用户能在全部切片交付后，按一条连续路径判断大需求是否真的完成。
- Agent 能用一份固定格式的路线图回答「这块解决什么问题」，并在需求阶段据此拒绝扩大范围。

**成功后，你能看到/做到**：你说一件要做很久的事，先得到一份拆分与顺序清单，逐条确认后开工；每块单独验收，全部做完再一起走一遍完整过程。

## 3. 用户场景

### 场景 A：新开一个大需求

1. 用户在对话里说明要做的完整事情，例如商品管理从列表到增删改查。
2. Agent 判断单个 spec 装不下，询问是否先拆成几步。
3. 用户同意后，Agent 查这个阶段已有的切片与约定。
4. 用户逐条确认 Agent 给出的切片候选，并决定推进顺序。
5. Agent 产出路线图，用户批准拆分与顺序。
6. 用户按顺序对第一个切片运行 `sdd-requirement`，并告知切片编号。

### 场景 B：切片定错了

1. 用户对某切片运行 `sdd-requirement`，访谈中发现这个切片实际要做两件独立的事。
2. Agent 停下，指出超出的是哪一条切片定义，不继续访谈。
3. 用户新开会话运行 `sdd-roadmap` 修订路线图，重新批准。
4. 用户回到需求阶段，Agent 重读修订后的切片定义继续访谈。

## 4. 必须做到

- **R1** 路线图写成 `specs/pNN-<slug>-roadmap.md`，不占用 `NNN` 序号；切片仍为 `specs/pNN-NNN-<slug>/`。
  - **反例**：路线图落到 `specs/p00-008-<slug>/spec.md`，与切片编号抢位。
  - **可观察证据**：`specs/` 下存在以 `-roadmap.md` 结尾的文件，且没有 `pNN-NNN-` 前缀。

- **R2** 第 1 节的整体目标写成用户的一段完整经历；整体不做逐条带理由。
  - **反例**：目标写成「支持商品管理」这类功能名，读者看不出起点和终点。
  - **可观察证据**：目标句里能指出用户从哪里开始、最后得到什么；每条「不做」后面带 `理由：`。

- **R3** 第 2 节四项齐全：完成条件、操作路径、验证方式、验证者；验证方式只取三类之一。
  - **反例**：验证方式写「跑一下测试」或直接写一条命令。
  - **可观察证据**：四项都能在文件里读到，验证方式是三类取值中的一个，验证者为 `用户` 或 `Agent`。

- **R4** 切片编号在排定顺序后按顺序分配，连续且与推进顺序行一致；前置引用存在、不指向自己、不成环。
  - **反例**：编号按创建顺序分配，与第 4 节推进顺序不同；或两片互相前置仍照常交付。
  - **可观察证据**：路线图第 3 节编号依次为 001、002；第 4 节推进顺序与之一致；`sdd_lint.py` 的编号与成环检查通过。

- **R5** 跨切片约定只写多个切片必须一致的行为；影响后续所有需求的约定先补 `docs/standards/`。
  - **反例**：把「用某个类实现」写成跨切片约定。
  - **可观察证据**：第 5 节每条能用一个用户可见或可观察的行为复述；涉及长期约定时，`docs/standards/` 有对应文档并登记在 `steering.md`。

- **R6** 允许沿用同一切片编号的路线外增补；与现有切片冲突时必须走修订，增补项不进入整体验收。
  - **反例**：增补 spec 改变了某切片的「做完后用户能」，路线图没有降级重批。
  - **可观察证据**：路线图第 3 节有增补登记或明确写「无」；增补 spec 的编号与其附着的切片相同、`slug` 不同。

- **R7** 整体验收只做一次，按第 2 节走一条连续路径；不重跑切片的需求条目，不汇总切片审查结论。
  - **反例**：把「7 个切片全部审查通过」当作整体完成，或把每个切片的验证命令再跑一遍。
  - **可观察证据**：第 7 节有一条整体验收记录，写明实际走过的路径；记录里没有引用各切片的需求编号或审查结论。

- **R8** 路线图 `Status` 为 `draft` 时 `sdd-requirement` 拒绝执行；改切片边界、顺序或完成条件要降级重批，更新状态与证据不降级。
  - **反例**：路线图还是 `draft`，Agent 就开始写切片的需求；或直接改切片定义而不降级。
  - **可观察证据**：未批准路线图下申请切片时，Agent 直接停下并说明状态；降级重批发生在正文修改之前。

- **R9** 路线图 lint 检查 11 项，结构、编号、引用、结论类问题为失败，退出码非 0。
  - **反例**：编号不连续、前置成环、切片定义写了「超出」，lint 仍然 PASS。
  - **可观察证据**：对同一份路线图运行 `sdd_lint.py`，正常文件输出 `PASS  11 项检查全部通过`，改坏一处后输出对应 `FAIL`。

- **R10** `AGENTS.md` 与 `project.md` 反映新流程：路线图可选、目录与编号说明、跨阶段硬规则、技能现状。
  - **反例**：`AGENTS.md` 流程表没有路线图一行，读者不知道有这一步；或编号说明仍说路线图占用 `NNN`。
  - **可观察证据**：在 `AGENTS.md` 第 2、3、5 节能读到路线图相应条目；`project.md` 的技能现状列出 `sdd-roadmap`。

## 5. 明确不做

- 不做排期、估时和优先级打分。理由：切片之间只比先后，不比投入产出；打分会产生假精度。
- 不做路线图与切片的编号同步工具。理由：同编号增补已明确允许，工具无从判断两份目录的关系。
- 不改动 `p00-001` 至 `p00-007` 的既有 spec。理由：用户决定不回填，避免为历史文档补字段。
- 不处理跨大需求的依赖。理由：一份路线图只覆盖一个 `pNN`，跨大需求排序属于项目级排期，不在本流程范围。
- 不改变 `sdd-plan`、`sdd-impl`、`sdd-review` 的现有规则。理由：本次只增加路线图层与需求阶段的前置检查。

## 6. 风险与取舍

#### 决策 1：路线图对切片需求的约束力
- 决策：路线图里的切片定义是否约束该切片 spec 的需求条目。
- 选择：约束。spec 的需求超出切片定义时停下，回路线图修订。
- 理由：不约束就会两处互相否决，和「plan 不得推翻 spec 第 6 节」是同一类冲突。
- 放弃了什么：允许 spec 在访谈中就地扩大范围，事后补路线图。
- 何时重新评估：切片定义反复出错、每次访谈都要回修时。

#### 决策 2：编号与顺序的关系
- 决策：编号只保证唯一，还是表示推进顺序。
- 选择：表示顺序。阶段 3 只分配名称与 slug，阶段 4 排定顺序后统一分配编号并回填。
- 理由：编号不表示顺序时，001、002 没有存在价值，读者还得去第 4 节翻译。
- 放弃了什么：批准后自由插入切片而不用重编号。
- 何时重新评估：增补 spec 频繁多到编号顺序已经没有参考价值时。

#### 决策 3：降级时是否清空正文
- 决策：路线图降级重批时，是否像 plan 一样清空正文。
- 选择：不清空，只把 `Status` 改回 `draft` 再改正文。
- 理由：路线图没有「前半段已确认」的分段，清空只会丢掉还要复用的切分。
- 放弃了什么：用清空来强制重新审查全文。
- 何时重新评估：出现只改一行却让整份路线图失去一致性的情况时。

#### 决策 4：路线外增补的编号
- 决策：路线图外的增补 spec 用新编号，还是沿用附着的切片编号。
- 选择：沿用，允许同一编号存在两份目录，`slug` 不同。
- 理由：增补通常是改某一片的局部行为，新编号会让人误以为这是新的推进阶段。
- 放弃了什么：`pNN-NNN` 作为唯一标识。
- 何时重新评估：增补多到需要单独索引时。

#### 决策 5：整体验收由谁判
- 决策：整体完成条件由 Agent 判定，还是由用户判定。
- 选择：默认用户，因为完成条件写的是用户视角的经历；只有能由一条端到端命令走完时才交给 Agent。
- 理由：Agent 无法判断「用户是否顺利完成」这类结果。
- 放弃了什么：全部交给 Agent 自动判定，省一次人工确认。
- 何时重新评估：项目改为无人值守的持续集成时。

#### 决策 6：本次是否走 sdd-plan
- 决策：本次流程变更是否按 spec → plan → impl 完整走一遍。
- 选择：跳过 plan 与 review，在用户逐段确认技能全文后直接落地。
- 理由：用户要求先看 `SKILL.md` 全文再落地，确认后即实现；本次没有独立的方案文档和核查记录。
- 放弃了什么：独立核查者对方案与任务的第三方检查。
- 何时重新评估：本次新增的路线图机制在下一个大需求上出现执行偏差时。
