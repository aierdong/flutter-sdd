# 轻量批准与延期跟进

> 本文件供人类审阅。只读第 1–6 节，就能判断这条流程变更该不该做、做成什么样、代价是什么。

| 字段 | 值 |

## 1. 背景与问题

**现状**：`sdd-grill` 要求通过批准 tag、同一 commit 和 tag 对比来证明人已批准 spec；“下一个再做”的延期事项只留在当前 spec 或 grill 决策日志里，后续启动时没有统一提醒入口。

**问题**：个人或小团队需要为自己已明确作出的决定维护额外 Git 证据；延期事项则容易随着会话结束而被遗忘。Agent 也缺少统一规则，判断什么情况下应写入待办、何时检查。

**为什么现在做**：用户要求简化批准动作，并让明确延期到未来的事项在后续 `sdd-grill` 启动时重新可见。

## 2. 目标

- 人明确表示需求可以进入下一步后，Agent 将 spec 状态记为 `approved` 并继续，不要求额外的 tag 或专用 commit。
- 明确延期到未来的事项自动登记到仓库根目录的 `FOLLOW.UPS.md`，并在每次启动 `sdd-grill` 时检查。
- 用户明确提出的产品、技术、质量或测试要求都可以直接写入 spec；不因其“属于技术”而擅自移到 plan。

**成功后，你能看到/做到**：在对话中确认“可以进入计划”即可继续；“下一个再做”的事项会出现在根目录待办中，并在合适的后续 Grill 会话被提醒。

## 3. 用户场景

### 场景 A：确认需求并进入计划

1. Agent 完成 spec 并通过结构门禁，将其状态保持为 `draft`。
2. 用户阅读后明确表示“需求 OK，可以进入 plan”。
3. Agent 将 `Status` 记为 `approved`，直接进入计划阶段；不要求用户编辑 tag、创建批准 commit 或提供 Git 证据。

### 场景 B：把事项留到以后

1. 访谈中用户决定某项工作不放入当前 spec，而留待未来处理。
2. Agent 确认具体触发条件和完成标准；若“下一个”所指不清，就先问清楚。
3. Agent 将待办、来源、触发条件、完成标准追加到根目录 `FOLLOW.UPS.md`。
4. 下次启动 `sdd-grill` 时，Agent 检查尚未完成的待办，向用户汇报相关或已触发的事项；若当前都不相关且未触发，则简要说明待办数量。触发条件已满足的事项不会被静默忽略或自动标成完成。

## 4. 必须做到

- [ ] **R1** 用户明确表示 spec 可以进入下一步后，Agent 才将 `Status` 设为 `approved` 并继续；lint 通过本身不构成批准。批准不要求 approval tag、专用 commit 或 tag/diff 校验；spec 后续有实质修改时，状态回到 `draft`，受影响的 plan 标为 `stale`。
  - **反例**：只因 lint 通过就把 spec 标为 `approved`；或用户已明确确认后仍要求创建 tag / 特殊 commit 才能继续。
  - **可观察证据**：用户在对话中明确同意进入下一步后，spec 状态为 `approved`，后续流程已开始，仓库无需新增批准 tag。

- [ ] **R2** 用户决定将一项明确工作延期到未来时，Agent 在本次 Grill 中将它追加到仓库根目录 `FOLLOW.UPS.md`，至少记录待办、来源 spec、具体触发条件、完成标准和状态；若“下一个/以后”无法确定触发点，Agent 先向用户澄清。仅仅列入当前 spec 的「明确不做」但没有未来承诺的事项，不自动变成待办。
  - **反例**：访谈日志写着“下一个代码 spec 处理”但 `FOLLOW.UPS.md` 没有记录；待办只写“以后做”而没有触发条件或完成标准。
  - **可观察证据**：当前 Grill 结束前，根目录文件中出现对应待办，包含来源、触发条件、完成标准和未完成状态。

- [ ] **R3** 每次启动 `sdd-grill` 时，Agent 检查根目录 `FOLLOW.UPS.md`；文件不存在时创建空模板。Agent 判断未完成项与当前请求的关联和触发状态，对已触发、相关或不明确的项目逐项向用户说明；若均未触发且无关，可汇总数量。遇到触发已满足或不明确时，先向用户显式提出，不得静默删除、延期或标记完成。状态可按用户处理决定更新为待办或进行中；只有有完成证据时才能标为已完成，标为已取消或改期必须有用户明确决定。
  - **反例**：新一轮 Grill 未读取待办文件；到期事项未告知用户；Agent 自行把未执行事项标成完成。
  - **可观察证据**：启动反馈列出待办及其是否触发；用户作出处理选择后，文件状态与决定一致。

- [ ] **R4** 用户明确提出的技术方案、技术约束、质量要求或测试要求均可作为 spec 内容，Agent 不得仅因其属于技术实现而擅自移至 plan；plan 只补充用户尚未决定的执行拆分与实现细节。
  - **反例**：用户要求将同步调用改为异步或新增单元测试，Agent 以“这是技术细节”为由从 spec 删除并自行留到 plan 决定。
  - **可观察证据**：用户提出的技术/质量/测试约束能在 spec 的目标、R 或第 6 节决策中找到；plan 对应条目不与之冲突。

## 5. 明确不做

- 不建立 issue tracker、负责人、估时、截止日期或额外审批记录。理由：目标是单一轻量待办文件与一次明确的对话确认。
- 不修改 `sdd-plan`、`sdd-impl`、`sdd-review` 的任务执行与证据要求。理由：本次只调整 `sdd-grill` 的批准交接与延期提醒。
- 不把没有未来承诺的「明确不做」事项全部复制到 `FOLLOW.UPS.md`。理由：避免把边界清单变成无差别待办堆积。

## 6. 风险与取舍

| 决策 | 选择 | 理由 | 放弃了什么 | 何时重新评估 |
|---|---|---|---|---|
| 批准方式 | 用户在对话中明确确认；`Status` 仅记录当前状态 | 不增加个人开发者无法从中获益的自我证明步骤，同时保留未批准不得进入 plan 的门槛 | 可离线独立验证的批准凭据 | 出现多人必须审计批准身份的实际需要时 |
| 待办载体 | 仓库根目录单一 `FOLLOW.UPS.md` | 每次启动 Grill 都能从同一位置查到延期事项，不依赖聊天记忆 | issue 系统、自动派发与提醒服务 | 待办数量或协作规模使单文件难以维护时 |
| 延期记录范围 | 只记录有明确未来动作的延期；必须有触发条件与完成标准 | 避免“以后再说”无限悬空，也避免把所有非目标变成待办 | 只写一句“下次做”的极简记录 | 触发条件无法稳定判断时 |
