# 轻量 SDD：实现阶段（sdd-impl）

> 本文件是需求说明，简称 spec。第 1–6 节说明实现技能的行为与边界，第 7 节列出待用户决定的问题。R1 等编号用于定位必须满足的需求。

- Spec：`p00-005-lightweight-sdd-impl`
- 类型：`new`
- 上游：`—`
- 附带交付：`—`
- Status：`approved`
- 版本：`v1`

## 1. 背景与问题

**现状**：仓库已经产出 `sdd-requirement` 和 `sdd-plan` 两个通用技能，尚无 `sdd-impl`。执行计划称为 plan，由用户批准后交给实现阶段执行。

**问题**：用户希望借鉴 Kiro 的编码流程，但不接受强制测试驱动开发（TDD）、逐任务重复检查、逐任务审查，以及必须保存测试证据的交付方式。这些步骤的时间和成本高于本次希望获得的收益。

**为什么现在做**：实现技能需要承接已批准计划，并为后续审查提供实际改动和执行结果。若不先明确边界，Agent 容易以保证质量为由追加计划外工作。

本次先完善 `sdd-impl` 自身设计，再处理其他内容的同步调整。Demo 工程及设计副产品不构成本次通用技能的约束。已有两个技能是交接基础，可以在后续同步步骤中迭代，不是不可修改的前提。

## 2. 目标

- Agent 按已批准计划连续完成实现，不重新决定需求或方案。
- Agent 只执行计划安排的必要检查，默认复用仍然适用的已有结果。
- Agent 在既定范围内自主处理实现细节和检查失败，不把每一步都变成用户确认。
- Agent 用任务勾选和对话说明进度，不额外生成证据文档；实现结束后自动交接审查。

**成功后，用户能看到的结果**：Agent 完成计划内改动和必要检查，简要说明实际结果，再自动进入审查；没有测试任务也能结束实现阶段。

## 3. 用户场景

### 场景 A：计划没有安排检查

1. 用户要求执行一份已批准的计划，内容是简单界面调整，没有安排测试或其他检查。
2. Agent 完成改动并勾选实现任务，不补测试，不自行运行编译、静态检查或 lint（格式及部分规则的检查脚本）。
3. Agent 说明改动结果及未安排检查的情况，自动交给 `sdd-review`，不要求用户提供测试证据。

### 场景 B：集中检查失败

1. 计划安排若干实现任务，最后安排一个相关范围的检查任务。
2. Agent 完成各项改动后勾选实现任务，检查任务保持未勾选。
3. 检查失败后，Agent 在不改变需求、方案及授权范围的前提下自行修复，定向重跑。
4. 同一独立失败问题经过三轮修复与重跑仍未解决时，Agent 停止，保留现场并报告，不继续消耗轮次。

### 场景 C：复用已有结果

1. 用户提供某项检查的结果，或前序任务已执行同一项检查。
2. 计划没有禁止复用，结果仍适用于当前代码和相关环境，后续改动也没有使其失效。
3. Agent 默认复用结果，不要求当前 Agent 再运行一次，也不要求补交新的证据。
4. 计划明确说明前次检查结果不能复用时，Agent 按计划重新执行。

## 4. 必须做到

- [ ] **R1** 用户启动实现后，Agent 只接手需求和计划均已批准、且没有待决需求的工作；满足条件时按任务依赖连续执行，不在普通内部步骤间等待用户说“继续”。
  - **反例**：计划未批准就改代码；每完成一个普通任务都要求用户再次确认才能继续。
  - **可观察证据**：不满足前置条件时，Agent 指出阻塞点；满足条件后，Agent 连续推进授权范围内的工作。

- [ ] **R2** Agent 的测试、编译、静态检查、lint 及其他验收检查均以已批准计划为准；计划未安排时不自行追加，发现确有必要时先说明原因，请用户决定是否补入计划。
  - **反例**：计划只要求改间距，Agent 却以“自检”为名运行全量测试；Agent 发现风险后未经用户同意追加检查。
  - **可观察证据**：实际执行的检查有计划依据或用户明确授权；没有检查安排时，Agent 不以缺少测试结果为由阻止实现阶段结束。

- [ ] **R3** 技能不强制 TDD，不要求先失败再通过的红绿循环，也不把存在测试或测试证据设为统一交付条件。
  - **反例**：每个任务编码前必须先生成失败测试；简单界面调整没有测试证据就被判为实现不完整。
  - **可观察证据**：技能允许计划明确安排的测试方式，也允许不安排测试；执行过程没有技能额外强加的红绿步骤。

- [ ] **R4** 测试和其他检查本身属于计划任务；默认在实现任务之后集中执行，只覆盖相关部分，必要的中途检查须由计划明确安排。
  - **反例**：Agent 给每个实现任务都插入测试，最后又默认运行全量测试；同一项检查因分属不同任务被重复执行。
  - **可观察证据**：任务执行顺序遵循计划；集中检查与中途检查均有明确任务落点，不因技能默认规则扩大到全量。

- [ ] **R5** 除非计划明确说明前次检查结果不能复用，Agent 默认复用用户或前序任务提供的适用结果；后续修改使结果失效时，才重新执行受影响的计划内检查。
  - **反例**：计划未禁止复用，Agent 却因结果不是自己执行或来自上一个任务而拒绝使用；Agent 将已失效的结果当成当前通过结果。
  - **可观察证据**：交付说明区分复用与本次执行；未禁止复用时，不额外要求新鲜证据，也不凭空声称旧结果适用。

- [ ] **R6** 实现任务的改动完成后，Agent 即可勾选该任务；检查任务单独记录状态，勾选不表示检查通过，中断恢复也不因缺少测试证据而重做已经完成的任务。
  - **反例**：所有实现任务必须等待末尾检查通过才能勾选；Agent 把实现任务已勾选写成“全部验证通过”。
  - **可观察证据**：集中检查尚未执行时，已完成的实现任务可保持勾选，检查任务未勾选；恢复后能区分已改完与尚待检查的内容。

- [ ] **R7** Agent 可以自行决定不改变需求和方案的局部写法，也可为现有任务新增计划文件清单之外的必要辅助文件；新增辅助文件不要求先修订计划，但须在交付中说明。需要改变需求、方案或超出上述授权时，Agent 停止并交用户决定。
  - **反例**：新增必要的辅助文件也必须重新批准计划；Agent 借辅助文件之名增加功能、改变方案或顺手重构无关内容。
  - **可观察证据**：新增文件服务于已有任务，交付中有说明；需要改变上游时，Agent 报告原因而不是自行改写上游。

- [ ] **R8** 计划内检查失败后，Agent 可在既定授权范围内自行修复，不逐次请用户确认；重跑仅覆盖失败项及修复直接影响的、计划已安排的检查。
  - **反例**：每次普通修复都等待用户批准；修复一个局部失败后默认重跑全部检查或插入独立审查。
  - **可观察证据**：修复与重跑连续进行，重跑范围与失败项、修复影响相对应；需要改变上游或扩大授权时停止。

- [ ] **R9** 每个独立失败问题最多自动修复并重跑三轮，首次执行检查不计入轮次；同一问题跨任务和恢复会话继续累计，第三轮仍失败时停止，保留现场，不自动回滚已有改动，并报告已尝试内容及遗留问题。
  - **反例**：同一失败进入第四轮自动修复；切换任务或恢复会话后把次数清零；两个独立问题被强制共用三轮额度。
  - **可观察证据**：对话中能区分各问题的修复轮次；达到上限后不再自动修补，也不把失败写成通过。

- [ ] **R10** 实现阶段不默认给单个任务安排独立审查，不套用逐任务“审查、修正、再审查”的循环。
  - **反例**：每个任务完成后都启动审查 Agent，审查通过才允许执行下一个任务。
  - **可观察证据**：普通实现任务之间没有技能强制插入的独立审查；计划内检查失败按修复规则处理，不自动升级为审查循环。

- [ ] **R11** Agent 不单独生成实现记录或证据报告，不强制归档原始输出、截图和日志，也不默认创建 Git 提交；交付时更新任务勾选，并在对话中说明实际改动、检查结果和未完成事项。
  - **反例**：必须生成额外报告或保存原始测试输出才能结束实现；未经用户或计划要求自动提交；未执行的检查被写成通过。
  - **可观察证据**：交付说明能区分本次执行、复用、未运行及失败；没有技能强制新增的记录文件或提交步骤。用户或计划明确要求的产物和提交不受此默认限制。

- [ ] **R12** 实现任务和计划内检查全部完成后，Agent 自动启动 `sdd-review`，不再等待一次用户确认；审查通过前只宣称实现阶段完成，不宣称整个 spec 完成。
  - **反例**：实现结束后必须等用户说“继续”才进入审查；实现 Agent 未经审查就宣布整个需求完成。
  - **可观察证据**：正常完成后出现自动审查交接；审查技能不可用时，Agent 报告交接受阻，不自行编造审查流程或通过结论。

## 5. 明确不做

- 不在本次设计阶段同步修改其他技能、流程入口或 Demo 规范。理由：用户要求先完善实现技能，再处理相关内容的同步调整。
- 不实现或重新设计 `sdd-review`，不规定其内部审查与修复循环。理由：本次只定义实现阶段及其自动交接条件。
- 不把 Demo 的逐需求测试、全量测试和证据归档要求移植进通用技能。理由：用户明确说明 Demo 和设计副产品不构成本次约束。
- 不增加检查配置系统、通用验证框架或额外状态与证据文件。理由：计划任务、任务勾选和对话已承载本次需要的信息。
- 不默认运行计划外检查，不默认逐任务审查，也不默认创建 Git 提交。理由：这些行为会增加未经批准的成本或操作。

## 6. 风险与取舍

#### 决策 1：分两步推进
- 决策：先明确实现技能，再处理周边一致性。
- 选择：先完善本次设计，不因 Demo 或已有技能的不同口径阻止讨论；后续再同步必要的交接变更。
- 理由：避免在实现阶段规则尚未确定时扩散修改。
- 放弃了什么：本次立即把所有文档和技能改成一致。
- 何时重新评估：实现技能设计基本完善、进入同步调整步骤时。

#### 决策 2：检查完全来自计划
- 决策：Agent 是否可以以质量保证为由追加检查。
- 选择：不能；测试、编译、静态检查与 lint 都以计划为准，需要新增时先请用户决定。
- 理由：让用户在批准计划时就能控制执行成本。
- 放弃了什么：Agent 自行追加检查所带来的额外发现机会；计划遗漏可能保留到后续审查。
- 何时重新评估：用户明确要求增加检查或修订计划时。

#### 决策 3：默认复用结果
- 决策：是否要求每次都产生新的检查结果。
- 选择：计划未明确禁止时，默认复用仍适用的结果，不按执行者、任务或会话划分有效性。
- 理由：减少相同状态下的重复执行，不把新鲜证据变成交付要求。
- 放弃了什么：每次由当前 Agent 重新执行所能获得的独立确认。
- 何时重新评估：计划明确禁止复用，或代码、环境变化使结果失效时。

#### 决策 4：自主实现与有限修复
- 决策：哪些操作无需逐次确认。
- 选择：局部实现、必要辅助文件、范围内失败修复可自行处理；每个独立失败问题最多三轮修复与重跑。
- 理由：减少普通实现中的往返，同时限制单个问题的自动消耗。
- 放弃了什么：文件清单的封闭白名单，以及无限自动修复的可能性。
- 何时重新评估：达到轮次上限，或必须改变需求、方案及授权范围时。

#### 决策 5：轻量进度与交付
- 决策：怎样记录进度和结果。
- 选择：改动完成即可勾选实现任务，检查任务单独记录；结果在对话中说明，不另建实现记录，不自动提交。
- 理由：支持续做，不额外制造证据产物。
- 放弃了什么：脱离对话的独立实现档案；恢复时可能需要找回先前的结果和修复轮次。
- 何时重新评估：用户或计划明确要求记录产物、提交或其他保存方式时。

#### 决策 6：自动交接独立审查阶段
- 决策：实现完成后是否再等用户确认。
- 选择：自动启动 `sdd-review`，不在每个任务之间插入审查。
- 理由：把完整改动交给审查阶段集中判断，减少阶段间等待。
- 放弃了什么：用户在每次交接前手动选择启动时机；审查技能不可用时只能报告受阻。
- 何时重新评估：审查技能可用性或交接契约发生变化时。

## 7. 审阅问题

本次无待决问题。用户已确认本需求，并明确允许跳过 `sdd-plan`，直接编写实现技能。
