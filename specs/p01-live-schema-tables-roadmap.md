# 真实 PostgreSQL 连接与 schema 表详情页（路线图）

> 本文件供人类审阅。第 1–2 节说明全部做完能完成什么、怎样算完成；第 3–4 节说明拆成哪几块、按什么顺序做；第 5 节说明哪些行为必须一致。

- 路线图：`p01`
- 名称：真实连接 PostgreSQL 的 schema 表详情页
- Status：`approved`
- 版本：`v1`

> 批准方式：用户明确同意切片划分与推进顺序后，Agent 把 `Status` 记为 `approved`。批准不覆盖任何切片的需求内容，那些需求仍由各自的 `spec.md` 单独批准。

## 1. 整体目标与边界

**整体目标**：用户从输入一组 PostgreSQL 连接参数开始，连上数据库、选定一个 schema、看到其中每张表和每个视图的六项真实信息，再在同一连接内换一个 schema 或刷新，全程不重启应用。

**整体不做**：

- 不做 database、schema、table 三级树，也不做字段、约束、外键详情面板。理由：那是完整浏览器的形态，属于另一个阶段；本阶段只在已有的单 schema 表格页上补齐真实数据。
- 不做任何写入、DDL 或表数据浏览。理由：`project.md` 约束对目标库只读，读取范围限于元数据。
- 不做连接保存、连接列表与连接切换。理由：`docs/standards/coding.md` 的 FSD-09 要求连接信息只存在于内存；用户本次只要求一条连接。
- 不做物化视图、外部表、序列、索引等其它对象类型。理由：用户只要求 table 与 view 两类。
- 不做自动刷新、轮询或结构变更监听。理由：用户明确要求刷新由用户自己触发。
- 不做分页、虚拟滚动、导出 CSV。理由：沿用 `p00-001` 已定的范围，行数规模在桌面滚动能力之内。

## 2. 整体完成条件

- 完成条件：用户用真实连接参数连上一个 PostgreSQL 库，在一个 schema 里看到每张表和每个视图的六项真实信息，再换一个 schema 并刷新，两次看到的表格内容都对应库里的实际结构。
- 操作路径：启动应用 → 填连接参数并连接 → 看到该库的 schema 列表 → 选定 schema 看到表和视图的六列 → 在库里新建一张表 → 回到应用点刷新看到新表 → 切到另一个 schema 看到该 schema 的表格内容
- 验证方式：`用户走主路径，Agent 准备数据`
- 验证者：`用户`

## 3. 切片清单

#### 切片：连接真实数据库并看到 schema 列表
- 编号：`p01-001`
- slug：`live-connection`
- 解决什么问题：应用一直显示演示数据，用户无法确认它能不能连上自己的库，也不知道库里有哪些 schema。
- 做完后用户能：填入主机、端口、数据库、用户名和密码并连上，页头换成真实连接信息，页面列出该库的全部 schema 名称；连不上时看到带错误码的失败提示。
- 前置：无

#### 切片：选定 schema 的表与视图六字段列表
- 编号：`p01-002`
- slug：`schema-relation-list`
- 解决什么问题：用户不知道选中的 schema 里有哪些表和视图，也看不到它们的列数、估算行数、大小与描述。
- 做完后用户能：看到该 schema 下每张表、每个视图的名称、类型、描述、列数、估算行数、大小，演示数据被真实数据替换。
- 前置：`001`（提供：一条可用的真实连接，以及该库的 schema 列表）

#### 切片：同一连接内换 schema 与刷新
- 编号：`p01-003`
- slug：`switch-schema-and-refresh`
- 解决什么问题：表结构在外部改动后用户只能重启应用才能看到，也无法在不重连的情况下查看另一个 schema。
- 做完后用户能：在页头切到另一个 schema，或点刷新，表格立即显示对应的最新结构与数值。
- 前置：`002`（提供：一个 schema 的表与视图六字段表格）

## 4. 依赖与顺序

- 推进顺序：001 → 002 → 003
- 顺序理由：没有真实连接就取不到任何元数据；六字段表格要先存在，换 schema 与刷新才有可切换的对象。

## 5. 跨切片约定

#### 约定：失败提示格式统一
- 要求：连接失败或取数失败时，界面文案都写成「消息（错误码：错误码值）」，错误码区域只用连接、schema、表三种，并集中定义在同一份码表里。
- 覆盖切片：001、002、003
- 留给各切片 plan 决定：具体错误码编号，以及面向用户的消息措辞。

#### 约定：密码不出现在界面和日志
- 要求：密码不出现在界面文案、错误提示和日志里。除密码以外的失败细节可以按原样展示，让用户直接看到真实原因。
- 覆盖切片：001、002、003
- 留给各切片 plan 决定：日志记录哪些字段，以及密码遮蔽的实现方式。

#### 约定：始终是同一个页面
- 要求：三个切片交付完成后，用户面对的仍是 `p00-001` 交付的页头加表格区域这一个页面；连接入口、schema 选择与刷新都在这个页面上增加，不新增第二个页面，也不做导航跳转。
- 覆盖切片：001、002、003
- 留给各切片 plan 决定：连接参数入口与 schema 选择控件的具体形态和位置。

#### 约定：重新取数期间不显示上一份 schema 的数据
- 要求：切换 schema 或刷新时，表格区域先进入加载状态，不把上一份 schema 的行留在屏幕上冒充新结果。
- 覆盖切片：002、003
- 留给各切片 plan 决定：加载态用进度指示还是骨架，以及刷新时是否保留当前排序。

#### 约定：空态与失败态沿用原有呈现
- 要求：schema 下没有表时保留六列表头并在表体提示；失败时替换整个表格区域；这两种状态下页头都保持可见。
- 覆盖切片：002、003
- 留给各切片 plan 决定：提示文案的具体措辞。

## 6. 决策记录

#### 决定：页面骨架沿用 p00-001 而不是 UI-06
- 决定：新页面用 `p00-001` 的页头加表格区域，还是用 `docs/standards/ui.md` UI-06 的工具栏加左树加右详情。
- 选择：沿用 `p00-001` 的页头加表格区域，schema 切换放在页头。
- 放弃：UI-06 的树加详情骨架。它要求字段、约束、外键三段详情，与本次只交付六字段表格不一致。
- 何时重新评估：用户要求浏览 database、schema、table 三级结构，或要求查看字段、约束、外键时。各切片的 `plan` 需按 `AGENTS.md` 第 5 条标注对 UI-06 的覆盖条款、理由与失效条件。
- 与下一条决策的差异：UI-06 是页面形态标准，改它会牵动后续所有页面，所以这里留覆盖；`FSD-08`、`FSD-09` 只约束错误信息怎么呈现，改它们不改变结构，所以那里直接改规范。

#### 决定：这件事另开一个阶段 p01
- 决定：这件事放在已使用的 `p00`，还是新开 `p01`。
- 选择：新开 `p01`，切片从 `p01-001` 起编号，并同步更新 `project.md` 的阶段行。
- 放弃：继续用 `p00` 接在 008 之后。那样一个阶段会同时容纳流程技能和这件事，与 `AGENTS.md` 第 3 节冲突。
- 何时重新评估：暂不。

#### 决定：切三片而不是四片
- 决定：把换 schema 和刷新拆成两片，还是合成一片。
- 选择：合成 `p01-003`。两者都是同一条连接上重新取数，用户看到的是同一件事：表格换到最新内容。
- 放弃：拆成两片。它们各自只剩很薄的一层状态刷新，单独验收价值低。
- 何时重新评估：刷新需要独立的历史、进度或差异展示时。

#### 决定：六字段详情放在同一片交付
- 决定：先交付名称与类型的列表、之后再补另外四个字段，还是六字段一次交付。
- 选择：`p01-002` 一次交付六字段。
- 放弃：拆成两片。中间状态会是一张部分列显示缺省值的表格，用户在界面上看到的是残缺结果。
- 何时重新评估：某个字段需要明显更长的额外计算，导致整片无法一次性交付时。

#### 决定：失败细节按原样展示，只遮蔽密码
- 决定：连接失败或取数失败时，是否把驱动返回的错误原文和完整连接串展示给用户。
- 选择：只要求密码不出现。完整连接串与驱动异常原文可以显示在界面和日志里，让用户看到真实失败原因。
- 放弃：把每一条驱动错误翻译成自有文案。那样要为每个驱动错误建映射，翻译工作量与漏翻风险都不划算，而且用户看到的仍是被改写的二手结论。
- 何时重新评估：错误文案里出现密码，或日志需要交付给项目外的人排查时。本条与 `docs/standards/coding.md` 当时的 FSD-08、FSD-09 原文冲突，处置见下一条决策记录。

#### 决定：同步修订代码规范，不留覆盖
- 决定：上一条松动与 `docs/standards/coding.md` 的冲突，改规范解决，还是留给各切片 `plan` 标覆盖。
- 选择：直接修订 `docs/standards/coding.md`。FSD-08 只保留「驱动异常对象不得越过数据层」，并写明错误原文可以经失败消息上浮；FSD-09 改为只禁止密码进入错误文案与日志，并要求展示或记录前主动抹掉文本里的密码。版本从 v5 升到 v6，`steering.md` 索引行的版本标注同步。
- 放弃：不改规范，让三个切片的 `plan` 各自标覆盖。同一段覆盖理由要写三遍，每片审查还要再确认一次，成本高于改一次规范。
- 何时重新评估：密码重新成为必须隔离的信息时，或需要把日志交给项目外的人排查时。依据：`AGENTS.md` 第 6 节允许这两份规范随时修订，不需要 spec 批准。
- 生效时点：这一条与 `project.md` 的阶段行已经按同一节规定先行落地，不等本路线图批准。

#### 决定：估算行数与大小按原值显示，界面不标注「估算」
- 决定：六字段里的估算行数和大小是估算值，界面是否需要标出来。
- 选择：不标注，直接显示数值。
- 放弃：在列头或单元格里加「估算」字样。
- 何时重新评估：用户拿这两个数做容量决策时。
- 对应：`p01-002`、`p01-003` 的表格显示
