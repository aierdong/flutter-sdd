# 把依赖决策移出代码规范

> 本文件供人类审阅。只读第 1–6 节，就能判断这条需求该不该做、做成什么样、代价是什么。

| 字段 | 值 |
|---|---|
| Spec | `p00-004-dependency-scope` |
| 类型 | `fix` |
| 上游 | `p00-003-lightweight-sdd-plan` |
| 附带交付 | `—` |
| Status | `approved` |
| 版本 | `v1` |

> 批准方式：用户明确确认需求可以进入下一步后，Agent 将 `Status` 记为 `approved`。不要求批准 tag、专用 commit 或其它凭据；状态仅用于标记流程位置。

## 1. 背景与问题

**现状**：`docs/standards/coding.md` v1 的 `FSD-12`（`:301`）规定第三方依赖只能是 Flutter SDK、`cupertino_icons`、PostgreSQL 驱动与 `flutter_lints`，并允许"在 spec 第 6 节记录决策"后新增。同一条（`:302`）禁止 `build_runner`、`freezed`、`json_serializable`、`mockito`。而 `docs/standards/ui.md` v1 的 `UI-01` 规定 `lib/ui/**` 与 `lib/app.dart` 只使用 `shadcn_flutter`，并写明"按 coding.md FSD-12，必须先写进当前 spec 第 6 节的决策，再改 `pubspec.yaml`"。

**问题**：两份规范互相把对方当前置条件。`p00-001` 一进入计划阶段就要决定 UI 组件库，`ui.md` 说要 shadcn_flutter，`coding.md` 说白名单里没有；改白名单要先有 spec，而 spec 的第 6 节决策又必须落在白名单允许的范围内——环上没有出口。`p00-001` 因此停在计划阶段之前。

同一个 `FSD-12` 还有一处自相矛盾：`coding.md:508` 规定"没有审计动作的规则不得写进本文件"，而依赖条款至今没有对应审计动作——`A6` 只管文件规模（250 行），`:499` 的证据行却写成"无新增依赖；A6 无输出"，把两件事塞进一格。也就是说，这条规则从写下的那天起就无法被验证。

**为什么现在做**：`FUP-002` 的剩余部分就是它；不解开，`p00-001` 无法进入计划阶段，任何要用组件库的 spec 都会先撞上同一堵墙。

## 2. 目标

- 让 `coding.md` 只约束"代码怎么写"，不再决定"可以引入什么"。
- 让 UI 组件库由 `ui.md` 单独决定，不再向代码规范追认流程。
- 让两份规范之间不再互相引用对方职责外的内容，冲突源消失而非被绕过。

**成功后，你能看到/做到**：打开 `coding.md` 找不到任何"允许/禁止某个包"的条款；打开 `ui.md` 看不到对 `coding.md` 依赖条款的引用；`p00-001` 的计划阶段不再因依赖冲突停下，组件库按 `覆盖` 处理。

## 3. 用户场景

### 场景 A：给 `p00-001` 做计划

1. 用户启动 `sdd-plan`，读 `p00-001` 第 6 节，看到"只用 Flutter 内置组件"。
2. 按 `steering.md` 加载 `ui.md`，看到 `UI-01` 要求唯一组件库是 shadcn_flutter。
3. 两处冲突：spec 说本次用内置组件，规范说统一用组件库。
4. 系统按"越具体越优先"判定为 `覆盖`：第 2 节标 `覆盖 docs/standards/ui.md UI-01`，第 3.2 节写理由与失效条件。
5. 计划继续推进，不再需要先改规范。

### 场景 B：实现阶段有人想引入一个新包（异常场景）

1. 实现中发现需要解析 TOML，手写太慢。
2. 现在：`FSD-12` 禁止，但没有审计动作能发现，`A6` 只查行数——规则存在而不可验证，实际拦不住。
3. 应该：`coding.md` 对此不表态；要不要引、引哪个，由当前 spec 第 6 节决策，`review.md` 核对实现与该决策一致。

## 4. 必须做到

- [ ] **R1** `coding.md` 的 `FSD-12` 只保留"单文件不超过 250 行""固定豁免清单""规范变更需版本化"三项，标题改为「规模与豁免」，不再出现任何关于第三方依赖或代码生成工具的条款。
  - **反例**：把白名单改写成"允许清单"或"基础依赖清单"；给某个包加"本次例外"的括号注；保留"不使用代码生成"整条；把依赖条款挪到别的小节继续生效。
  - **可观察证据**：`FSD-12` 段落内不再出现「第三方依赖」「依赖只允许」「build_runner」「json_serializable」「mockito」等条款文字；`freezed` 只允许出现在「固定豁免」行的文件名 `*.freezed.dart` 里，不得作为工具禁令出现。

- [ ] **R2** `coding.md` 的适用范围不含 `pubspec.yaml`：头部「适用」字段只列 `lib/**`、`test/**`、`analysis_options.yaml`。
  - **反例**：保留 `pubspec.yaml` 并注明"仅用于核对包名"；或把它挪到正文某处继续约束。
  - **可观察证据**：头部「适用」行 grep 不到 `pubspec`。

- [ ] **R3** 同类依赖限制在全文范围内一并清除：`FSD-09` 只保留"连接信息只存在于内存、不写入文件、`SharedPreferences`、数据库或剪贴板"，`FSD-03` 只保留"测试替身手写，命名 `FakeXxx` 或 `StubXxx`"，`A9` 只保留"豁免与 spec 第 6 节的决策一致"。
  - **反例**：删了 `FSD-12` 却留着 `A9` 的「新增依赖」；或把 `FSD-09` 整条删掉，连"连接信息不落盘"的安全约束一起丢了；或把 `FSD-03` 的"测试替身手写"也删掉，等于允许生成替身。
  - **可观察证据**：`coding.md` 全文 grep「新增依赖」「不引入 mockito」零命中；`FSD-09` 该行仍含「不得写入文件」；`FSD-03` 该行仍含「测试替身手写」。

- [ ] **R4** `ui.md` 不再引用 `coding.md` 的依赖条款：`UI-01` 里"按 coding.md FSD-12，必须先写进当前 spec 第 6 节的决策"整条子项删除，`UI-01` 仍规定唯一组件库是 `shadcn_flutter`。
  - **反例**：保留指向 `FSD-12` 的引用，形成悬空引用；或反过来把"唯一组件库"也删掉，导致 UI 没有组件库可依。
  - **可观察证据**：`ui.md` grep `FSD-12` 零命中；`UI-01` 仍含 `shadcn_flutter` 与"唯一组件库"。

- [ ] **R5** 两份规范与索引同步升版：`coding.md`、`ui.md` 顶部版本各自递增到 `v2`，`steering.md` 索引里这两行的版本标注同步改为 `v2`。
  - **反例**：只改正文不改版本；改了版本却不改 `steering.md`，索引仍写 `v1`。
  - **可观察证据**：两份文件头部「版本」为 `v2`；`steering.md` 对应两行均为 `v2`。

- [ ] **R6** 本次只删不增：`coding.md` 的 FSD 条目数与审计动作数保持不变（仍为 `FSD-01`–`FSD-12`、`A0`–`A9`），删掉的条款不换成等价的间接限制。
  - **反例**：删了白名单又加一条"依赖变更需在 review 中说明"；或新增"本规范不涉及依赖"的声明条款。
  - **可观察证据**：`grep -c '^### FSD-'` 与 `grep -c '^### A[0-9]'` 在改前改后相同；diff 的新增行只有版本号、适用范围与删改后的残句。

- [ ] **R7** 删除可逆：本次删掉的原文逐字记录在 `grill.md` 的决策区，恢复时可直接贴回。
  - **反例**：只写"删掉了依赖白名单"，事后无法还原原文；或记录时改写、压缩了原句。
  - **可观察证据**：从 `grill.md` 复制的文本与改动前的 `coding.md` 对应段落逐字一致。

## 5. 明确不做

- 不删除 `FSD-12` 豁免清单里的 `*.g.dart`、`*.freezed.dart`、`lib/generated/**`。理由：删掉"能否使用生成工具"不等于"生成产物要计入 250 行规模"，那会把生成代码逼进规模统计。
- 不修改 `FSD-03` 里"测试替身手写，命名 `FakeXxx` 或 `StubXxx`"的写法要求。理由：它约束测试怎么写，与"能否引入某个包"无关。
- 不修改 `p00-001` 第 6 节「只用 Flutter 内置组件」。理由：spec 的特例优先于通用规范，由 plan 标 `覆盖` 处理；改 spec 会让一次性的特例变成永久状态。
- 不在 `AGENTS.md` 新增依赖相关硬规则。理由：用户明确不设专门规则，技术选型已由 spec 第 6 节承担。
- 不改 `FSD-01`–`FSD-11` 的写法要求，也不改 `ui.md` 的视觉条款（`UI-02`–`UI-08`）。理由：本次只处理"决定能引什么"这一类越界。
- 不新建规范文档，也不改 `project.md`、`AGENTS.md`、技能文件。理由：本次是两份规范的职责收口，不涉及流程。

## 6. 风险与取舍

| 决策 | 选择 | 理由 | 放弃了什么 | 何时重新评估 |
|---|---|---|---|---|
| 依赖条款整体删除 | `coding.md` 不再规定可引入哪些依赖 | 代码规范无法决定引入什么；白名单与 `ui.md` 构成死锁，且没有审计动作，本就不可验证 | 失去"一眼看到允许哪些包"的清单，判断改由 spec 第 6 节承担 | 出现未经 spec 决策就改 `pubspec.yaml` 的情况时 |
| 修一类而非只修 `FSD-12` | `FSD-09`、`FSD-03`、`A9` 的依赖限制一并清除 | 同一原则下留残留，下次还会以另一种形式冲突 | 改动面比最小方案大，diff 涉及四处 | 暂不 |
| 不加"本规范不涉及依赖"声明 | 只删不写 | `coding.md:508` 要求每条规则有审计动作，声明类元规则无法验证 | 将来可能有人重新加白名单，只能靠 `grill.md` 与本次 spec 说明缘由 | 第二次出现同类越界时 |
| `ui.md` 只删引用、不动组件库规定 | 保留 `UI-01` 的 `shadcn_flutter` | 组件库是视觉决定，属于 UI 规范职责；越界的只是向 `coding.md` 追认流程 | — | 暂不 |
