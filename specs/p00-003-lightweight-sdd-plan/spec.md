# 轻量 SDD：计划阶段（sdd-plan）

> 本文件供人类审阅。只读第 1–6 节，就能判断这条流程变更该不该做、做成什么样、代价是什么。

| 字段 | 值 |
|---|---|

| 上游 | `—` |

## 1. 背景与问题

**现状**：`AGENTS.md` 定义了四段流程，但只有 `sdd-grill` 是可执行的技能。计划阶段的通过条件只有一句"每条 R 都有设计、任务与验证；无待决问题"，没有技能、没有模板、没有校验脚本。已批准的 `p00-001-schema-tables-page` 因此卡在计划阶段：它 11 条 R 的具体实现方式、影响文件与验证命令都还没有落点。

同时，参考过的 Kiro 流程把设计写成 `design.md` + `tasks.md` + `research.md` 三份长文档，一次性生成后交人审。这套做法有三个问题：文档量把人挡在"走哪条路"之外；设计里没人做过的选择被写得像既定事实；任务计划面向多 Agent 并行分派（`(P)`、`_Depends_`、测试档位标签），在单人串行场景里是纯开销。

**问题**：没有 `sdd-plan`，已批准的 spec 无法转成可执行任务；人也没有一个时机去指定 spec 装不下的技术取向（组件库、密度、结构归属）。这些取向要么靠口头在对话里交代一次、下个 spec 再重说，要么被 Agent 自行决定后写进代码。

**为什么现在做**：`p00-001` 已批准，是流程的第一个真实用例。计划阶段的形状定得越晚，后面 `sdd-impl` / `sdd-review` 越容易照着错的形状长。

## 2. 目标

- 让已批准的 `spec.md` 能稳定产出 `plan.md`：方案摘要、约束与来源、设计、任务、`R → 验证`、风险。
- 让规范按需加载：先扫 `steering.md` 索引决定读什么，再精读，而不是把 `docs/` 全读一遍或凭印象引用条款。
- 让技术取向通过访谈进入设计，而不是靠 Agent 猜或靠人一次性交代。
- 让人只在一个时点集中表态：方案摘要；确认后设计与任务由 Agent 完成并自检。
- 让长效技术约定有固定归属，不会只活在某一份 `plan.md` 里。

**成功后，你能看到/做到**：给 `sdd-plan` 一个已批准的 spec 编号，它会先给出 30 行以内的方案摘要和几条待拍板的选型；你确认后，同目录出现完整的 `plan.md`，`plan_lint.py` 退出码 0，任务带 checkbox 与验证命令，可以直接交给 `sdd-impl`。

## 3. 用户场景

### 场景 A：从已批准 spec 到可执行 plan

1. 用户说"给 `p00-001` 做计划"。
2. Agent 先校验 spec 是 `approved`、第 7 节无待决项，然后扫 `steering.md` 索引与 `lib/`，列出必读 / 选读 / 不读三组文档。
3. Agent 精读必读项，产出约束表；发现某条口头约定属于长效约定且没有标准文档时，停下来说明要先补哪份文档。
4. Agent 按维度逐个提问（一次一问），覆盖结构归属、数据流、依赖选型、失败路径、观感密度、既有模式复用。
5. Agent 写出第 1–2 节并停下，`Status` 为 `draft`，请用户确认路线与选型。
6. 用户确认后，Agent 独立完成第 3–6 节，跑 `plan_lint.py` 退出码 0，`Status` 为 `design-ok`。
7. 用户说"审核通过，可以下一步"，`Status` 改为 `approved`。

### 场景 B：spec 的特例覆盖通用规范

1. `docs/standards/ui.md` 规定唯一组件库是 shadcn_flutter；`p00-001` 第 6 节规定本次只用内置组件。
2. Agent 判定这是"更具体的来源覆盖更一般的来源"，不中断，也不回 spec。
3. 第 2 节该行去向写 `覆盖`，影响格写 `覆盖 docs/standards/ui.md UI-01`；第 3.2 节加一条来源为 `覆盖` 的决策，写明理由与失效条件（本 spec 结束后回到 `ui.md`）。
4. `plan_lint.py` 核对被覆盖的文档确实存在、决策表确有该行；`Status` 可以走到 `approved`。

### 场景 C：口头约定缺标准文档

1. 用户在设计访谈中说"所有报告统一输出 TSV"。
2. Agent 判定这是影响后续所有 spec 的长效约定，而 `docs/standards/` 下没有相应规范。
3. Agent 停下：说明需要先补哪份文档，`plan.md` 的 `Status` 留在 `draft`，不写设计与任务。
4. 用户另开一次会话补完规范后，回到本 spec 的计划阶段重跑。

## 4. 必须做到

- [ ] **R1** `sdd-plan` 只在 `spec.md` 的 `Status` 为 `approved` 且第 7 节没有待决问题时启动；否则停止并在回复中指出阻塞点，不产出 `plan.md`。
  - **反例**：spec 仍是 `draft` 就开始写 plan；第 7 节有"必须你决定"的编号项仍继续。
  - **可观察证据**：`plan.md` 头部的 Spec 行写着 `（spec vN / approved）`；spec 不满足条件时该文件不存在，回复里点名阻塞项。

- [ ] **R2** 阶段 1 先读 `steering.md` 索引，再决定精读哪些文档；输出必读 / 选读 / 不读三组清单，精读项数不超过本型预算。跳过了与本次触碰面高相关但未读的文档时，在第 6 节风险表补一行，写明它让哪条决策未被验证。
  - **反例**：把 `docs/` 下所有文档读一遍；凭印象引用 `coding.md:163` 而没有打开该文件；跳过某份规范却不留痕迹。
  - **可观察证据**：第 2 节每条约束的来源都能在 `steering.md` 索引里找到；未读文档在第 6 节有对应风险行。

- [ ] **R3** 设计访谈一次只问一个问题；问题总数不超过"本型必做维度数 + 2"（`new` 8 / `extend` 7 / `fix` 6）；每个答案落到第 3.2 节决策表，且必须同时写出「放弃」的选项。
  - **反例**：一次抛出三个问题；决策表里有行写不出"放弃"（说明它不是决策）；答案只写"用 A"而没有理由。
  - **可观察证据**：第 3.2 节每行有 `选择` / `放弃` / `理由` / `来源`；`来源` 是维度 ID 或 `spec §6`；问题数在输出里报出且不超上限。

- [ ] **R4** 访谈的答案只能收窄实现，不得新增 spec 未定义的、用户可见的行为；出现这类诉求时停止访谈，要求回 `sdd-grill`。
  - **反例**：访谈中定了"点行打开详情"，而 spec 第 5 节明确不做行选中与详情；或为了绕开某条 R 而放宽其边界。
  - **可观察证据**：`plan.md` 的任务与设计里没有实现 spec 第 5 节列出的任何"不做"；出现越界诉求时 `plan.md` 停止推进并指出回哪一步。

- [ ] **R5** 第 1–2 节先写完并停下等用户确认；未确认前第 3–6 节保持为空，`Status` 为 `draft`。用户确认后 Agent 一次写完第 3–6 节，不再向人提问，`Status` 改为 `design-ok`。
  - **反例**：一次生成完整 `plan.md` 再让人审；或没人确认就继续写任务。
  - **可观察证据**：首次交付的文件只有第 1–2 节有内容，`Status` 为 `draft`；`plan_lint.py` 在 `draft` 状态下会拦下非空的第 3–6 节。

- [ ] **R6** 第 4 节每个任务带 `改动` / `验证` / `覆盖` / `依赖` 四行，验证行是可执行命令加预期结果，不能自动验证的写 `手工：` 加步骤；任务用 `- [ ]` 开头，checkbox 只表示断点位置，不作为完成证据。
  - **反例**：任务只有标题没有验证；验证写"跑一下测试看看"；任务全部勾选就宣称 spec 完成，而 `review.md` 没有命令输出。
  - **可观察证据**：`plan_lint.py` 的 L05 通过；中断后重开能从第一个未勾选任务继续；`review.md` 的结论只引用命令输出。

- [ ] **R7** `plan_lint.py` 校验九项形状（头部、结构、摘要、约束、任务、覆盖、空洞词、阻断态、spec 待决）并给出退出码；退出码 0 才允许交付 `plan.md`。
  - **反例**：lint 报 FAIL 时用文字解释"这条其实没问题"绕过；改了 lint 规则却不说明改了什么、为什么规则本身错了。
  - **可观察证据**：交付回复里有 `plan_lint.py` 的输出与退出码；FAIL 项在文档里被改掉，而不是被解释掉。

- [ ] **R8** 约束冲突按层解决：本次实现特例 > spec 第 4/6 节 > `docs/standards/*`，越具体越优先。用更具体的来源覆盖更一般的来源时，第 2 节该行标 `覆盖` 并写明覆盖了哪一条，第 3.2 节必须有来源为 `覆盖` 的决策，写清理由与可判断的失效条件。反方向（plan 推翻 spec 的 R 或第 6 节决策）不允许。
  - **反例**：spec 写了本次的例外做法，plan 却按通用规范执行并不留痕；或标了 `覆盖` 却不写覆盖了哪一条、什么时候失效，让"例外"变成永久状态。
  - **可观察证据**：第 2 节去向为 `覆盖` 的行，影响格含 `覆盖 <文档> <条款>`，L04 核对被覆盖文档存在；第 3.2 节有对应决策且「何时重评」不是 `暂不`，L08 校验。

- [ ] **R9** 既没有现成规范、也不该长期生效的约定，要么回 spec（版本 +1、`Status` 回 `draft`、`plan.md` 标 `stale`），要么在第 2 节标 `仅本次` 并说明理由；影响后续所有 spec 的则标 `先补约定` 并中断。不得既不留去向也不进 spec。
  - **反例**：plan 里定了一个只此一次的选型，下个 spec 无人知晓；或改了 spec 已批准的决策却在 plan 里实现。
  - **可观察证据**：第 2 节每行都有去向；标 `回 spec` 的条目对应的 `spec.md` 版本已递增、`plan.md` 为 `stale`；标 `先补约定` 时 `Status` 停在 `draft`。

- [ ] **R10** 技能、模板、规则与脚本不绑定具体语言、框架、构建工具或业务领域；示例用通用场景（批量作业、格式转换、命令），约束来源只认已生效的规范、spec 与 `grill.md`，不把项目自述类的说明文档当约束。
  - **反例**：模板的任务示例写成某个 Demo 工程的页面与测试命令，换个项目就失效；把项目 readme 里的一句话当作约束写进第 2 节。
  - **可观察证据**：`sdd-plan` 的全部文件里不出现具体框架名、框架专用命令或 Demo 业务名词；脚本只依赖标准库与 Markdown 结构。

## 5. 明确不做

- 不修改 `docs/standards/*` 的任何条款。理由：规范内容是项目知识变更，不是流程变更。`ui.md` 已由用户单独补齐；本 spec 只保证 plan 能读到它，并在 spec 写特例时按 `覆盖` 留痕。`coding.md` 的 FSD-12 白名单仍是 FUP-002 的剩余部分。
- 不生成 `research.md` / `design.md` / `tasks.md`。理由：三份文档与 `plan.md` 内容重叠，写两处必然漂移。
- 不做并行任务标记 `(P)`、`_Depends_` / `_Boundary_` 标签、`_Test profile` 测试档位。理由：单人串行，这些是面向多 Agent 分派的开销。
- 不引入 `spec.json` 与 `phase` / `approvals` 状态机。理由：`Status` 字段加 lint 已足够表达"能不能进下一步"。
- 不实现 `sdd-impl` / `sdd-review`，不改 `sdd-grill` 的闸门与 `sdd_lint.py`。理由：一次只换一格流程。连带修正：删掉 `sdd-grill/SKILL.md` 里三处对项目自述文档的引用，因为同一口径不能两个技能两套说法；这不涉及闸门与校验逻辑。
- 不给 `plan.md` 加成本表。理由：计划阶段的预算是过程指标，在输出里报数即可，不需要长期记录；需求阶段的成本基线仍由 `grill.md` 承载。
- 不做跨 spec 的路线图与排期。理由：不属于计划阶段。

## 6. 风险与取舍

| 决策 | 选择 | 理由 | 放弃了什么 | 何时重新评估 |
|---|---|---|---|---|
| 加载策略 | 先扫 `steering.md` 索引，再按清单精读 | 预算花在相关条款上；扫描便宜、精读贵，分开算才不会为了省钱不扫索引 | 漏读风险要靠第 6 节风险行兜底，不能机检 | 索引规模超出单屏，或反复出现漏读导致返工时 |
| 研究方式 | 访谈式，一次一问，逐层推进 | 取向（密度、结构归属、失败呈现）只能在对话里问出来；一次性长文档容易写成"既成事实" | 比一次性生成多几轮往返 | 人明确要求"直接出稿，别问"时（仍须标 `Agent 自定`） |
| 交付节奏 | 摘要先过人，确认后才写设计与任务 | 人的注意力只花在"走哪条路"；任务清单的错误代价低于路线错误 | 多一次等待；摘要被推翻时要重写 | 摘要连续两次被整段推翻时，说明维度清单没覆盖到该问题 |
| 状态机 | `draft` → `design-ok` → `approved` → `stale` | 两道人类闸门各对应一个状态，`plan_lint` 能机械判定"draft 时不许有设计与任务" | 比单一 `draft/approved` 多一个取值 | 出现需要多人并行审阅时 |
| 任务形态 | checkbox + 四行固定字段 | 断点可续；四行可机检 | 比纯表格多几行，比 Kiro 的嵌套子任务少得多 | 单任务需要多于四类信息时 |
| plan 头部字段 | 只记 `Spec` 与 `Status`，不写 commit SHA / tag / 基线 | 提交前拿不到 SHA，填进去必然过期；填了又要为这次编辑再提交，顺序上不可能自洽。个人项目不依赖版本控制，回滚改写成"撤销哪些改动、还原哪些文件" | 失去"从哪个版本开始的"这一行记录，靠 `spec` 版本号承担 | 项目改为多人和版本控制驱动时 |
| 约束去向 | 五值枚举：`既有` / `覆盖` / `回 spec` / `先补约定` / `仅本次` | 越具体越优先是常态，`覆盖` 让"这次为什么不一样"可核对；长效约定不再只活在 plan 里 | 覆盖需要多写一格被覆盖条款与失效条件 | 覆盖条目长期不重评时，说明该规范该改了 |

## 7. 审阅问题

**必须你决定**：本次无需你决定的事项。

**建议确认**：

- 状态机取四个值（`draft` / `design-ok` / `approved` / `stale`），其中 `design-ok` 专指"摘要已确认、正在写设计与任务"。
- 冲突处理从"一律中断补约定"改为按层覆盖：spec 的特例优先于通用规范，`覆盖` 必须写清覆盖条款与失效条件；只有 plan 想推翻 spec 的 R 或第 6 节决策时才回 `sdd-grill`。
- `p00-001` 与 `docs/standards/ui.md` 的冲突作为这套优先级的第一个验证用例：前者要求内置组件，后者要求 shadcn_flutter，按 `覆盖` 处理。
- 本 spec 的 `Status` 暂为 `draft`：技能文件已按上述设计落地，但你尚未对这份 spec 说"可以进入下一步"。
