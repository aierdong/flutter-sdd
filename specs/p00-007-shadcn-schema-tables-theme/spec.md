# 单 schema 表列表页改用 shadcn_flutter 并跟随系统主题

- 上游：`p00-001-schema-tables-page`
- 附带交付：`—`

- 版本：`v1`

> 用户已明确确认进入计划；`approved` 只标记需求已获批准，不代表计划或实现已批准。

## 1. 背景与问题

**现状**：上游需求 `p00-001-schema-tables-page` 已交付并通过审查。页面使用 `MaterialApp`、Material 按钮、进度指示和表头交互；六列表格由 Flutter 基础布局自行拼装。应用已有深浅两套颜色，但页面与主题根尚未采用 `shadcn_flutter`。上游第 6 节曾选择仅用 Flutter 内置组件；第 5 节排除页面内的深浅主题切换控件。

**问题**：现有界面与已生效的 UI-01「唯一组件库是 shadcn_flutter」不一致。用户希望整张表格及现有控件改用该库，并让应用在运行中自动跟随系统的浅色、深色模式，不增加手动设置。

**为什么现在做**：这是对已交付页面的单次界面迁移，不增加数据库或连接管理能力；迁移后再继续沿用该页面展示演示数据和四种页面状态。

## 2. 目标

- 用户启动应用时看到基于 `shadcn_flutter` 的现有单 schema 页面，包括表格、按钮及加载指示。
- 系统在应用运行中切换浅色或深色模式时，页面自动更新，当前排序与浏览位置不丢失。
- 用户仍可查看原有的六列数据及有数据、空、加载、失败四态，不需要手动切换主题。

**成功后，你能看到/做到**：在 macOS 或 Windows 上打开页面并切换系统外观，不重启也能看到整页颜色随之变化；表格继续显示原有内容和排序，组件呈现为 shadcn 风格。

## 3. 用户场景

### 场景 A：浏览表格并切换系统外观

1. 用户启动应用，看到原来的连接名、数据库名、schema、六列数据及禁用的「新建连接」。
2. 用户点击可排序列并滚动表格，继续按原有字段与比较规则浏览数据。
3. 用户在操作系统中切换浅色或深色；页面不重启、不出现主题开关，直接切换对应外观。
4. 用户仍看到同一份数据、排序方向以及切换前的横向和纵向浏览位置。

### 场景 B：空、加载、失败和长列表

1. 页面收到空数据时，仍显示六列表头及原有空态文案；加载中与失败时仍只替换表格区。
2. 失败对象含异常细节时，页面只显示消息和错误码，不显示异常原文或敏感连接信息。
3. 表较多或窗口变窄时，用户仍能滚动到最后一张表并查看六列；表格保留 `shadcn_flutter` 自身的默认布局与能力，不为了复制旧实现而人为关闭其视口裁剪等机制。

## 4. 必须做到

- **R1** 应用根、现有按钮和加载指示迁移到 `shadcn_flutter`；页面及应用根不再使用 Material/Cupertino 组件，必要的基础布局和文本仍可使用 Flutter `widgets.dart`。本条取代上游第 6 节「只用 Flutter 内置组件」的技术取舍，不改变上游 R1 的首屏入口。
  - **反例**：应用仍由 `MaterialApp` 承载；禁用按钮或进度指示继续使用 Material 组件；找不到库依赖；因为迁移困难而恢复 Material 控件。
  - **可观察证据**：应用根和现有控件来自 `shadcn_flutter`，应用正常启动；按钮仍禁用，加载态仍显示进度指示。

- **R2** 有数据和空数据时，六列表格使用 `shadcn_flutter` 的表格组件，并保留原有字段、数量、表头排序规则及空态提示；组件自身默认的行悬停和视口裁剪等能力不为模仿旧表格而特意启用或关闭。数据行不增加点击选中、导航或详情功能。本条**取代** `p00-001 R9` 中的「全部行都构建、不启用虚拟滚动」及 `p00-001 R10` 中的「悬停不产生高亮」；其余可观察行为继续以 R3、R4、R7、R8 以及本条为准。
  - **反例**：仍用原来的 `Row` 拼表格；改成五列或失去排序；空态不再显示表头；主动配置组件关闭默认悬停效果或视口裁剪；点击数据行打开详情。
  - **可观察证据**：六列表头及行来自 shadcn 表格，五列仍可排序且默认表名升序；空态保留表头和提示；500 行仍可纵向滚动到最后一行，横向滚动后仍能读取完整的长表名和描述，800×600 下不发生布局溢出。组件默认视觉允许与旧表格不同，旧版「全部构建」不再作为验收条件。
  - **取代**：`p00-001 R9`、`p00-001 R10` 的上述局部限制。

- **R3** 应用首次打开时按照系统模式显示浅色或深色主题；应用运行中系统模式发生变化时，整个现有页面自动更新为对应主题，不需要重启，也不提供手动覆盖设置。此项明确扩展上游第 5 节的主题边界：原先不做的是页面内手动切换，本次只做系统跟随。
  - **反例**：系统切为深色后仍显示浅色背景；需要重启才更新；表格变深而页头或错误文案仍保持浅色；页面出现主题开关。
  - **可观察证据**：分别在系统浅色、深色下启动，并在应用持续运行时双向切换系统模式，页面的页头、表格、按钮、空态、加载态及错误文字均随主题更新。

- **R4** 用户在有数据的页面已经排序并滚动时，系统主题变化只改变外观，不重置表数据、当前排序列、排序方向、横向或纵向滚动位置；不因重建页面而重复读取数据库。
  - **反例**：切为深色后排序回到表名升序；滚动回到起点；行数或数据内容变化；因主题变化发出网络或数据库请求。
  - **可观察证据**：切换前后可排序列、方向标记、可见行及横纵滚动位置保持，只有浅深色视觉改变；无数据库环境也能完成切换。

- **R5** 组件迁移后，原有页头内容、禁用按钮、六列数据、数量、五列排序及有数据、空、加载、失败四态的文案与互斥关系仍可用；失败文案保留消息与错误码，不展示原因对象或密码。除 R2 明确取代的行悬停与渲染机制外，原页面的只读演示数据、启动参数和外部传入数据的边界不变。
  - **反例**：空态显示「0 张表」或丢失表头；加载时保留旧行；失败时暴露异常原文；禁用按钮可点击；切换主题触发数据库连接；描述空值不再显示 `—`。
  - **可观察证据**：默认演示仍为六张表；`data`、`empty`、`loading`、`error` 四种演示状态各自显示原有页头及对应表格区，错误码仍与消息同段显示；无数据库也能运行。

## 5. 明确不做

- 不做页面内主题开关、主题偏好持久化或手动覆盖系统模式。理由：用户要求仅随系统外观自动变化。
- 不做新建连接、搜索、刷新、重试、确认弹窗、表详情或真实 PostgreSQL 查询。理由：本次是既有页面的组件迁移，不扩大业务能力。
- 不为了还原旧表格而特意启用或关闭 shadcn 表格原生能力，也不要求所有 500 行同时构建。理由：用户选择保留组件默认形态；这明确取代上游 R9 的对应限制。
- 不要求数据行维持旧版「悬停绝不高亮」的效果；也不新增点击后持久选中、导航或详情。理由：用户选择原生悬停外观，但没有要求新的行操作；这明确取代上游 R10 的悬停限制。
- 不把系统主题变化当成数据状态变化，不清空当前数据、排序或滚动位置。理由：保留用户正在浏览的上下文。
- 不改变上游 R2–R8、R11 的数据字段、四态文案、排序规则、错误码格式或 UI-only 边界。理由：这些已通过验收，本次只替换呈现层。

## 6. 风险与取舍

#### 决策 1：增量交付
- 决策：修改原需求还是追加一次交付。
- 选择：新建增量需求并引用已验收的 `p00-001-schema-tables-page`；原文不回改。
- 理由：本次可以单独验收组件迁移和主题跟随。
- 放弃了什么：让原需求的批准失效并重新审阅全部旧条目。
- 何时重新评估：需重新定义原页面业务能力时。

#### 决策 2：组件与表格的默认能力
- 决策：迁移范围与新旧组件能力的优先级。
- 选择：应用根、现有控件及整张六列表格使用 `shadcn_flutter`；基础 Flutter widgets 可用于布局和文本。保持 shadcn 表格原生提供的视觉、悬停和视口行为，不为复制旧实现主动开关其能力；但六列、排序、四态及数据可达性必须保留。
- 理由：用户要的是组件平替，而不是在新组件中重造旧组件；旧版「无悬停高亮」「全部构建」与此取舍冲突，已在 R2 逐项取代。
- 放弃了什么：旧表格逐像素外观、禁止悬停高亮和全部行同步构建。
- 何时重新评估：默认能力导致六列、排序或数据可达性无法满足时，先请用户决定是否改变需求，不回退 Material。

#### 决策 3：既有界面规范的适用范围
- 决策：shadcn 原生外观与现行密度、色彩及装饰规定不一致时用什么验收。
- 选择：仅对本次迁移的 shadcn 组件，原生尺寸、间距、颜色、悬停与装饰优先；这覆盖 `docs/standards/ui.md` 的 UI-02、UI-03、UI-04、UI-05、UI-07 中与组件默认形态直接冲突的固定数值或视觉写法。UI-01 的 shadcn 应用根、UI-08 的可读性与对比度下限仍适用。现有页头与六列表格的区位、800×600 无溢出及主题下的文字可读性仍须保证。
- 理由：用户最新决定不人为配置组件去复刻旧尺寸与色彩；若强制固定尺寸，会使「原生形态」失去意义。
- 放弃了什么：以旧的 28 高数据行、4 档间距、旧主题色 token 或绝无组件阴影等规则逐像素验收新组件。
- 何时重新评估：需要把这次外观推广为后续所有页面的长期标准时，须另行修订规范；本条不修改长期规范。

#### 决策 4：系统主题与运行状态
- 决策：主题变化由谁触发、用户原有浏览状态是否保留。
- 选择：由操作系统决定浅色或深色；应用运行中双向跟随，不添加手动开关；数据、排序与双向滚动位置保持。
- 理由：用户切换系统模式不应中断当前的表格浏览。
- 放弃了什么：仅启动时读取主题或用户手动覆盖。
- 何时重新评估：用户明确提出应用内独立主题偏好时。
