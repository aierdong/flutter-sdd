# sdd-roadmap

## 它解决什么问题

一个阶段的事大到一次交付不完时，直接写 spec 会出现两种失败：需求条目越写越多，最后写成一个谁也验不完的巨型 spec；或者只做了前半段，用户拿到手发现整条流程走不通。

本技能先回答三个问题，再让后面的流程开工：这个阶段该拆成哪几块、每块做完用户能拿到什么、全部做完算不算完。

本文使用以下术语：

- **阶段**：一次完整交付，用一个两位阶段号 `pNN` 标识。一个阶段只装用户要完成的一件完整的事。
- **路线图**：本技能产出的文档 `specs/pNN-<slug>-roadmap.md`，说明这个阶段拆成哪些切片、按什么顺序做、全部做完怎样算完成。
- **切片**：一次可以独立交付和验收的小变更，编号 `pNN-NNN`，对应一份 `spec.md`。编号表示推进的先后。
- **阶段历史**：同一 `pNN` 下已经规划过、已经交付的切片，以及已生效的跨切片约定。它记在路线图里，不需要靠翻遍每份 spec 还原。
- **整体验收**：全部切片交付后，按整体完成条件走一遍连续路径。它与切片验收是两件事。
- **闸门**：进入下一阶段前必须满足的条件。
- **lint**：检查文档格式和引用的脚本；它不能代替用户判断拆分是否合理。

## 在流程里的位置

```text
（可选）sdd-roadmap  →  specs/pNN-<slug>-roadmap.md   用户批准后才可以按切片开工
     ↓
sdd-requirement  →  spec.md + grill.md        （按切片逐个进行）
     ↓
sdd-plan  →  plan.md
     ↓
sdd-impl  →  代码与提交
     ↓
sdd-review  →  review.md   该切片交付，回到路线图补记交付证据
     ↓
（路线内切片全部交付后）整体验收  →  第 7 节整体验收记录
```

路线图是可选的。一个修正型需求，或者一个装得下的完整需求，直接从 `sdd-requirement` 开始，不需要路线图。只有需要拆成多次可独立验收的交付时才需要。

## 边界

本技能负责：判断要不要路线图、查阶段历史、写整体目标与完成条件、切分切片、排顺序、定跨切片约定、产出并校验路线图、安排并记录整体验收。

本技能不做以下工作：

- 不写任何切片的 `R` 条目、第 7 节问题或 `plan.md`。切片的需求由 `sdd-requirement` 确定。
- 不排期、不估时、不计算优先级得分。切片之间不比较投入产出，只比较先后。
- 不决定技术选型、目录结构、接口形态。这些留给各切片的 `plan.md`。
- 不记录切片进度状态。推进位置按 `specs/` 下的目录事实推算，见「推进与修订」。
- 不重跑切片的需求条目，也不汇总切片验收结论当作整体结论。
- 不替用户编造目标。用户说不清要做什么时，本技能停下，不填一个看起来合理的目标。

一个阶段只装一件事。用户的需求实际包含两件互不依赖的事时，Agent 先问是否分成两个 `pNN`，不把它们塞进同一份路线图。

技能要能移植到其他项目。示例统一使用商品列表、导入文件这类通用场景，不写死本项目的编号、业务或历史决定。

## 写作要求

本技能、模板和生成的路线图，全文都必须让人读懂。

- 写清谁做什么。一句话说一件事；条件多就拆开，不写无主语长句。
- Agent 在路线图首次使用术语时写出完整名称并解释用途。后文可以用简称；相隔较远时可以再写一次全称。
- 正文用中文，路径、标识符和命令保持原样。
- 路线图使用固定字段行和记录块，不使用表格。字段名按模板固定，同一片内不重复。
- 只写结论和理由，不写调查过程和修改经过。影响切分的取舍写进第 6 节决策记录。
- 切片的“做完后用户能”只写一句话可观察行为。写到这里为止，细节属于该切片的 spec。
- 不把可以从别处推导出来的东西写进路线图。进度由目录推导，交付与否由 `review.md` 证明。

## 输入

- 用户口述的阶段目标，可以是口语、不完整。
- `project.md`：当前阶段号、项目目标与约束。
- `steering.md`：知识索引，Agent 按索引读取相关规范。
- 同一 `pNN` 下已有的路线图：阶段历史、已交付切片、已生效的跨切片约定。
- 仓库根目录 `FOLLOW.UPS.md`：用户已承诺未来处理的延期事项。

## 阶段 0：判断要不要路线图

Agent 先判断，再动手。判断不成立时不要建空路线图，建了比不建更糟。

| 情况 | 做法 |
|---|---|
| 用户明确要求把这件事分几步做 | 建路线图 |
| 需求边界清楚，能写成 1–12 条 R，且不依赖尚不存在的能力 | 不建，直接 `sdd-requirement` |
| 需求明显超出一个 spec，但用户没要求拆 | Agent 问一次，由用户决定 |
| 用户只是问“这事该怎么拆” | 只做口头讨论，不写文件 |

用户没有要求、Agent 又判断不清时，Agent 不擅自建路线图，也不擅自判定“不需要”。Agent 问一个问题，给出“直接做”和“先拆”两个具体后果。

## 阶段 1：查阶段历史

调查的重点是这个阶段已经走到哪里，不是逐个读 spec。Agent 只查三类事实：已经规划了什么、已经交付了什么、已经定下哪些必须一致的行为。

按以下顺序读：

1. 同一 `pNN` 下已有的路线图。它记着已规划的切片、交付证据、跨切片约定和整体不做清单，是查历史的主要依据。有路线图时，Agent 不再逐份打开 spec 还原历史。
2. 其他 `pNN` 的路线图只看头部和切片名称，用来判断这件事是否已被别处覆盖。
3. `project.md`、`steering.md` 和 `FOLLOW.UPS.md`，确认约束与已承诺的延期事项。
4. 只在用户口述点到具体能力、页面或 spec 编号时，读对应 `spec.md` 的相关节。

还没有路线图时，Agent 只读 `specs/` 目录清单、各 spec 的头字段与第 2 节目标，不逐份精读。读不出历史的地方，Agent 如实说明，不猜。

工具调用预算 10 次。预算用尽时，Agent 列出未读内容和因此未经核实的判断，不假装已经查清。

Agent 只查事实，不在这一阶段提切片方案。影响切分的取舍（例如“为什么不把这两件事放一片”）记进第 6 节决策记录。

## 阶段 2：整体目标与整体完成条件

Agent 先写这两项，再切分。切分脱离目标时，回头改这里。

### 整体目标

写成一句话，而且必须是一个过程：用户从哪里开始、经过什么、最后得到什么。

- 不算目标：“支持商品管理。”这是功能名，不是过程。
- 算目标：“用户能创建商品列表页，完成一次增删改查并看到列表保持最新。”

**整体不做**逐条写容易被误认为包含的相邻能力，每条带理由。不要罗列无关功能。

### 整体完成条件

写成一条可观察的端到端行为，并写清怎么验证。第 2 节固定四项：

```text
- 完成条件：<用户能连续做完的一件完整的事>
- 操作路径：<起点 → 中间步骤 → 终态>
- 验证方式：用户手工走一遍 | Agent 运行端到端命令 | 用户走主路径，Agent 准备数据
- 验证者：用户 | Agent
```

- **完成条件**写结果，不写实现。它回答“全部做完后，用户能做什么”。
- **操作路径**写 3–6 步实际操作，用来支撑完成条件。写不出路径，说明完成条件还太虚。
- **验证方式**从三类里选一个，判断依据是结果怎么被观察到：人能看见的界面行为交给用户；已有命令能全程跑通，由 Agent 运行并留下输出。
- **验证者**写 `用户` 或 `Agent`，默认 `用户`，因为整体完成条件写的是用户视角的经历。

这里只写验证方式的类型，不写命令。命令和入口属于最后一个切片的 `plan`，现在还不存在，路线图不提前编。

三条硬规则，防止把整体验收做成切片的重复劳动：

1. 整体验收不重跑任何切片的 `R`，也不重新执行它们的验证命令。
2. 整体验收不把各切片 `review` 的结论拼成整体结论。
3. “所有切片 spec 都通过”不能代替整体判断。它只是进入整体验收的前提。

用户说不清目标时，Agent 停下，列出已经掌握的输入，说明现在缺的是目标，由用户补充。Agent 不替用户编一个目标继续往下做。

## 阶段 3：切出交付切片

**切法**：按用户能完成的一件事切，不按技术层切。

按“数据层、接口层、界面层”切出来的片，单独交给用户什么也用不了，不满足独立验收。按“用户能新建一条记录”“用户能改一条记录”切出来的片，每一片都能单独用。

这一阶段只分配名称和 slug，编号留到阶段 4。每片写四个字段：

```text
#### 切片：<名称>
- slug：<英文短横线名称>
- 解决什么问题：<一句话，用户遇到的困难>
- 做完后用户能：<一句话可观察行为>
- 前置：无 | <前一片的 slug>（提供：<交付给用户的能力>）
```

切片记录不写状态。这一片做到哪里，看 `specs/` 下有没有对应目录和通过的 `review.md`，见「推进与修订」。

**独立性检查**：逐片问一次“假设其他切片都不存在，这一片做完后，用户能不能用它完成一件完整的事”。不能时，Agent 合并切片或换一种切法，并把理由记进决策记录。

不允许出现“内部准备好、用户看不到”的切片。纯使能工作（例如建立只读连接）也必须能独立观察，例如连接成功后能列出库名。写不出可观察结果，说明这片切得太细或切错了位置。

Agent 把候选清单交给用户，并明确说明这是候选。用户逐片确认或改写；用户改过的表述以用户原话为准。

切片数量超过 8 个时，Agent 提示考虑拆成两个阶段，由用户决定。这不是失败条件，Agent 不擅自合并。

## 阶段 4：依赖与顺序，分配编号

Agent 先和用户确定推进顺序，再一次分配编号。编号就是顺序，不把两者分开表达。

1. Agent 按依赖关系排出一条推进顺序。没有依赖关系的切片也要选定先后，不为它们保留“可换序”的模糊状态。
2. Agent 按顺序给每片分配 `001`、`002`，连续且不跳号。批准前编号可以自由重排：此时还没有任何 spec 目录存在，重排没有成本。
3. Agent 回填每片的 `- 编号：pNN-NNN`，并把 `前置` 里的 slug 换成编号。阶段 6 之前不得残留 slug。

**前置**指这一片需要前一片已经交付给用户的能力，不是代码文件的写入顺序。只是改动同一批文件不算依赖，不写进路线图。写不出“提供什么”，说明这条依赖是假的，删掉。

第 4 节只写两件事：

```text
- 推进顺序：001 → 002 → 003
- 顺序理由：<一句话，说明为什么这样排>
```

逐片的前置关系写在各片记录里，第 4 节不重复罗列。

Agent 检查三件事：编号连续且与顺序行一致；每个前置编号在本路线图内存在；依赖不成环。

发现依赖环时，Agent 立即停下，列出环上的切片，给用户两个具体选项：合并其中两片，或调整某一片的范围让依赖消失。Agent 不静默重排顺序，也不擅自扩大或缩小某片的范围。

## 阶段 5：跨切片约定

多个切片共用同一套行为时，必须写下来，否则各切片的 `plan` 会各定一套，回头改起来比一开始定下来贵。

Agent 按影响范围分三类处理：

| 影响范围 | 写在哪 |
|---|---|
| 本阶段内多个切片必须一致 | 路线图第 5 节 |
| 只影响单个切片 | 不写，留给该切片的 `plan` 决定 |
| 影响后续所有阶段 | 停下，先补 `docs/standards/` 并登记到 `steering.md`，再回来继续（见 `AGENTS.md` 第 5 条） |

每条约定写三项：要求、覆盖哪些切片、显式留给各切片 `plan` 决定的部分。

只写必须一致**行为**，不写实现方式。“新增和修改共用同一个校验入口”是可观察约定；“用某个类实现”不是，属于 `plan`。

## 阶段 6：组装、闸门与校验

Agent 按 [templates/roadmap.md](templates/roadmap.md) 写文件，路径为 `specs/pNN-<slug>-roadmap.md`。`pNN` 用当前阶段号，`slug` 用英文短横线名称。

闸门如下，全部通过才能交给用户批准。

| 闸门 | 判据 | 谁来判 | 不通过时怎么处理 |
|---|---|---|---|
| 头字段 | 路线图号、名称、Status、版本齐全；编号与文件名一致 | `sdd_lint.py` | Agent 补齐或改名 |
| 结构 | 第 1–7 节标题齐全 | `sdd_lint.py` | Agent 补齐 |
| 切片字段 | 每片字段齐全，编号连续且与顺序行一致 | `sdd_lint.py` | Agent 补齐或重排编号 |
| 前置引用 | 前置编号存在，且不成环 | `sdd_lint.py` | Agent 请用户决定怎么拆环 |
| 交付证据 | 写了交付证据的切片，其 `specs/pNN-NNN-*` 目录与 `review.md` 存在 | `sdd_lint.py` | Agent 补证据或删该行 |
| 整体不做 | 每条都带理由 | `sdd_lint.py` | Agent 补理由或删条 |
| 完成条件 | 完成条件、操作路径、验证方式、验证者四项非空且取值合法 | `sdd_lint.py` | Agent 重写 |
| 路线外增补 | 有登记块时字段齐全，附属于已有编号 | `sdd_lint.py` | Agent 补齐 |
| 目标成过程 | 整体目标写的是用户的一段经历，不是功能名 | 人 | Agent 重写，必要时回阶段 2 |
| 切片独立 | 每片不依赖后面的切片也能单独验收 | 人 | Agent 合并或重切 |
| 完成条件不循环 | 没有用“各切片都通过”代替整体判断 | 人 | Agent 重写 |
| 验证不重复 | 验证方式不是重跑切片条目或汇总切片结论 | 人 | Agent 重写 |

```bash
python3 .agents/skills/sdd-roadmap/tools/sdd_lint.py specs/pNN-<slug>-roadmap.md
```

退出码 `0` 表示全部通过，`1` 表示有失败，`2` 表示用法错误或文件缺失。

lint 有失败时，Agent 修正文档，不通过解释绕过。怀疑校验规则有误时，Agent 暂停交付，向用户说明依据和拟议变更；用户明确确认后才改规则。

## 阶段 7：请用户批准

Agent 用 `Status：draft` 交付，并说明批准范围：

- 批准的是切片划分、推进顺序、跨切片约定和整体完成条件。
- 不批准任何切片的需求内容。每个切片的需求仍由该切片的 `sdd-requirement` 确定并单独批准。
- 批准后调整切分或顺序要重新批准，走「推进与修订」。

用户明确同意后，Agent 才把 `Status` 改为 `approved`。用户只说“看着还行”而没说批准时，Agent 简短确认一次。未批准时，Agent 不得基于这份路线图创建任何切片 spec。

## 整体验收

路线内切片全部交付后安排一次，只做一次。它验证的是切片之间的衔接，不是切片本身。

执行顺序：

1. Agent 读第 2 节的完成条件、操作路径、验证方式和验证者，按它们安排，不改写。
2. 验证方式为 `用户手工走一遍` 时，Agent 准备好操作路径需要的数据和入口，把步骤交给用户，由用户判断结果。Agent 不替用户点“通过”。
3. 验证方式为 `Agent 运行端到端命令` 时，Agent 运行并记录命令与关键输出。命令失败不等于整体不成立，Agent 先判断失败原因是环境还是衔接。
4. Agent 把结果追加到第 7 节「整体验收记录」。
5. 结果为未通过时，Agent 指出断在哪一步，交用户决定：增补一个切片、重开某个切片，还是推翻完成条件重新走修订。

发现断点位于某个已交付切片内部时，Agent 记录断点并交用户决定，不在整体验收里顺手修代码。

整体验收不重跑任何切片的 `R`，也不重新执行它们的验证命令。它是整个阶段唯一一次跨切片验证，也是唯一一次。

## 推进与修订

**推进位置**：路线图不记录切片状态。Agent 每次汇报走到哪一步时，按 `specs/` 下的事实推算，不改文件：

- 没有 `specs/pNN-NNN-*` 目录 → 未开始。
- 有目录，但没有通过的 `review.md` → 进行中。
- 有通过的 `review.md` → 已交付。

**切片交付**：该切片的 `sdd-review` 通过后算交付。下次进入这个阶段时，Agent 在该片追加一行 `- 交付证据：<review.md 位置>`。这一行是证据，不是状态；证据缺失时，读者应当认为这片没有交付。

**路线外增补**：允许在 `pNN` 下增补路线图没有规划过的 spec，例如“调整商品列表的页面布局并增加骨架屏”“修正数据加载过程中的提示逻辑”。

- 增补的 spec 沿用它所附着的切片编号，因此同一编号可能出现两份 spec 目录，slug 不同。这是允许的：编号表示推进位置，不承担唯一标识。
- 没有增补时，路线图不写任何占位行。有增补且用户要求登记时，Agent 在第 3 节追加一条增补记录块。
- 增补的 spec 不得与现有切片冲突。冲突指改变某片的“做完后用户能”、触碰第 5 节约定，或需要整体目标之外的新能力。冲突时必须走修订流程改路线图，不在需求阶段绕过。
- 增补的 spec 不改变整体完成条件，也不进入整体验收路径。整体验收记录只列举它们，不为它们安排验证。

**要重新批准的变化**：改整体目标、整体完成条件或操作路径、整体不做清单、切片的“解决什么问题”或“做完后用户能”、增删切片、调整顺序、增删跨切片约定、登记有冲突的增补。

**不用重新批准的变化**：追加交付证据、追加第 6 节决策记录、追加第 7 节整体验收记录、追加不冲突的增补登记、修正错别字与排版。

**降级动作**：Agent 先把 `Status` 改为 `draft`，再改正文，然后重新请用户批准。降级时不清空正文——路线图没有“前半段已确认”的分段，清空只会丢掉还要复用的切分。

**调整顺序**：批准后只重编号尚未创建 spec 目录的切片。已创建目录的切片不改编号，也不改它的 `spec.md` 内容，Agent 在第 4 节写明它实际的推进位置。顺序调整要重新批准。

**切片定义有误时**：Agent 在 `sdd-requirement` 停下，不在需求阶段改路线图。用户新开一次会话运行本技能修订路线图并重新批准，再用新会话重读修订后的切片定义继续需求访谈。

**已交付切片重开**：用户确认后，Agent 删掉该片的交付证据行，并在第 6 节追加一条重开决策，写明原因。其余内容不动。重开需要改切片定义时，按上面的降级规则处理。

## 输出说明

lint 通过后，Agent 给用户四行总结：

1. **结论**：一句话说明全部做完后能完成什么，再写切片数量和推进顺序。
2. **闸门**：退出码、通过项数、依赖是否成环。
3. **成本**：工具调用数 / 预算。
4. **下一步**：请用户阅读路线图并决定是否批准；批准后说明从哪个切片开始、启动 `sdd-requirement` 时提供该切片编号。

lint 有失败时，Agent 先修正，不发这份总结。

## 异常处理

- **用户说不清目标**：Agent 停下，列出已知输入，说明缺的是目标。不编造目标，也不把“先随便写一个”当作可行做法。
- **用户要求跳过调查**：Agent 照实标注哪些结论未经核实、影响哪些切片划分，用 `draft` 交付。
- **出现依赖环**：Agent 停下，列出环，请用户在合并切片和调整范围之间选择。
- **切片越切越多**：Agent 提示可能存在两件事，请用户决定是否拆成两个 `pNN`。不擅自合并。
- **某一片其实装不下**：该片需要独立的目标、独立的交付节奏时，Agent 建议把它提升为新的阶段，并说明理由。
- **用户坚持把两件事放一份路线图**：Agent 说明后果，由用户决定。合并时整体完成条件必须能覆盖两件事，否则不成立。
- **整体验收在切片之间断裂**：Agent 记录断点，不判定“整体完成”，也不把责任推给某个切片了事，交用户决定补片还是重开。
- **lint 与内容判断冲突**：Agent 对照现行规则检查文档；怀疑校验有误时暂停交付，不绕过失败，也不擅自改脚本。

## 下游契约（给 sdd-requirement）

路线图批准后，为每个切片提供以下材料：

1. **切片定义**：编号与“解决什么问题”。该切片的 `spec.md` 必须落在定义范围内，不得扩大。超出时停下，回本技能修订路线图。
2. **前置与顺序**：该切片的前置切片。前置未交付时，Agent 先问用户是否仍要开工，不默认放行。
3. **跨切片约定**：该切片的 `plan` 必须遵守，不得自行偏离。`plan` 认为约定不成立时，回本技能修改，不在计划里绕开。
4. **增补判定**：请求不在路线图规划内时，Agent 先比对现有切片。不冲突才按增补开工，编号沿用附着的切片；冲突必须先回本技能修订。
5. **整体完成条件**：路线内最后一个切片交付后，由路线图指定的验证者判一次。增补的 spec 不进入这次验收。任何一个切片的 `review` 通过都不代表整体完成。
6. **批准状态**：`Status` 为 `approved` 才能作为开工依据。`draft` 时 `sdd-requirement` 拒绝执行。
