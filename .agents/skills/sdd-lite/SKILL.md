# sdd-lite

## 职责与边界

本技能为简单变更保留需求、授权、验证和交付结果，不要求完整的四阶段流程。

- **SDD（规格驱动开发）**：先明确这次交付必须满足什么，再据此修改和核对成果。
- **轻量 spec**：本次交付的短记录，文件名为 `spec.md`。它同时保存要求、做法、验证安排和实际结果。
- **主 Agent**：负责调查、编写记录、修改、验证和交付的当前 Agent。
- **审查 Agent**：未参与本次编写、实现、验证或失败调查的新子 Agent，只读核对成果并返回结论。
- **R1、R2**：定位必须满足的需求条目；**V1、V2**：定位开工前约定的验证项目。

流程只有两段：

```text
定向调查 → 形成短记录 → 用户一次批准开工
                              ↓
                修改 → 约定验证 → 独立审查 → 记录结果
```

Agent 不另建 `grill.md`、`plan.md` 或 `review.md`，不做完整维度覆盖、详细任务拆分或实现前的多轮独立计划核查。Agent 不调用四阶段技能来模拟轻量流程。

项目入口必须允许轻量交付。入口仍要求完整计划或指定其他完成条件时，Agent 先报告冲突，请用户决定调整入口或明确允许本次例外；加载本技能本身不构成覆盖授权。

## 适用条件

Agent 按不确定性和实际影响判断，不按文件数、代码行数或“修 Bug”“补文档”等名称判断。

以下条件必须同时满足：

- 本次只解决一个问题，用户期望和完成条件能够简短说清。
- Agent 可以沿用既有技术路线和规范，不需要复杂的任务协调。
- Agent 能界定改动及直接影响，并说明哪些已有行为必须保持不变。
- 本次不涉及重要架构选择、新的重要依赖、数据迁移、权限模型或对外兼容性变化。
- 本次不需要改变路线图的切分、跨切片约定，或制定影响后续交付的长期规范。

Agent 可以先只读诊断，再判断是否满足条件。Bug 根因暂时未知，不直接排除轻量流程；但不能在关键事实未查清时编造修复做法并请求开工。

不满足条件时，Agent 说明具体原因和已查清内容，停止修改，由用户决定缩小范围、补充调查或升级完整流程。

## 开始前读取与记录归属

1. Agent 读取 `AGENTS.md`、`steering.md` 和本文件。Agent 按索引只加载直接相关的规范，不为凑调查量遍历仓库。
2. 用户提供了编号时，Agent 读取对应记录。涉及已有能力时，Agent 查找相关需求、决定、实现与测试；没有已有 spec 时如实写明，不要求用户追补全部历史。
3. 本阶段有路线图时，Agent 读取相关切片和跨切片约定。指定切片必须已获批准，本次不得超出其边界。路线外增补不得与既有切片冲突。
4. `FOLLOW.UPS.md` 存在时，Agent 检查其中与本次相关或已触发的事项。Agent 只报告相关项，由用户决定并入、另做、延期或取消，不自动扩大本次范围；文件不存在且本次没有延期承诺时，不为轻量交付创建空清单。
5. Agent 使用项目现有的 `specs/pNN-NNN-<slug>/` 编号体系。当前阶段取自项目信息；新交付使用该阶段下一个三位序号。路线外增补沿用所附着的切片编号、使用不同 slug。阶段或编号无法确定时，Agent 询问用户，不猜号。
6. 已验收能力的后续变更默认新增轻量记录，引用上游文件及相关需求，说明扩展、修正或取代了什么，不覆盖已验收历史。只有用户明确要求且原记录仍未完成时，才修订原轻量记录。原记录属于完整流程时，Agent 不擅自改成轻量格式。
7. Agent 修改成果前记录已有工作区改动，区分本次工作与用户或其他任务的改动，不覆盖无关内容。

## 第一段：查清并确认

### 定向调查

Agent 每次调查都应服务于一个具体判断：当前行为、正确行为、直接影响、可沿用的做法或验证入口。该判断已经有可靠答案时，Agent 不换一种方式重复调查。

- Agent 自己核实可查事实，区分用户报告、已验证事实和根因假设。已有可靠事实与决定直接复用。
- Agent 沿本次入口及直接调用、依赖和测试追查，不进行全仓库体检，不顺手调查相邻功能。
- 关键事实无法查清时，Agent 说明缺什么以及影响哪个判断，不把事实问题交给用户做产品选择。
- 只读诊断不等于任意命令授权。需要试改、启动程序、访问外部服务或执行有副作用的复现时，Agent 先说明动作和影响并取得对应授权，不处理未获准的真实数据。

本技能不设必须用满的工具或问题额度。调查不再收敛、影响范围持续扩大时，Agent 应报告原因，不以“再查一点”为由无限延长。

### 只问实质问题

Agent 在提问前先判断：现有要求、已有决定或当前场景的通行做法能否给出答案。能够确定的直接采用；用户需要了解的自主选择合并写入做法，不维护独立的自主决定清单。

只有答案确实改变用户可见结果、范围、验收，或用户确实可能有偏好时才提问。Agent 一次只问一个决定，写清具体选项及后果；没有分歧时可以零提问。

Agent 不为内部命名、局部代码组织或已有惯例重新访谈。出现多个相互牵连的实质分歧时，Agent 重新判断是否仍适合轻量流程。

### 形成短记录与批准

Agent 按 [短记录模板](templates/spec.md) 编写一份 `spec.md`。用户尚未授权落盘时，Agent 先在对话中给出内容，获准后再写文件。

- 第 1 节记录现状和必要的事实依据，不写调查流水账。
- 第 2 节列出稳定编号的 R。每条写清条件、行为和结果，足以判断是否兑现；文档变更写清需表达或纠正的内容。Agent 不为凑条目拆句，也不把多件事塞进一条。
- 第 3 节记录上游关系、必须保持不变的行为，以及容易被误认为包含的明确不做事项。不做事项说明理由。
- 第 4 节简述做法、已知影响范围、适用规范、验证安排和撤回办法，不写详细设计、文件白名单或任务依赖图。没有实质选择时，不编造备选方案。
- 每个 V 写清对应 R、执行者、命令或操作及预期。执行者使用“主 Agent”或“用户”；审查不是验证执行者。能通过内容核对完成的文档修改，不机械安排构建和测试。
- 第 5 节只放实际结果。开工前写“尚未执行”，审查写“待审查”，不得提前填写通过。

主 Agent 自检要求、边界、做法与验证是否一致，确认没有待用户决定的问题，再请用户批准。确认前，Agent 说明各项验证检查什么、怎样算通过，并提醒用户一并审阅做法中的自主选择。

用户明确允许按当前记录实施后，Agent 才将 `Status` 从 `draft` 改为 `approved`。批准同时覆盖本次要求、做法和验证安排，不再拆成需求、方案和开工三次确认。用户只认可方向、没有允许开工时，Agent 简短确认一次。

## 第二段：修改、验证与收尾

### 修改与验证

1. Agent 确认记录的流程为 `lite`、状态为 `approved`，要求、边界、做法与验证仍对应本次工作，再连续执行。`draft`、已完成记录或完整流程记录不能直接用于本次实施。
2. Agent 只做兑现已批准要求所必需的改动。局部写法和必要辅助文件可以自行选择；新增功能、顺手重构和相邻问题不在授权内。
3. Agent 按第 4 节执行验证，可以复用范围、动作、预期均匹配且仍适用于当前成果和环境的既有结果。用户验收只能复用用户本人明确确认、且仍适用的结果。
4. Agent 对独立且安全的验证一次收齐结果；依赖失败项或继续执行会造成破坏的项目停止，记录“未运行”和原因。Agent 不把失败、未运行或无法核实写为通过。
5. 验证执行者为用户时，Agent 给出前置条件、步骤和预期并等待反馈。用户未明确确认通过时，Agent 不代判，也不进入独立审查。
6. 失败可以在原授权内修复，再定向执行失败项及受修复影响的约定验证。不默认全量重跑，不自行增加验证系统。同一问题第三次验证仍失败时，Agent 停止自动修复，报告已尝试内容和剩余问题；无法执行不计作验证失败。
7. 必须改变要求、边界、做法中的实质决定或验证安排时，Agent 先停止。用户同意修订后，Agent 先将状态退回 `draft` 并递增版本，再修改开工内容。Agent 在第 5 节追加简短修订记录，保留旧版到新版的变化、原批准条款的必要原文和对应的已做改动，并写明哪些结果失效。R、V 不因删除而重新编号或复用；取代原条目时写清对应关系。用户重新批准后，Agent 在该记录注明批准的版本与内容，再继续实施，不用补写记录为已发生的越界改动背书。

新增的必要检查也属于验证安排变化，不能在批准后悄悄加入。Agent 可以说明建议，由用户决定修订或升级流程。普通实现、自检、结果登记不要求逐步确认。

### 独立审查

全部改动完成、约定验证均已通过或有适用结果后，主 Agent 先在第 5 节记录实际改动、逐项验证结果及其来源，再新建审查 Agent。约定了用户验收时，必须先取得用户确认；没有安排用户验收时，不增加一次用户确认。

主 Agent 使用 [独立审查提示词](templates/reviewer-prompt.md)，提供短记录路径、本次实际改动范围、已有工作区改动、验证结果及其适用依据。审查期间主 Agent 冻结本次成果，不一边审查一边修改。

审查 Agent 只读核对每条 R 的实际落点、边界、已批准做法、适用规范和已有验证结果，并检查本次改动及直接相关路径中的具体缺陷。审查 Agent 不重复测试，不重新选方案，不新增要求，不修改任何文件，也不调用要求完整计划的 `sdd-review`。

审查结论只有三种：

- **通过**：每条 R 有支持符合判断的依据，没有未解决的具体缺陷或影响通过判断的核实限制，约定验证均有满足预期且仍适用的结果。
- **不通过**：存在已证实的要求违反、具体实现缺陷或约定验证未满足。审查 Agent 列出问题、依据和修正目标。
- **受阻**：没有足以确定不通过的问题，但关键事实缺失，不能作出通过判断。审查 Agent 写明缺失内容和影响。

不影响行为、理解和结论的笔误可以作为轻微问题保留，不阻止通过。审查 Agent 不把“有更好做法”当成缺陷。

主 Agent 等待子任务结束并取得完整结果后，将结论、逐条 R 判断、问题及核实限制忠实写回第 5 节，不自行改判。主 Agent 不另建审查报告；审查 Agent 没有可用的独立上下文时，主 Agent 记录受阻，不自审替代。

审查通过后，主 Agent 将 `Status` 改为 `completed`。不通过或受阻时，状态保持 `approved`，并明确写明本次未完成、需要回第一段重新确认，还是只需继续原授权内的修复或补齐结果。涉及复杂方案、重要影响或长期约定时，建议升级完整流程。

本次流程至此结束。主 Agent 不在收到不通过或受阻结论后自动修复、重开审查或要求用户确认审查结论。用户另行启动修复后，审查只复核原问题和直接影响；原问题编号与仍适用结论保留，不能静默删除。

## 升级与延期处理

- 升级由用户决定。Agent 提供已确认要求、事实、决定、已做改动和验证结果，不把轻量批准当成完整流程的批准。
- 用户同意升级后，Agent 保留原轻量记录，不覆盖为另一种格式；按新交付建立完整流程记录，并互相引用。完整流程复用可靠材料，按对应阶段完成自己的批准，不重问已确定事项。
- 用户明确承诺未来处理某事项时，Agent 问清触发条件和完成标准，再登记到根目录 `FOLLOW.UPS.md`。仅明确不做、不承诺未来处理的内容留在本记录，不登记延期。
- 延期记录使用现有的 `ID`、`状态`、`事项`、`来源 spec`、`触发条件`、`完成标准` 六个字段，状态为 `待办` 或 `进行中`。ID 从文件头“已分配最大编号”继续递增为 `FUP-NNN` 并同步最大值，不能按现存记录猜号；无法确定时询问用户。新建空文件时从 `FUP-000` 起分配。
- 同一延期事项更新原记录，不重复新增。完成须有证据，取消须有用户决定；满足条件后从活跃清单移除，在本次记录保留证据或取消理由。

## 交付回复

Agent 先用一句话说明用户现在能看到或做到什么，再报告：

- 当前是待批准、已完成，还是未完成；记录路径及版本。
- 实际改动范围和逐项验证结果，区分本次执行、复用、未运行与无法核实。
- 独立审查结论、未解决问题和判断限度；没有审查时直说未审查。
- 本次新增或处理的延期事项，以及需要用户决定的具体内容；没有则不列空项。

只有独立审查通过才能宣称轻量交付完成。轻量切片完成不代替路线图的整体完成条件验收。
