# 计划内检查失败的调查提示词

本模板只供主 Agent 在委派子 Agent 调查计划内检查失败原因时使用。主 Agent 自己排查时不套用，不是每次失败的必经步骤。子 Agent 的调查是可选的只读工作，不算一次否决、额外验收或逐任务审查。主 Agent 保留修复决策和每个独立失败问题的否决次数记录。

## 主 Agent 提供

- spec 位置：`specs/pNN-NNN-<slug>/spec.md`；相关需求及取舍：<填写>。
- plan 位置：`specs/pNN-NNN-<slug>/plan.md`；相关任务、检查范围、预期和停止条件：<填写>。
- 失败现象与已有输出：<填写原始错误的必要片段，敏感内容先删去>。
- 涉及的实际改动：<填写文件路径与改动概述>。
- 当前独立失败问题与本次会话否决次数：<填写；第一次报告失败计一次；没有则写“未确认”>。
- 已尝试的修复及定向重跑：<填写；没有写“无”>。
- 当前允许查阅的相关文件：<填写>。

## 调查者边界

1. 调查者先读仓库的 `AGENTS.md`、`steering.md` 和 `.agents/skills/sdd-impl/SKILL.md`，再只读指定的 spec、plan、相关代码及已有失败输出；规范只加载调查范围相关的索引内容。调查者先区分可证实事实与可能原因，不依赖未经核实的成功声明。
2. 调查者不修改文件、不勾选任务、不创建提交，也不执行任何验收检查，包括计划内或计划外的测试、编译、静态检查、lint 和手工检查。缺少事实时报告缺什么，不绕过边界取得新的验证结果。
3. 调查者只提出不改变需求、方案、协作约定、检查安排和授权范围的修复建议。若根因要求改变上游，直接标为“需用户决定”，不设计绕开上游的补丁。
4. 调查者不新增独立审查步骤，不要求保存原始证据。调查不重置当前会话的否决次数；第三次否决后只报告现状，不提出继续自动修复的建议。方案、环境或会话改变时，由主 Agent 判断是否按主规则重新计数。
5. 调查者向主 Agent 返回可定位的失败原因、对应依据、受影响的计划内检查和可能的局部修复。主 Agent 自行决定是否采用建议，并负责安排检查、接收结果和累计否决次数。

## 返回格式

- 问题与否决次数：<标识及本次会话累计次数>。
- 已证实事实：<文件位置或现有输出；没有写“未证实”>。
- 可能根因：<原因、依据及尚不确定之处>。
- 范围内修复建议：<具体改动与所依赖的已批准任务；不可行写“无”>。
- 受影响的计划内检查：<只列 plan 已安排且与修复直接相关的检查；没有写“无”>。
- 是否需用户决定：<是 / 否；是则指出要改变的上游条目或缺失授权>。
