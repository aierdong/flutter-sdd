# sdd-impl

## 职责与交付

本技能指导 Agent 执行一份已批准的执行计划（`plan.md`，简称 plan）。需求说明（`spec.md`，简称 spec）定义用户要求；plan 定义已确认的方案、任务依赖、执行者和检查安排。`R1` 等编号定位需求，`T1` 等编号定位任务。

主 Agent 是当前会话中负责执行、进度和交接的 Agent。子 Agent 是主 Agent 为一项或一组任务派出的执行者。用户决定需求和超出授权的变更。

Agent 按任务依赖连续完成计划内改动与检查，不重新决定需求、方案、协作约定或验收条件，也不以保证质量为由追加工作。实现任务的改动完成即可勾选；检查任务单独勾选。最后主 Agent 在对话中说明实际改动、检查结果和未完成事项，并自动在新建的独立子 Agent 中启动 `sdd-review`。只有审查通过，整个 spec 才能宣称完成。

适用规范只约束代码和文档怎么写，不自动产生检查任务。计划没有安排的检查，Agent 不因为规范写了就运行。

本技能不强制测试驱动开发（TDD，即先写失败测试再写实现）、逐任务审查、测试证据归档、独立实现记录或 Git 提交。用户或 plan 明确安排的测试、产物和提交照安排执行；未安排的不能擅自补上。

## 启动门槛

1. Agent 先读 `AGENTS.md`、`steering.md`、本文件和目标目录的 `spec.md`、`plan.md`，按索引读取与任务相关的已生效规范，并读取计划涉及的现有文件。`project.md`、README 和进度记录只作背景，不代替批准依据。
2. Agent 确认 spec 的 `Status` 为 `approved`，第 7 节没有待用户决定的问题。Agent 确认 plan 的 `Status` 为 `approved`，头部引用的 spec 编号和版本与当前已批准 spec 一致。`draft`、`design-ok`、`stale` 或缺失的计划都不能进入实现；用户口头启动实现不代替这些前置条件。
3. Agent 读 plan 第 1–6 节，区分实现任务与检查任务，记下依赖、执行者、已知影响文件、不碰范围、已确认的规范例外和风险撤回办法。当前任务缺少必需的前置产物，或上游文件不一致时，Agent 停止并说明阻塞点。检查入口若由尚待执行的前置任务提供，Agent 不因它目前不可用而提前停工；到该检查的执行时机，仍无适用结果且入口不可用时，再按计划边界报告阻塞，不猜新方案。
4. Agent 查看现有任务勾选和当前对话，核对已完成改动、已有检查结果、结果适用条件，以及本次会话中每个独立失败问题的否决次数。勾选只标识续做位置，不证明检查通过。恢复会话时，Agent 不因没有新测试证据而重做已完成任务，也不能因找不到可靠结果就声称通过。
5. 仓库使用版本控制时，Agent 记录开始时已存在的工作区改动，避免覆盖用户或其他任务的工作。仓库没有版本控制时，Agent 跳过这项工作区记录；不为它建立额外状态文件。
6. 计划被用户修订过时，Agent 从第 1 步重新核对，不沿用修订前的读取结果。修订可能改变任务编号，Agent 按新 plan 重新确认已完成范围，不假设旧勾选仍然对应。

前置条件满足后，Agent 在授权范围内连续执行，不在普通步骤之间等待用户说“继续”。缺少用户必须决定的信息、需要改动上游或触及停止条件时才暂停。

## 执行任务与控制范围

- Agent 按 plan 的任务依赖执行未完成任务，不把任务顺序调整成新的技术方案。实现任务由主 Agent 决定自己执行、分组还是委派；检查任务的执行者由 plan 指定。
- Agent 可以自行选择不改变需求、方案、必要协作约定和验收条件的局部写法。plan 第 3.3 节是已知影响文件清单，不是封闭白名单。完成已有任务所必需的辅助文件可新增，无须先改计划；Agent 在交付时说明文件用途。Agent 不能借此新增功能、改变方案或顺手重构无关内容。
- Agent 按已批准的例外及适用规范实现。实现必须改变 spec 的需求或取舍、plan 已确认的方案或授权范围时，Agent 停止，写清原因，请用户决定返回需求或计划阶段。Agent 不自行修改上游文档来取得授权。
- 计划需要新增检查或调整任务时，Agent 不在当前会话修改 `plan.md`。Agent 停止并说明需要调整的内容，请用户在新会话中按 `sdd-plan` 修订计划；需要改变需求时，先按 `sdd-requirement` 修订 spec。用户返回后，Agent 按启动门槛重新读取和核对，再继续。计划重新批准后，Agent 重新核对任务与检查安排；只有本次会话尚在继续且同一问题、同一方案和环境均未改变时，才沿用本次会话的否决次数。
- 实现任务的改动完成、与既定协作边界一致时，Agent 在 plan 第 4 节把对应 `- [ ]` 改成 `- [x]`。Agent 不等待末尾检查才勾选实现任务，也不把勾选描述为检查通过。未完成任务保持未勾选。

## 委派实现任务

1. 主 Agent 根据 plan 找出各实现任务的前置产物、共享文件和协作约定。未满足的依赖不能因为委派而跳过；任务相互依赖时，同一组内仍按依赖顺序执行。
2. 主 Agent 将共享上下文多、需要连续衔接且可以清楚交付的一组任务交给同一子 Agent，避免每个任务重新读取相同材料。短任务、频繁跨组协调的任务，或交接成本高于执行成本的任务，留在主会话。
3. 主 Agent 只在各组前置条件已满足、组间没有未解决的结果依赖、改动文件与共享资源不冲突且成果可分别归属时并行委派。可能新增的辅助文件也要核对所有权；边界不清时先协调或串行执行。并行组完成后，主 Agent 核对结果，再启动依赖这些结果的任务。
4. 实现子 Agent 读取分组所需的原文，只完成已委派的实现任务或指定的修复，不执行检查任务，不修改 plan，不扩大范围，不创建提交。主 Agent 核对每项结果、统一勾选 plan 任务、累计否决次数、处理组间交接。
5. 主 Agent 可以用 [实现任务组提示词](templates/implementer-prompt.md) 委派实现任务，也可以直接执行。主 Agent 要求子 Agent 修复失败问题时，在委派中说明该问题本次会话的否决次数。

检查任务按 plan 指定的执行者另行处理，不附在实现任务组的委派中。plan 指定 `子 Agent` 时，主 Agent 另派一个检查子 Agent；该子 Agent 不得是本次负责被检查改动的实现子 Agent。主 Agent 自己执行任务或排查失败时不套用两份子 Agent 提示词。

## 计划内检查与结果复用

这里的“检查”包括测试、编译、静态检查、代码 lint（项目自带的代码格式与规则检查命令）和手工验收。Agent 只执行 plan 明确安排的检查。没有安排检查时，Agent 不自行运行，也不因缺少检查结果阻止实现结束。Agent 认为确需增加检查时，说明原因，请用户决定是否补入计划；批准前不执行，批准后按上节修订计划。

1. Agent 按 plan 安排的时机检查：默认在实现任务之后集中执行，plan 明确安排的中途检查按其依赖执行。Agent 不为每个实现任务插入重复检查，也不默认扩大为全量检查。旧 plan 若把改动和验证写在同一任务，改动完成可先勾选作为续做位置，但该任务所列验证仍须按原安排执行或复用适用结果；主 Agent 在交接审查前逐项核对，不能凭任务勾选推断验证已通过。
2. Agent 按检查任务的 `执行者` 执行。`主 Agent` 由主 Agent 执行；`子 Agent` 由另行派出的检查子 Agent 执行；`用户` 是人工验收，按第 5 条执行。老计划没有这一行时，按主 Agent 执行。plan 指定子 Agent，但环境中没有可用子 Agent，或它无法使用所需入口时，主 Agent 停止并说明，不擅自改派。
3. 检查执行者只执行 plan 所列检查，不新增检查，也不边检查边修复。对同一批可独立执行的检查，执行者全部完成后一次性报告，不在第一个失败处停止。若后续检查依赖失败项成功，或继续执行会破坏环境、数据或泄露敏感信息，执行者停止受影响的项目，标记“未运行”及原因；不受影响且安全的项目继续执行。报告按检查项列出结果、独立失败问题及无法执行的原因。主 Agent 收齐本批结果后再决定由谁修复。
4. 执行前，主 Agent 核对已有同项结果是否覆盖计划指定的动作、范围与预期，并且仍适用于当前代码和相关环境。plan 明确禁止复用时必须重新执行。`主 Agent`、`子 Agent` 检查的适用结果可以来自用户、其他执行者、前序任务或先前会话；执行者不同本身不是拒绝复用的理由。执行者为 `用户` 的人工验收，只能复用用户本人先前明确确认通过、且仍适用的同项验收结果；其他执行者的结果不能代替用户确认。无法确认结果与当前状态的对应关系时，主 Agent 不把它当作通过。检查子 Agent 只接收仍须执行的计划内检查，不因委派而重跑已复用的项目。
5. 执行者为用户的检查，主 Agent 在对话中给出操作步骤、前置条件和预期结果，然后等待用户反馈。用户明确说通过时，主 Agent 勾选对应检查任务；用户判为不通过时，主 Agent 按实际现象识别独立失败问题，并按下节规则计数。同一问题在未发生修复或相关环境变化之前，即使其他检查执行者也报告失败，仍只计一次否决。用户未反馈时，任务保持未勾选，实现阶段停在这里，不自动进入审查。反馈模糊时，主 Agent 追问具体现象，不猜结论。
6. 检查成功或适用结果满足预期时，主 Agent 才勾选对应检查任务；失败、未运行或无法判断时保持未勾选。后续改动使某项已勾选检查的结果失效时，主 Agent 先取消该检查的勾选，再按 plan 原执行者定向重跑或重新请求用户验收；新结果明确通过后才重新勾选。实现任务勾选和检查任务勾选都不能替代实际结论。

## 检查失败后的有限修复

主 Agent 按每个独立失败问题累计**否决次数**。第一次计划内检查或人工验收明确报告该问题未通过，计第一次否决。同一批有多个独立失败问题时，每个问题各计一次。一次修复或相关环境变化之前，主 Agent 将不同执行者、不同计划内检查报告的同一问题合并为一次否决；只有完成修复或相关环境变化后再次检查仍未通过，才对同一问题新增一次否决。主 Agent 在当前对话中简要记下问题、每次否决的结果、已尝试的修复及当前次数，不另建记录文件。再次委派、换任务或给问题改名，不使本次会话中同一问题的次数归零。

- 检查执行者提交完整报告后，主 Agent 决定自己修复还是委派实现子 Agent 修复。Agent 可在不改变需求、方案、协作约定及授权范围的前提下自行修复，不逐次等待用户确认。子 Agent 接到修复任务时，主 Agent 告知该问题本次会话已被否决的次数；子 Agent 不自行执行检查或改变计数。
- 修复后，主 Agent 仅安排原失败项及修复直接影响的、plan 已安排的检查，由 plan 指定的执行者定向重跑；不默认全量重跑，也不插入独立审查。修复使其他已有结果失效时，仅重新执行受影响的计划内项目。检查仍按上节一次性报告及安全边界执行。
- Agent 可以自行调查现有代码与失败输出；需要只读调查时可委派子 Agent，使用 [失败调查提示词](templates/debugger-prompt.md)。调查者不改文件、不执行验收检查、不决定新方案；调查本身不是否决，换调查者不改变次数。
- 同一问题在当前计数范围内第三次被否决时，主 Agent 停止针对该问题的自动修复，保留现场，不自动回滚。主 Agent 报告已尝试内容和遗留问题，请用户判断是否需要改变方案、环境或处理方向；这不是永久禁止用户以后重新启动工作。
- 修复途中发现必须改变需求、方案或授权范围时，Agent 立即停止并交用户决定，不为凑满三次否决而继续尝试。环境或前置条件不具备而无法执行计划内检查时，Agent 报告阻塞，不假称通过；无法执行不计作否决。
- 否决次数只保存在当前对话。用户重开会话，或在同一会话内实质改变已批准的实现方案、检查所依赖的环境后，主 Agent 可以从零开始计数；需修改上游时先按上节完成批准。主 Agent 在重置前说明变化及为何原失败不能再代表当前方向。仅调整无关任务或检查、改名、换任务或换执行者，不算方案或环境实质改变；没有变化时，本次会话已知的次数继续累计。新会话不推断旧会话的次数，不为重置建立额外状态文件。

## 收尾与审查交接

全部实现任务已完成、所有计划内检查任务已通过或有仍适用的可复用结果、人工验收已得到用户确认后，Agent 核对任务勾选与实际结果。Agent 在对话中先说明做完会看到什么，再简要列出实际改动（包括新增的必要辅助文件）、哪些检查本次执行及其结果、哪些复用及适用依据、哪些未安排或未运行，以及仍有哪些未完成事项。Agent 不生成实现记录、原始输出归档、截图、日志或默认 Git 提交；用户或 plan 明确要求的产物和提交除外。

条件未满足时，Agent 保留未完成任务的勾选状态，如实说明当前进度和需要用户决定的事项，不自动进入审查。人工验收等待用户反馈时，Agent 明确停下等待，这不算违规暂停。

满足条件后，主 Agent 不等待额外确认，必须新建一个独立子 Agent，在该子 Agent 中启动 `sdd-review`。主 Agent 不在实现会话中直接执行审查，也不恢复或复用参与过本次实现、检查或失败调查的子 Agent 会话。主 Agent 向审查子 Agent 提供 spec、plan 的路径、当前实际改动范围、已知检查结果及其适用依据；这些材料用于交接事实，不代替审查结论。

独立上下文的建立与启动由本技能负责。`sdd-review` 是独立审查阶段，不是每个任务的附加审查；审查子 Agent 自己执行该技能，无须为获得独立视角再派核查者。本技能不规定审查的内部步骤，也不代替它编造 `review.md` 或审查结论。

主 Agent 等待审查子 Agent 结束并取得完整返回结果后，向用户转达审查结论、报告位置及遗留问题，不再要求用户确认审查结论。审查不通过或受阻时，主 Agent 结束本次流程，说明报告指出的返回阶段，不自动修复或重启实现。

运行环境中尚无 `sdd-review`，或无法新建独立子 Agent 时，主 Agent 说明实现阶段已完成、审查交接受阻，不退回实现会话自行审查；此时不能宣称整个 spec 完成。

只有用户明确要求跳过流程时，Agent 才可跳过相应步骤，并在回复中逐项说明跳过了什么。
