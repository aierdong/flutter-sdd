# 检查维度

## 用法

维度是 Agent 必须逐条思考并留下记录的一类检查方向，不是要向用户逐条提出的问题。下面的清单优先列出容易造成返工的情况。不同需求类型必须检查不同维度：

| 类型 | 必检维度 | 通常不必问 |
|---|---|---|
| 新建 | D1–D6 + N1、N2、N3（共 9） | 哪些已有行为必须保持不变 |
| 增量 | D1–D6 + E1–E5（共 11） | 用户与场景 |
| 修正 | D1、D6 + F1–F4（共 6） | 首版边界、用户与场景 |

维度 ID 是固定编号。日志的覆盖矩阵、spec 第 7 节的 `维度：` 和校验脚本都使用它。Agent 不得修改已有 ID；记录额外检查方向时可以另加一条，不占必检集合。

**提问前先自问**：这个问题在当前场景下是否存在惯例或通行做法？存在，就按通行做法自己定，在 `grill.md`「自主决定」记一行，不向用户提问。不存在，或用户确实可能有偏好、两个答案会让验收标准不同，才提问。用户仍保留最终判断：批准需求前可查阅「自主决定」并推翻任意一条。

Agent 每轮按顺序检查每个维度，每个维度问 0–2 个问题。要思考，未必一定要问；判断不必问的维度，在覆盖矩阵记「自主决定」并指向对应记录。为把某个问题聊透而继续的追问记入成本字段的「深挖」，不占基础额度。下文所有业务例子均为虚构。

## 通用维度

### D1 失败与部分失败

**为什么检查**：流程可能已经完成一部分才失败。Agent 必须先判断系统保留什么、用户看到什么，避免实现后重做。按场景通行做法能定下的就不提问。

**检查什么**：

- 系统在哪一步可能失败？
- 系统是否保留已完成的部分？谁负责清理？
- 用户会看到什么？用户能否重试？系统会不会重复处理？

**例子**：

- 系统导入前 20 行成功，第 21 行失败。
- 系统已生成报告，但刷新报告列表失败。
- 用户提交表单成功，但系统发送通知失败。

**答案含糊时怎么继续查**：

- 用户说“失败就报错”时，Agent 问：“用户再次打开页面时，还能看到已导入的 20 行吗？”
- 用户说“重试就行”时，Agent 问：“系统会不会把已成功的行再导入一次？”

### D2 边界与既有行为

**为什么检查**：新增功能可能改变已有行为。Agent 应在实现前查清谁依赖这些行为。

**检查什么**：

- 本次除了新增能力，还会改变哪些已有行为？
- 哪些测试、文档或用户操作依赖这些行为？
- 系统如何处理旧数据和旧配置？

**例子**：

- 用户仍需按原来的方式筛选报告列表。
- 旧表单没有新字段，系统需要确定显示什么。
- 自动化程序读取报告中的固定字段，字段改名后会读取失败。

### D3 空与极值

**为什么检查**：Agent 应先判断空数据和极端输入怎么处理；没有用户偏好时按通行做法定下，避免测试时才补需求。

**检查什么**：

- 数据为 0 条、1 条或达到上限时，系统分别怎样处理？
- 用户输入重复值、超长文字、中文或其他非英文字符、空字符串时，系统怎样处理？

**例子**：

- 没有报告时，页面显示空白、提示，还是创建入口？
- 用户连续导入两份同名文件时，系统怎样区分两次的结果？
- 用户填写的表单名称为空、过长或与已有名称相同时，系统怎样处理？

### D4 并发与顺序

**为什么检查**：多个操作可能同时发生或先后顺序不同。Agent 应先判断结果，避免实现时临时改变接口。

**检查什么**：

- 两个入口同时修改同一份数据时，系统怎样处理？
- 用户重复提交，或系统收到请求的顺序与发送顺序不同时，结果是什么？
- 用户取消后又重试时，系统怎样区分这些操作？

**例子**：

- 两个窗口同时编辑同一份表单。
- 用户提交导入后，又立即点击取消。
- 用户连续生成两份报告，较早提交的报告反而较晚完成。

### D5 权限与密钥

**为什么检查**：Agent 应先判断访问范围和敏感信息处理有没有通行做法；涉及新增对外暴露面、权限模型、数据删除或不可逆操作时，才请用户决定，避免审查时补安全设计。

**检查什么**：

- 哪些用户能查看数据？哪些用户能执行操作？
- 错误信息、日志或导出文件是否含有敏感值？系统在哪里遮蔽或移除这些值？

**例子**：

- 报告包含联系方式，系统是否只显示部分号码？
- 系统导出报告时，访问外部服务所用的密钥不能出现在文件、日志或错误提示中。

### D6 可逆性

**为什么检查**：用户应知道操作能否撤销，不能在批准后才发现数据无法恢复。

**检查什么**：

- 哪一步操作不能撤销？
- 用户操作错误后，系统能恢复哪些内容？是否需要备份、预览或二次确认？
- 系统是否需要提前提示操作不可撤销？

**例子**：

- 用户删除报告时，系统同时删除其附件。
- 用户用新文件覆盖已导入的数据，旧数据没有备份。

## 类型专属维度

### 新建专属

**N1. 首版边界**

- 首版做什么、明确不做什么？用户为什么暂时不需要其余能力？
- Agent 必须查清首版范围，避免一个需求不断增加新目标。范围没有惯例可依，须请用户决定。

**N2. 用户与场景**

- 谁使用这项能力？用户多久使用一次？用户目前怎样解决问题？
- 用户已有手工操作或其他工具时，新能力需要改善哪一步？

**N3. 与既有能力的关系**

- 本次复用已有组件或接口，还是新增一套？
- 用户要求新增一套时，Agent 必须问清为什么不能复用，避免重复维护。

### 增量专属

**E1. 与既有 R 的关系**

- 本次扩展、修改或取代上游第 4 节的哪几条 R？
- Agent 必须写明被取代的编号，不能只写“调整了一下”。

**E2. 上游“不做”清单是否被推翻**

- 本次是否要做上游第 5 节明确不做的事项？
- 如果要做，用户必须明确推翻原决定，并说明当时不做、现在要做的原因。
- Agent 用这一检查避免两份 spec 的要求互相矛盾。

**E3. 边界是否外扩**

- 新能力是否超出上游 spec 的范围？
- 如果超出，Agent 必须写清新范围，不能把它当作顺手改动。

**E4. 老数据与老用户**

- 已有表单、导入记录或报告是否需要补字段或迁移？
- 用户升级后第一次打开页面会看到什么？

**E5. 回归面**

“回归面”指本次改动可能影响的已有行为。

- 哪些已有行为必须保持不变？Agent 将它们写进第 5 节“不改变……”条目。
- 哪些已有测试需要调整？调整是否意味着改变原来承诺的行为？

### 修正专属

**F1. 正确行为的一句话定义**

- 用户能否用“当 X 时，系统应该 Y”说清正确行为？Agent 说不清时应继续定位问题。

**F2. 同源入口**

“同源入口”指调用相同接口或使用相同逻辑的其他入口。

- 其他入口是否存在同样的错误？
- 本次只修当前入口，还是修复所有同类入口？用户必须明确范围。

**F3. 已产生的错误数据**

- 系统是否要修复此前生成的错误结果？
- 如果不修，用户会在哪里遇到这些结果？

**F4. 谁在依赖现状**

- 已有测试是否把错误行为当作预期？文档是否描述了错误行为？
- 本次修正会改变哪些已有预期？

## 次级维度（按需）

| 维度 | 检查什么 | 什么时候检查 |
|---|---|---|
| 触发者与入口 | 除当前用户外，命令行、自动化程序或定时任务能否触发操作？ | 新增能力时必检 |
| 数据留存与清理 | 系统保留记录多久？谁负责清理？ | 新增长期保存的数据或历史记录时 |
| 对外契约 | 本次是否改变接口、命令行输出或事件中传递的数据？ | 不同程序需要交换数据时必检；“对外契约”指双方约定的数据和行为 |
| 时间与外部依赖 | 系统超时、重试或外部服务不可用时，用户看到什么？ | 系统需要调用网络服务或外部存储时 |
| 观测与文案 | 用户看到什么提示？系统记录什么日志？ | 操作可能明显失败时 |
| 多目标差异 | 系统导入不同文件格式时，处理方式是否不同？ | 本次能力需要兼容多个目标时 |

次级维度不计入必检集合，也不进入覆盖矩阵。Agent 只在明显适用时检查；需要提问时在 `grill.md` 决策区记录答案，自己定下的记入「自主决定」。

## 覆盖矩阵

Agent 在访谈结束前填写 `grill.md` 的「覆盖矩阵」。矩阵记录每个维度怎样落地，格式固定，脚本按维度检查：

- 矩阵必须为本类型每个必检维度留一条记录。少一条会 FAIL；记录额外的检查方向不 FAIL。
- 新生成的覆盖矩阵必须使用记录块，不使用表格。每块以 `#### 维度 D2` 等唯一标题开始，下设 `- 维度：D2 边界与既有行为`、`- 状态：已问`、`- 依据：R1、§5` 三个字段。维度值必须以固定 ID 开头；字段与维度记录不得重复，值中的 `|` 不拆分。
- 状态只能写 `已问`、`自主决定`、`不适用`、`已推翻并说明`、`待决`。状态说明这个维度怎样落地，不说明问得多不多。
- 依据必须写具体位置：`已问` 写提问结论的位置（决策编号、R# 或小节），`自主决定` 写 `grill.md`「自主决定」里的 `A<N>` 编号，`不适用` 写具体理由。依据为空会 FAIL，引用不存在的 `A<N>` 也会 FAIL。
- spec 第 7 节涉及本类型必检维度的待决问题，矩阵对应记录必须标为 `待决`，不能用其他状态代替。依据写明对应问题，例如“§7 第 1 题：是否保留已导入的行”。
- 反过来，矩阵每个 `待决` 记录在 spec 第 7 节都必须有对应维度的问题。问题解决后，Agent 同步删除问题并更新矩阵状态与依据。
- 还有待决问题时，spec 只能保留为未批准状态，不能记为 `approved`。

下面是 `extend` 类型的完整格式示例。`§5` 表示第 5 节；示例中的需求和依据均为虚构，不可直接当成项目事实。D5 没有提问：`A1` 是 `grill.md`「自主决定」里的一条轻记录，用户批准前可以推翻。

#### 维度 D1
- 维度：D1 失败与部分失败
- 状态：已问
- 依据：R2 规定报告生成后刷新失败的提示

#### 维度 D2
- 维度：D2 边界与既有行为
- 状态：已问
- 依据：§5 规定保留原有筛选行为

#### 维度 D3
- 维度：D3 空与极值
- 状态：已问
- 依据：R3 规定空列表和最大条数

#### 维度 D4
- 维度：D4 并发与顺序
- 状态：已问
- 依据：R4 规定重复生成报告的处理方式

#### 维度 D5
- 维度：D5 权限与密钥
- 状态：自主决定
- 依据：A1 日志按通行做法遮蔽访问密钥

#### 维度 D6
- 维度：D6 可逆性
- 状态：不适用
- 依据：本次只新增查看入口，不修改或删除已保存的数据

#### 维度 E1
- 维度：E1 与既有 R 的关系
- 状态：已问
- 依据：R1 写明扩展 pNN-NNN R5

#### 维度 E2
- 维度：E2 上游「不做」
- 状态：已推翻并说明
- 依据：§6 说明本次为何允许查看历史报告

#### 维度 E3
- 维度：E3 边界是否外扩
- 状态：已问
- 依据：§5 排除报告编辑能力

#### 维度 E4
- 维度：E4 老数据与老用户
- 状态：已问
- 依据：R6 规定旧报告的显示方式

#### 维度 E5
- 维度：E5 回归面
- 状态：已问
- 依据：§5 规定原导出行为保持不变

Agent 写不出不适用理由时，必须继续检查该维度。Agent 标记「已问」时，依据必须指向提问结论的位置；标记「自主决定」时，依据必须指向 `grill.md` 的 `A<N>` 记录。两种都不能只写“已经讨论”。

## 追问示例

用户回答含糊时，Agent 应换一种问法，不重复原问题：

1. **给具体场景**：“报告生成后刷新列表失败，界面显示成功还是失败？”
2. **问已有做法**：“上一次导入失败时，你们保留了已成功的行吗？”
3. **问相反选择**：“如果系统撤销已成功的行，用户会失去什么？”
4. **问可能的误解**：“如果不写进 R，实现者最可能怎样理解？”
5. **增量时问上游**：“这次决定会改变上游的哪条要求？”

以下回答还不足以形成需求：

- 用户说“应该没问题”时，Agent 改问具体场景。
- 用户说“看情况”时，Agent 追问哪两种情况需要不同处理。
- 用户说“你决定”时，Agent 按当前场景的通行做法自主决定，记入 `grill.md`「自主决定」，不继续追问；用户批准前可以推翻。

## 决定问不问

Agent 在准备把一个维度变成问题前，先判断这个场景下是否存在惯例或通行做法。存在就自己定并记一笔，不提问；Agent 有能力做这个判断，不需要预先准备的惯例清单，也不问用户「这个要不要我定」。

只有下面几种情况才提问：两个答案会让验收标准不同、用户确实可能有偏好、问题涉及新增对外暴露面或不可逆操作，或需要改变跨 spec 约定的技术选型。用户明确指定的技术约束、测试要求和命令仍必须留在 spec，不能因其属于技术内容就移到 plan。

各维度的「检查什么」列的是思考方向，不是提问清单。实现细节、命名格式、不改变可观察结果的数值，以及按场景通行做法就能定下的处理方式，都由 Agent 自己决定。Agent 不猜测性能风险并因此上强度、增加验证系统；确有用户可观察的规模或时限约束且需求未写时，才把它作为需求问清。

Agent 检查每个维度后把结论落到行为上：影响用户可观察结果的，写进 R 或第 5 节；其余写进「自主决定」，并在覆盖矩阵引用它的编号。没有提问、也没有自主决定记录的维度，脚本会报缺口。

成本字段区分两类用量：向用户提出的不同问题计入「问题数」，受基础额度限制；为聊透同一个问题而继续的追问计入「深挖」，不占基础额度。基础额度用尽时，Agent 不为此向用户申请追加；确属新的实质分歧时停下，请用户决定是否拆 spec。
