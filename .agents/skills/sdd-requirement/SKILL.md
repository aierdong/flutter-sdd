# sdd-requirement

## 它解决什么问题

需求不清通常有两个原因：访谈漏问了重要情况，或 Agent 没有查清现有行为和已有决定。本技能先调查事实，再逐项访谈，最后生成需求文档。

本文使用以下术语：

- **spec**：一份只解决一个问题的需求文档，文件名为 `spec.md`。
- **R**：必须满足的需求条目，编号为 `R1`、`R2` 等。
- **维度**：访谈需要检查的一类问题，例如失败后的处理方式。
- **上游 spec**：本次需求所扩展或修正的已有需求文档。
- **闸门**：进入下一阶段前必须满足的条件。
- **lint**：检查文档格式和规则的脚本；它不能代替用户判断需求。

## 在流程里的位置

```text
sdd-requirement   →  spec.md + grill.md   用户明确确认后进入下一步
     ↓
sdd-plan    →  plan.md              第 1–2 节供人审阅，第 3–6 节供 Agent 执行
     ↓
sdd-impl    →  代码与提交
     ↓
sdd-review  →  证据与结论
```

本技能只负责需求阶段。输出应满足文末的「下游契约」。

## 边界

本技能负责判断需求类型、检查延期事项、只读调查、检查规范冲突、访谈和生成文档。文档包括 `spec.md` 第 1–7 节与决策日志 `grill.md`。用户明确延期的工作还要登记到仓库根目录 `FOLLOW.UPS.md`。

本技能不做以下工作：

- Agent 不替用户决定尚未确定的产品或技术选择。用户指定的技术方案、质量要求和测试要求必须保留在 spec，不能仅因其涉及技术就移到 plan。
- Agent 不写 `plan.md`，不拆实现任务，不改产品代码。
- Agent 不制定项目路线图，也不修改已有路线图。切片定义有误，或本次需求超出切片范围时，Agent 停下，由用户在新会话用 `sdd-roadmap` 修订。

技能和模板必须能移植到其他项目。示例统一用 `pNN-NNN`，不写死真实编号、项目特例或历史决定。`FOLLOW.UPS.md` 是通用的根目录待办文件名。

**四条硬规则**：

1. **访谈期间不写 spec。** Agent 应先问清需求，避免草稿让访谈提前停止。
2. **一次一问。** Agent 不要把多个决定放进同一个问题。
3. **事实自己查，决定问用户。** Agent 应用文件和命令核实事实，不让用户代查。
4. **只有用户明确确认才算批准。** lint 通过不代表批准。用户明确确认需求可以进入下一步后，Agent 才把 `Status` 改为 `approved`。用户不需要创建 tag、专用 commit 或其他批准凭据。

## 写作要求

本技能、规则、模板，以及生成的 spec 和日志，全文都必须让人读懂。计划中给 Agent 执行的部分也不例外。

- 写清谁做什么。一句话说一件事；条件多就拆开，不写无主语长句。
- Agent 在每份文档首次使用术语或阶段代号时，写出完整名称并解释用途。后文可以使用简称；相隔较远时可以再次使用全称，不强制每处重复。同一件事只用一个名字，编号只用于定位。
- 示例使用导入文件、生成报告等简单场景，不借用当前项目的特殊业务或技术规则。
- 只保留现行做法和必要理由，不把修改经过、历史决定写进使用说明。
- 先检查意思是否好懂，再检查格式是否正确。不能为了简短丢掉关键条件。
- 所有新生成的机械文档尽量不用表格；机械读取区域必须使用固定字段行或记录块。头部写作 `- Spec：` 后接反引号包裹的编号；成本使用普通 `- 类型：...` 等字段行。
- 记录块统一为 `#### <记录标题>` 下的 `- 字段：值`。同一区域的关键字段和记录不得重复，值中的 `|` 是普通文字，不拆列。覆盖矩阵字段固定为「维度 / 状态 / 依据」，规范触碰固定为「条款 / 状态 / 依据」。

## 输入

- 用户的需求描述，可以是口语或不完整的表述。
- 相关代码路径或上游 spec 编号；Agent 不确定时先调查。
- `steering.md`：知识索引，Agent 按索引读取相关规范、设计和专题。
- 同领域已有的 `spec.md`、`grill.md`：用于了解已有需求和决定。
- `specs/pNN-<slug>-roadmap.md`：大需求路线图。用户指定了切片，或需求明显落在某份路线图范围内时，Agent 读取它。
- 仓库根目录 `FOLLOW.UPS.md`：仍需处理的延期事项。

## 启动检查：延期事项

每次启动本技能，Agent 必须在判断需求类型和访谈前检查 `FOLLOW.UPS.md`。

1. 文件存在时，Agent 读取全部记录。文件不存在时，Agent 创建包含最大编号字段和空列表说明的模板。Agent 使用字段记录块登记事项，状态只保留 `待办`、`进行中`。
2. Agent 对照当前请求检查每项的触发条件，并简要汇报已触发或相关事项。条件已满足、当前需求可能覆盖该事项，或条件不明确时，Agent 先问用户：并入当前 spec、另开 spec、延期到新的触发条件，还是取消。所有项均未触发且不相关时，Agent 报告数量和“当前均未触发”。
3. Agent 不因条件到期就自动并入需求，也不静默删除或改期。事项完成必须有实现和验证证据；事项取消必须由用户明确决定。满足相应条件后，Agent 从文件中删除该事项记录。Agent 在 `grill.md` 待办登记中引用已有实现与验证证据的位置，不规划或新建实现审查证据文件；取消理由写回对应 spec 的「明确不做」或 `grill.md`。文件不保留已完成或已取消的记录。
4. Agent 在 `grill.md`「待办登记」中记录已触发、相关或经用户处理的项。没有这类项时，Agent 写明数量及均未触发或不相关；没有待办时写“FOLLOW.UPS 无待办项”。

新记录字段固定为 `ID`、`状态`、`事项`、`来源 spec`、`触发条件`、`完成标准`。ID 使用三位递增编号 `FUP-NNN`。文件头保存 `- 已分配最大编号：FUP-NNN`，新建空清单时写 `FUP-000`，另写“无待办项”。新增事项时，Agent 从这个编号加 1，并同步更新最大编号；删除事项时不降低它，已分配过的编号永不复用。

Agent 按以下格式记录事项：

```text
#### 待办 FUP-NNN
- ID：FUP-NNN
- 状态：待办
- 事项：<未来明确要做的工作>
- 来源 spec：pNN-NNN-<slug>
- 触发条件：<具体条件>
- 完成标准：<可判断的结果>
```

Agent 新增事项前必须确认已分配的最大编号，不能仅凭当前活跃事项的最大号推测，因为更大的编号可能已被删除。Agent 无法确认最大编号时，必须问用户，不得猜号新增。相同事项已存在时，Agent 更新原记录，不重复创建。仓库只维护这一个根目录文件，不增加 issue tracker（外部问题跟踪系统）、负责人、估时或截止日期。

## 启动检查：路线图与切片

大需求有路线图时，本次需求可能对应其中一个切片。Agent 在判断需求类型和访谈前完成这项检查。

1. Agent 看 `specs/` 下是否有同阶段的路线图。用户指定了切片，或需求明显落在某份路线图范围内时，Agent 读该路线图第 3 节对应的切片记录。
2. 用户没有指定、也没有对应路线图时，Agent 照常访谈。这次需求按普通 spec 处理，不要求用户补路线图。
3. 用户指定了切片时，Agent 依次检查三件事：
   - 路线图 `Status` 必须是 `approved`。状态为 `draft` 时，Agent 拒绝执行，并说明该路线图尚未批准。
   - 切片编号必须在路线图第 3 节存在。
   - 本次需求不能超出该切片的「解决什么问题」和「做完后用户能」。
4. 任何一项不通过，Agent 停下，不进入访谈，也不在需求里绕过。用户需要在新会话运行 `sdd-roadmap` 修订路线图并重新批准，再用新会话重读切片定义继续。
5. 检查通过后，Agent 在 `spec.md` 头部填 `路线图` 与 `切片` 两个字段，并在 `grill.md`「路线图对照」照抄该切片的定义和结论。没有指定切片时，两个头字段都写 `—`。

需求不在路线图规划内时，Agent 先比对现有切片：

- 与现有切片不冲突，例如只是调整某一片的页面布局或修正提示逻辑。Agent 按增补处理，编号沿用所附着的切片，`slug` 不同。是否登记到路线图由用户决定。
- 与现有切片冲突，例如改变某片的「做完后用户能」、触碰跨切片约定，或需要路线图之外的新能力。Agent 停下，按第 4 条处理，不在需求阶段扩大范围。

## 阶段 0：判断需求类型

| 类型 | 判定 | 虚构例子 | 必读 |
|---|---|---|---|
| **新建** new | 系统还没有这项能力 | “我要导入一份表格” | `steering.md` 指向的相关规范与设计、相似实现、可复用组件 |
| **增量** extend | 用户要为已有能力增加行为 | “在 spec pNN-NNN 的导入功能中增加预览” | 上游 `spec.md` 全文，尤其是 R、明确不做和边界；相关代码与测试 |
| **修正** fix | 已有行为错误或不完整 | “报告生成成功后，页面却显示失败” | 当前实现、已有测试，以及依赖现状的调用方 |

需求提到已有页面、功能或 spec 编号时，Agent 默认按增量处理，除非用户明确要求替换。这样可以避免重复定义同一能力。

### 增量或修正必须先问

> 这次要修订原 spec，还是在原 spec 之上新增一次交付？
>
> A. **修订原 spec**：Agent 修改原文件，递增版本（如 `版本: v2`），将状态改回 `draft`。用户再次明确确认后才能继续。原需求尚未实现完，或本次只补遗漏时，可选此项。
> B. **新建 spec 并引用上游**：Agent 使用新编号，头部写 `上游: pNN-NNN`。上游 R 不变，本 spec 声明扩展或取代哪些条目。上游已实现并验收，本次可独立验收时，可选此项。

A 会使原批准失效。B 会让两份 spec 并存，需要维护引用。Agent 不替用户选择。

## 阶段 1：调查事实

| 类型 | 工具调用预算 | 调查内容 |
|---|---|---|
| 新建 | 8 次 | 相关规范与设计、相似能力、可复用部分、本次涉及的配置文件 |
| 增量 | 12 次 | 上游 spec 全文、相关代码与测试、上游明确不做的事项 |
| 修正 | 8 次 | 当前实现、相关测试、依赖现状的测试数据、文档和界面入口 |

Agent 必须为阶段 1.5 预留读取规范条款的预算。规范较长时可以分次读取。Agent 不凭印象填写出处或行号。

Agent 在 `grill.md`「事实收集」中区分事实与待定决定。以下示例均为虚构：

```text
#### 事实 1：导入结果保存
- 已读：src/import_records.py:40，系统逐行保存导入结果。
- 未读：无。

#### 事实 2：报告入口
- 已读：src/report_page.py:25，用户可以在报告页重新查看上次导入结果。
- 未读：无。

#### 待定问题 1：部分失败
- 问题：某行导入失败后，系统是否保留已成功的行？
- 决定者：用户。
```

事实清单只写查到的内容，不写实现方案。

预算用尽时，Agent 不把尚未查清的事实转交用户决定，也不放进 spec 第 7 节：

1. Agent 在事实收集中列出「未读」内容，并说明哪些结论因此未验证。
2. 「待定问题」只保留需要用户决定的行为或约束。Agent 对可查的事实继续调查，或明确标为 `未验证` 并说明影响哪条 R。产品、技术、质量和测试选择都可能需要用户决定，不能仅因类别不同就移到 plan。

Agent 需要追加工具调用时，按阶段 2 的追加机制请求用户批准：每次追加 4 次，记录为 `工具追加`，最多 `+8`。仍不够时必须重新划分 spec 边界。

## 阶段 1.5：检查规范冲突

Agent 按 `steering.md` 读取本次涉及的 `docs/standards/*.md`，在 `grill.md`「规范触碰」中逐条记录：

1. Agent 检查本次行为、文案、目录结构、依赖和命令是否与规范冲突。
2. Agent 给每条写 `无冲突`、`冲突` 或 `不涉及`，并标明规范原文位置。
3. 冲突项必须进入访谈。用户决定修改规范、修改需求或拆分 spec；Agent 将决定写进 `grill.md` 和 spec 第 6 节。

规范冲突不能留在第 7 节。第 7 节记录尚有歧义的需求；规范冲突则是两处明确要求互相矛盾，必须先解决。`tools/sdd_lint.py` 会检查这一点。

本次不涉及任何规范条款时，Agent 在「规范触碰」写一行 `无`。

## 阶段 2：访谈

Agent 按 [rules/dimensions.md](rules/dimensions.md) 检查本类型的必问维度。

| 类型 | 先问 | 其次 | 可以少问 |
|---|---|---|---|
| 新建 | 用户与场景、首版边界、与已有能力的关系 | 失败后如何处理、空值与极值、权限、能否撤销 | 哪些已有行为必须保持不变 |
| 增量 | 与上游 R 和明确不做事项的关系、是否扩大范围 | 失败后如何处理、旧数据、已有行为、能否撤销 | 已知的用户与场景 |
| 修正 | 正确行为、其他入口是否有同样错误 | 已有行为、错误数据修复、失败后如何处理 | 首版边界 |

每个问题不超过 3 行，例如：

```text
Q: 报告已经生成，但刷新列表失败时，系统显示成功还是失败？
   A. 显示成功并提示列表未刷新 —— 用户知道不必重新生成报告。
   B. 显示失败 —— 用户可能再次生成同一份报告。
```

Agent 必须遵守以下规则：

- 两个选项都写具体行为，不用“更稳妥”“更友好”等形容词代替。
- 范围、数据影响、成本、不可逆操作这四类问题不给推荐答案。Agent 只可推荐实现方式。
- 用户回答含糊时，Agent 换成两个具体场景，请用户选择。
- 每条候选 R 都必须有反例。Agent 先写出违反该需求的具体情况，再请用户判断是否成立或补充。反例否决不占问题预算；Agent 写不出反例时，应重新问清该需求。
- 每轮至少做一次反向检查：Agent 列出可能顺手添加的配置项、重试或确认弹窗，逐条问是否需要。用户不要的内容写进第 5 节。
- 增量和修正必须逐条比较上游第 4、5 节。Agent 要问清修改哪条 R；若本次要做上游明确不做的事项，必须由用户明确推翻原决定并给出理由。

问题上限等于本类型必做维度数加 3 次派生追问：新建 12、增量 14、修正 9。派生追问指访谈中新出现的澄清问题，例如拆分顺序或方案冲突，不是新增维度。

Agent 只统计向用户提出的问题，不计反例否决、事实核实和规范触碰扫描。Agent 将计数写进 `grill.md` 成本字段，lint 检查 `问题数 ≤ 上限 + 追加`。

### 达到上限后怎么办

Agent 达到当前上限而仍有问题时，必须停下，不自行多问。Agent 给用户以下选择；这一问本身不占预算：

> 预算已用完，还剩 N 个具体问题：<逐项列出>。
> A. **拆分**：按 <具体切法> 拆成两个 spec，各自重新计算预算。
> B. **追加**：确认仍是同一个问题，追加 4 问（`+4`）后继续。

拆分与追加属于范围决定，Agent 不推荐答案。用户批准追加后，Agent 填写成本字段的 `问题追加` 和 `追加理由`。理由必须说明谁批准、为什么仍是一件事。

- Agent 每次只能追加 `+4`，最多两次，合计 `+8`。第三次必须拆分。
- 追加额度必须是确定数字，不能写“按需”或“视情况”。
- 有追加额度就必须有理由。
- 工具预算使用同一机制，填写 `工具追加`，同样最多 `+8`。

### 决策日志

Agent 在 `grill.md` 追加决策，不改写已有记录。以下为虚构例子：

```text
#### Q1：部分失败处理
- 问题：某行导入失败后，系统是否保留已成功的行？
- 决定：保留。用户需要先使用已成功的数据。
- 放弃：撤销整次导入。
- 何时重新评估：用户要求整份文件必须全部成功时。
- 对应：R2 / §5
```

Agent 从日志整理 spec 第 6 节。后续需求涉及同一领域时，Agent 先读日志，避免重复询问。

### 登记延期事项

用户明确决定把工作留到下一个 spec、下一次代码交付或其他未来条件时，Agent 按以下步骤处理：

1. Agent 先确认用户确实承诺未来要做。用户只是明确不做时，内容只放在 spec 第 5 节。
2. Agent 问清触发条件和可判断的完成标准。“以后”“有空”不足以登记。
3. Agent 在 `grill.md` 记录决定，并立即将待办写入根目录 `FOLLOW.UPS.md`，填齐 ID、事项、来源 spec、触发条件、完成标准和状态，不让用户手工抄写。
4. 待办来自 spec 第 6 节「何时重新评估」时，Agent 必须在 lint 前同步根目录文件。Agent 在「待办登记」记录 ID、本次结果、来源决定和后续触发条件。
5. Agent 不确定是否属于未来承诺时，必须询问用户，不批量把“明确不做”加入待办。

## 阶段 3：检查闸门

Agent 必须先满足以下要求才能组装 spec。文档写完后还必须运行 lint，退出码为 0 才能交付。脚本只能检查格式，不能替人判断内容。

| 闸门 | 判据 | 谁来判 | 不通过时怎么处理 |
|---|---|---|---|
| 头字段 | Spec / 类型 / 上游 / 附带交付 / Status / 版本齐全且合法；Spec 与目录名一致；没有批准凭据字段 | `sdd_lint.py` | Agent 补齐或修正字段和目录 |
| 结构 | 第 1–7 节标题齐全 | `sdd_lint.py` | Agent 补齐 |
| 规模 | R 编号连续，共 1–12 条 | `sdd_lint.py` | 用户拆分需求 |
| 可测条目 | 每条 R 有非空的 `**反例**`、`**可观察证据**` | `sdd_lint.py` | Agent 重新访谈 |
| 范围 | 每条「不做」带 `理由：` | `sdd_lint.py` | Agent 补理由或删条 |
| 覆盖面 | 覆盖矩阵恰好包含本类型的必做维度；`不适用` 有理由 | `sdd_lint.py` | Agent 补访谈 |
| 前后一致 | 第 7 节涉及的必做维度在矩阵中标为 `待决`；矩阵每个 `待决` 记录都有对应问题 | `sdd_lint.py` | Agent 问清或如实记录待决状态 |
| 第 7 节格式 | 每条问题有 `维度：<ID>` 和 A/B 两个具体选项；有待决问题时不得 `approved` | `sdd_lint.py` | Agent 补选项或继续请用户决定 |
| 规范触碰 | 日志有清单；冲突项不留在第 7 节 | `sdd_lint.py` | 用户在访谈中解决冲突 |
| 成本基线 | 十一个字段齐全；问题和工具用量不超预算与追加之和；追加只能为 `+4` / `+8` 且有理由；类型与 spec 一致 | `sdd_lint.py` | Agent 停下请用户拆分或追加 |
| 附带交付 | 登记的 R# 存在且带 `**范畴**`；带范畴的 R 已登记 | `sdd_lint.py` | Agent 补登记或移除标记 |
| 路线图对照 | 头部 `路线图` 与 `切片` 同填或同空；`grill.md` 有对照记录且照抄切片定义；结论不是「超出」「切片定义有误」 | `sdd_lint.py` | Agent 停下，交用户决定是否修订路线图 |
| 延期待办 | Agent 已检查全部活跃项、登记本次延期工作和处理结果，并删除已完成或取消的记录 | 人 | Agent 补登记或问清条件 |
| 长度 | 第 1–6 节约 200 行内，R 不靠合并多件事来减少条数 | 人 | Agent 删冗余文字，不删需求 |
| 可测性 | 每条 R 能用“条件 + 行为 + 结果”说清 | 人 | Agent 重新访谈 |
| 诚实 | 待决问题不包含可查事实；内容不是为通过检查而填的空话 | 人 | Agent 回阶段 1 补查 |

```bash
python .agents/skills/sdd-requirement/tools/sdd_lint.py specs/pNN-NNN-<slug>
```

lint 有 FAIL 时，Agent 不交付 spec，也不通过解释绕过检查。文档不符合现行规则时，Agent 修正文档。怀疑校验规则有误时，Agent 暂停交付，向用户说明问题、依据和拟议变更；用户明确确认后，才按确认范围修改规则和校验。普通使用本技能时，Agent 不得自行修改校验来让文档通过。

### 校验脚本

`tools/sdd_lint.py` 使用 Python 3.8+ 标准库，不依赖项目语言、框架或构建系统，也不需要安装第三方包。

- Agent 从技能原位置运行脚本，不把它复制进产品目录。POSIX 环境使用 `python3`。
- 退出码 `0` 表示全部通过；`1` 表示有 FAIL；`2` 表示用法错误或缺少 `spec.md`、`grill.md`。Agent 根据退出码判断结果。
- 脚本按常量、解析、结果容器、spec 检查 L01–L07、grill 检查 L08–L10、入口分段。
- 维度 ID、预算和上限由 `rules/dimensions.md` 与脚本常量共同定义。修改时必须同步。

## 阶段 4：组装文档

1. Agent 按 [templates/spec.md](templates/spec.md) 写需求，按 [templates/grill.md](templates/grill.md) 写日志。
2. 目录为 `specs/pNN-NNN-<英文短横线slug>/`。`pNN` 使用现有目录中最大的两位阶段号；`NNN` 为阶段内三位序号，从 `001` 起，新 spec 取该阶段最大编号 +1。两份文档放在同一目录。
3. 第 7 节只保留真正未决的问题，每条有两个选项和 `维度：<ID>`。访谈充分后，这一节应接近为空，不能用“是否完整”“是否有风险”充数。
4. Agent 运行 lint，修改文档直到退出码为 0。
5. Agent 停下，不写 plan、不生成任务、不改代码。Agent 简要汇报结果与未决问题，请用户确认需求是否可以进入下一步。

### 记录批准

1. Agent 交付时使用 `Status: draft`。lint 通过只说明结构合格。
2. 第 7 节没有待决问题，且用户明确表示需求可以进入 plan 或下一步后，Agent 才改为 `approved` 并继续流程。还有待决问题时，Agent 先请用户决定。用户不需要编辑文件或提供其他凭据。
3. 用户只说“看起来不错”而没说明是否继续时，Agent 简短确认一次。用户拒绝或要求修改时，状态保持 `draft`。
4. 批准后需求冻结。用户要求实质修改需求、边界或决策时，Agent 递增版本并改回 `draft`，等待再次确认。纯排版或不改变意思的勘误不重开批准。已有 plan 受影响时，Agent 将其标为 `stale`。
5. `Status` 只标记流程位置。Agent 不核验 Git tag、commit 或 diff 来证明批准。

## 输出说明

lint 通过后，Agent 给用户四行总结：

1. **结论**：一句话说明做完会看到什么，再写类型与 R 条数；增量或修正附 `上游: pNN-NNN`；指定了切片时再写 `路线图: pNN 切片 NNN`。
2. **闸门**：退出码、通过项数、维度覆盖数与不适用数、遗留问题数。
3. **成本**：问题数 / 上限、追加额度、工具调用数 / 预算。
4. **下一步**：请用户阅读第 1–6 节；有第 7 节待决问题时，先请用户逐项决定，全部解决后再确认是否继续。同时报告新增或触发的 FOLLOW.UPS 项。

lint 有 FAIL 时，Agent 先修正，不发这份交付总结。

## 异常处理

- **用户要求跳过访谈**：Agent 列出已知与未知内容，使用 `Status: draft`，并在顶部说明哪些维度未访谈。跳过必须可见。
- **事实查不到**：Agent 在事实收集的待定问题中标 `未验证`，不凭常见做法填空，也不放进第 7 节。
- **预算用尽**：Agent 记录未读清单和受影响结论，并在回复中说明。Agent 不静默结束调查。
- **回答增加了范围**：Agent 不直接加进 R，先记入第 5 节或留待未来，由用户明确决定是否纳入。
- **需求实际包含两个目标**：Agent 说明拆分方式并等待确认。用户坚持合并时，额外条目必须带 `**范畴**` 并登记为「附带交付」。
- **用户还说不清需求**：Agent 可以只定义问题、不定义方案，但必须在草稿顶部说明不完整。
- **访谈达到上限**：Agent 停下，请用户在拆分和追加 `+4` 中选择。Agent 不把超额问题转移到第 7 节。
- **路线图未批准**：Agent 拒绝执行，说明该路线图的状态，不代替用户批准，也不先访谈再补状态。
- **需求超出切片定义**：Agent 停下，指出超出的是哪一条切片定义，交用户决定修订路线图还是另开 spec。Agent 不在本次需求里扩大范围。
- **没找到对应切片**：Agent 问用户这次需求是路线外增补，还是记错了编号。增补且不冲突时按增补处理；有冲突时停下修路线图。
- **lint 与内容判断冲突**：Agent 对照现行规则检查文档；怀疑校验有误时，暂停交付并向用户提出变更。用户明确确认前不改校验、不绕过 FAIL，也不把疑似错误当成已批准的例外。

## 下游契约（给 sdd-plan）

需求阶段必须提供以下材料，计划阶段才能避免猜测：

1. **R 列表**：编号稳定、行为可观察、每条有反例。计划阶段据此制定验收和测试。
2. **明确不做**：计划阶段据此限制范围，不能顺手添加功能。
3. **上游与影响范围**：计划阶段据此安排检查，确认已有行为没有被破坏；没有上游时写“无”。
4. **第 6 节决策**：plan 不得推翻。需要改变时，先回 spec 重新确认。
5. **第 7 节问题**：计划阶段遇到这些问题必须问用户，不能自行选择。
6. **附带交付**：头部 R# 与 `**范畴**` 必须对应。plan 应把产品代码与规范、文档或契约变更分成两组任务、两组验证，不能混在一个任务中。
7. **成本基线**：`grill.md` 成本字段记录本次问题数和工具用量，后续比较流程成本时以此为依据。

文件清单、接口签名、任务拆分、测试命令和验收脚本默认属于 `plan.md`。用户明确指定某项命令、测试行为或实现约束为必须满足的要求时，Agent 必须保留在 `spec.md`，由 plan 安排执行。
