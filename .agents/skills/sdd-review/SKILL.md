# sdd-review

## 职责与边界

本技能指导审查 Agent 核对一次交付的实际状态。需求说明（`spec.md`，简称 spec）定义用户要求；执行计划（`plan.md`，简称 plan）定义已确认方案、任务和检查安排。`R1` 等编号定位需求，`T1` 等编号定位任务。

审查 Agent 读取原文并直接作出判断，不另派核查者，不沿用实现阶段最后核查的执行者安排。实现阶段负责在独立子 Agent 中启动本技能；独立上下文的建立和启动属于 `sdd-impl`，不是本技能的步骤。

审查 Agent 只报告现状，不重复实现、测试或方案评审，不要求用户参与或确认结论。只读不等于转述交接说明：审查 Agent 必须核对实际成果，区分已知事实、能够支持的判断和无法核实的内容。

- 审查 Agent 只写目标 spec 目录下的 `review.md`，不修改代码、配置、spec、plan、任务勾选或其他被审查成果。
- 审查 Agent 不运行测试、构建、启动、格式化、静态扫描或任何 lint（格式和规则检查脚本），也不新增检查、截图、日志或证据归档要求。审查 Agent 可以使用读取、搜索和版本控制的只读命令核实文件与差异。
- 审查 Agent 不修复问题、不自动回滚、不修改上游以迁就实现，也不为通过审查降低要求。
- 审查 Agent 不重新选择方案，不以更安全、更通用或更完整为由新增需求、检查任务、产品能力或验证系统。
- 审查 Agent 不要求 Git 提交、批准 tag、专用批准凭据或额外实现记录。仓库没有版本控制也可以审查。

## 输入

审查 Agent 接收目标 spec 编号或目录，以及实现阶段提供的交接事实：

- spec 和 plan 的路径。
- 本次实际改动范围，包括完成任务所必需的辅助文件。
- 已执行与复用的检查结果、预期、适用依据，以及已知未完成事项。
- 人工验收的已有结果；本技能不再次请求用户操作或确认。

交接摘要可以来自启动本技能时传入的文本，不要求另建文件。摘要是待核实的输入，不是审查结论。已有 `review.md` 是上次审查记录，不自动证明当前状态。

## 开始前核对

1. 审查 Agent 读取 `AGENTS.md`、`steering.md`、本文件、目标 spec 和 plan，按索引读取直接相关的已生效规范。项目自述、README 和进度记录只作背景，不代替要求。需要理解决定时，审查 Agent 读取同目录 `grill.md` 的相关事实与决策，不据此推翻已批准 spec。
2. 审查 Agent 核对 spec 和 plan 均为 `approved`，spec 没有待用户决定的问题，plan 引用的 spec 编号和版本一致。状态字段不证明成果符合要求，也不要求另找批准凭据。
3. 审查 Agent 对照任务、交接范围和实际文件，确定本次成果及直接依赖。使用版本控制时，审查 Agent 区分本次改动与已有或其他任务的改动；未提交差异、最新提交和 plan 文件清单都不能单独代表本次范围。没有版本控制时，审查 Agent 依据交接范围、实际文件和调用关系核实，不虚构历史差异。
4. 审查 Agent 核对实现任务、检查任务和已有结果，区分完成、未完成、失败、未运行及无法核实。任务勾选只标识进度，不能单独证明检查通过。
5. 已有审查报告时，审查 Agent 先读原问题、原结论和本次修复交接，确定本轮是首次完整审查还是修复后的定向复核。

需求或计划未批准、版本不一致、关键材料缺失或改动范围无法确定时，审查 Agent 不猜测、不发起用户问答。审查 Agent 记录已经核实的事实、缺失内容和影响，生成受阻或不通过的报告后结束。已证实违反要求时不能仅写受阻；事实不全时也不能捏造确定错误。无法继续的项目写明未审查及原因，不将局部读取伪称完整审查。

## 核对实际成果

首次审查覆盖以下全部适用内容。审查 Agent 只沿本次改动及直接相关路径核实，不开展全仓库优化或重新排查所有历史问题。

### 1. 逐条核对需求

审查 Agent 从 spec 第 4 节的每条需求出发，找到实际实现或交付物，结合规定的条件、行为、结果、反例和可观察证据判断是否兑现。存在同名文件、类或测试，不等于满足需求。

每条需求记录实际落点、已有检查依据、判断及其限度。审查 Agent 区分代码阅读、文件内容、自动检查结果和用户验收，不把某一种依据包装成另一种。附带的规范、文档、数据或对外约定交付也须按对应需求核对，不能因产品代码完成就一并判为完成。

### 2. 核对方案、协作与边界

审查 Agent 核对实现是否落实 plan 的已确认方案、必要协作约定、任务职责和明确不碰范围，并遵守 spec 的明确不做与取舍。

plan 的已知影响文件不是封闭白名单。必要辅助文件、局部命名或编码方式不同，本身不构成偏离。审查 Agent 报告越界时，必须指出实际改变了哪项既定行为、依赖、边界或代价，不按类名、目录或设计模式推断。

审查 Agent 不重新判断用户选定的方案是否最优。只有实际冲突影响既定要求或任务履行时，才报告上游失效，不借审查补需求或补计划。

### 3. 核对具体缺陷与适用规范

审查 Agent 阅读实际成果及直接相关调用关系，核对输入输出、状态、错误处理、资源和依赖是否存在可说明触发条件及后果的错误。正确性、安全、性能、可维护性和架构只是观察角度，不各自生成额外验收要求。

审查 Agent 按现行规范的适用范围及 plan 已批准的例外核对成果。已接受的例外不能再列为缺陷；规范没有规定的偏好不能写成违规。规范中的命令不因此成为本阶段的执行任务。

审查 Agent 只报告有依据的发现，不把潜在写法、缺少某种设计模式、没有额外测试或存在更优方案当作确定缺陷。既有测试通过也不能抵消代码中已经证实的错误。

### 4. 核对已有检查结果

审查 Agent 逐项对照 plan 的检查任务及第 5 节安排，核对实际动作、范围、预期、结果和当前适用条件。旧 plan 将实现与检查写在同一任务时，审查 Agent 仍核对该检查，不凭勾选略过。

- 有适用的既有结果时，审查 Agent 引用来源和关键结果，不为获得独立视角重新执行。结果是否可复用按 `sdd-impl` 的规则核对；不能仅因结果来自其他执行者就拒绝。
- 检查失败、遗漏、结果失效或无法对应当前成果时，审查 Agent 如实记录，不代跑，不以任务勾选补齐结果。
- 人工验收引用实现阶段交接的用户确认或已有记录，不要求截图、原始日志或再次确认来证明用户确实确认过。只有勾选而没有可识别的结果时，审查 Agent 写明无法核实，不把它推断成用户未验收。
- plan 明确未安排检查时，审查 Agent 写明未安排，不因此要求补测试或阻止审查通过。已有事实足以核对要求时，可以作出符合结论，同时说明未获运行验证；要求本身仍无法核实时，审查 Agent 说明具体缺失，不把未安排检查直接等同于不符合。
- 已安排的检查没有完成，返回实现阶段。必须增加检查、改变方法或调整任务才能解决时，返回计划阶段；审查 Agent 不自行增加或修改安排。

## 发现怎样记录

审查 Agent 完成本轮能够执行的核对后，一次性整理完整发现，不在第一个问题后开始修复。确实无法继续的项目须标明范围和原因。

每个问题采用 [报告模板](templates/review.md) 的独立记录块，使用稳定编号 `Q1`、`Q2` 等。审查 Agent 合并同一根因的重复表现，分别记录事实、影响、级别、处理阶段和修正目标。修正目标说明必须恢复的要求，不预先替上游选择新方案，不展开完整实现。

问题级别：

- **必须解决**：已经证实违反既定要求、存在具体实现错误或计划内检查未满足。未解决时，审查不能通过。
- **轻微问题**：不影响行为、理解、执行和结论的笔误或排版。审查 Agent 可以保留在报告中，不因此判为不通过，也不为此启动修订或复核。
- **无法核实**：缺少关键事实，尚不能确定是否符合。审查 Agent 必须说明缺少什么及影响哪个判断，不能将怀疑写成确定缺陷。影响通过判断时，结论为受阻；同时存在已证实问题时，按不通过报告，并列出核实限制。

每个发现须引用路径、行号或可定位的段落，以及必要原文或关键输出。交接文本没有文件行号时，引用对应检查任务及结果摘要，不虚构路径。缺失项须引用产生该要求的依据和已核对的位置。与要求无关的优化偏好不进入必须解决清单。

## 返回哪个阶段

审查 Agent 按解决问题实际需要改变的内容确定处理阶段，不按问题名称或严重程度机械分类：

- **`sdd-requirement`**：必须改变 spec 的行为、边界、取舍或验收要求。
- **`sdd-plan`**：需求不变，但必须改变方案、设计、必要协作约定、任务或检查安排。
- **`sdd-impl`**：需求和计划不变，只需修正实现、补齐交接事实或完成原有检查。

实现偏离正确的 plan，通常应回实现阶段，不能为了接受现状而改计划。计划已经违反需求时，应报告计划失效，不能只要求实现者照错计划继续做。审查 Agent 不为缺少历史输出要求新增证据归档。

多个问题涉及不同阶段时，审查 Agent 保留各项处理阶段，并在最终结论中报告最靠前的失效阶段，顺序为需求、计划、实现。纯属本轮读取失败而尚不能定位责任阶段时，审查 Agent 写明返回阶段无法确定及缺失条件，不猜测上游失效。

## 报告、结论与结束

审查 Agent 按 [templates/review.md](templates/review.md) 在目标 spec 目录生成 `review.md`。正文用中文，路径、标识符和命令保持原样。报告不用表格，使用固定字段和独立记录块。Agent 写清谁做什么，一句话说一件事；首次出现术语时解释含义，不用编号代替意思。

结论只有三种：

- **通过**：本轮适用范围已核对，每条需求有支持符合判断的依据，没有未解决的必须解决问题或影响通过判断的无法核实项，计划内检查均有满足预期且仍适用的结果。未安排检查及轻微问题如实保留，不宣称绝无缺陷。
- **不通过**：存在已证实的必须解决问题。报告完整问题及返回阶段；同时存在无法核实内容时，一并说明。
- **受阻**：没有足以确定不通过的问题，但关键事实或审查条件不足，不能作出通过判断。报告缺失内容、影响及能够确定的处理阶段。

审查 Agent 不使用基本通过、有条件通过等模糊结论，不改 spec 或 plan 的状态来表示完成，也不靠补勾任务制造一致。只有审查通过，才能宣称该 spec 完成。

修复后再次审查时，审查 Agent 读取现有报告，保留原问题编号，逐项写明已解决、未解决或无法核实及依据。审查 Agent 只复核原问题、修复的直接影响和因此失效的既有结果，不默认全量重审。偶然发现新的明确问题时可以记录，但不借此扩大为无关重审。需求、方案或改动范围发生实质变化，定向复核已不足以判断时，审查 Agent 说明需要完整审查的范围及原因；未经审查部分不能沿用通过结论。

本轮报告须完整描述当前状态，不仅保留修改说明。既有报告中的未解决问题和仍适用结论不能在更新时静默消失；结论失效时写明原因。本技能不要求另建审查轮次文件或原始输出档案。

报告完成后，审查 Agent 返回实际成果的一句话总结、审查范围、最终结论、各级别问题数量、报告位置，以及不通过或受阻时的返回阶段与原因。Agent 如实说明本阶段没有执行测试或其他检查命令，引用的是已有结果。

审查 Agent 随后结束，不请求用户确认，不启动修复、不重启实现、不自动进入下一个 spec，也不建立内部修改与复核循环。需要用户改变需求、方案或授权的事项只写入报告，留给返回后的阶段处理。
