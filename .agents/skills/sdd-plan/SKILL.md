# sdd-plan

## 职责与边界

本技能把已批准的 `spec.md`（需求说明）变成 `plan.md`（执行计划）。需求中的 `R1`、`R2` 是逐条需求编号。用户决定需求和方案，主 Agent 编写计划，独立核查者只读检查。

服务方向是单向的：方案确认（A）为已批准的 spec 服务，开工确认（B）为 A 已确认的方案服务，并将每条需求落实到任务和验收。主 Agent 只说明怎样满足上游，不替上游查漏补缺，不补需求、不另造方案，也不把验收升级为更强的保证。已确认的适用规范仍须遵守，但不能从规范名称或实现术语推导出未规定的要求。

计划分两次确认，不能合并：

- **方案确认（A）**：Agent 只写第 1–2 节，完成检查后请用户接受或修改方案。用户同意后才能写第 3–6 节。
- **开工确认（B）**：Agent 写设计与任务，完成检查后请用户决定是否实现。用户明确允许后才能将状态改为 `approved`。

主 Agent 在每次确认中最多编写一轮、修改两轮，并安排三次独立核查。达到上限时，主 Agent 必须停止，由用户决定下一步。主 Agent 在中断后继续处理时须保留轮次，不因更换会话自动清零。主 Agent 在对话中保留阶段、轮次及问题清单：A 停止时在回复中给出，B 同时在第 6 节记录。恢复工作时，主 Agent 先读取这些结果。

### 阶段内部连续执行

用户明确启动当前阶段后，主 Agent 自动连续执行该阶段内的编写、自检、lint、独立核查、范围内修订和定向复核，无需用户逐步确认。主 Agent 可以发送进度说明，但不得把“开始独立核查”“继续修订”“等待核查结果”变成用户确认问题，也不得用用户问答、确认按钮或结束回复等待用户说“继续”的方式暂停内部流程。

需要等待后台核查时，主 Agent 使用运行环境的完成通知、阻塞等待或结果获取方式，不把等待责任转给用户。只有用户需要作出方案确认或开工决定，或出现本技能规定的停止条件、缺少必须由用户决定的信息时，主 Agent 才暂停并提问。内部步骤无需确认不等于允许跳过 A、B 的用户批准或超出核查与修改上限。

B 的流程可以表述为：

```
主会话编写完整计划 → lint
  → 第一次独立核查
  → 必要时修改 → 第二次独立核查
  → 必要时修改 → 第三次独立核查
  → 停止，向用户报告结果
```

本技能不改 `spec.md` 或 `grill.md`，不写实现代码，不运行项目构建、测试或启动命令，不规划实现后的审查报告、命令输出或证据归档文件。计划只说明怎样实现、怎样验证以及预期结果。项目排期不属于本技能。

### 开工确认的冻结边界

进入 B 后，Agent 不得修改 `spec.md`，也不得修改 A 已确认的 plan 第 1–2 节，连排版或勘误也不在 B 中处理。主 Agent 与核查者都只能依据已确认方案和 spec 第 4 节制定、核查设计与任务，同时遵守需求的边界、取舍及第 2 节确定的规范范围。

Agent 可以细化文件、接口、任务与验证命令，不能新增功能、交付物、验收要求，或改变技术路线和已接受的代价。例如，未在需求或已确认方案中确定的截图交付要求，不能在 B 中追加。发现适用的明确要求确实无法同时满足，或必须改变上游才能完成任务时，Agent 报告依据并停止，交用户决定返回哪个阶段；不得自行改写上游来消除冲突。Agent 不凭类名、目录或设计模式反推新增功能或方案变化，须指出实际改变了哪项已确认行为、依赖、边界或代价。

## 计划深度的停止线

本技能以已批准需求为依据，固定方案、协作边界、任务和验收条件，不把计划写成文字版代码。方案确认（A）决定技术路线、职责划分、主要数据流、边界与代价；开工确认（B）把已确认方案细化为可以按顺序执行和验证的任务。需求仍由 spec 定义，计划不得重新定义需求。

- 主 Agent 详细说明跨文件或跨任务协作：谁提供数据、谁使用数据、共享数据的含义、状态如何传递，以及必要的输入输出约定。签名或具体结构只有影响协作、兼容性或既定验收时才需要固定。
- 主 Agent 为任务写清前置产物、改动职责、依赖与验收依据。执行某个任务及其验证时，所需文件、类型、数据与入口必须已存在，或由该任务、前序依赖任务提供。
- 主 Agent 开始讨论具体函数、变量、参数、枚举值、构造写法或组件嵌套时，先判断是否已进入编码阶段。除上游明确限定或跨任务协作必须固定的约定外，主 Agent 不在计划中决定这些内容，也不为它们建立选择与放弃记录。主 Agent 可以说明所需信息和状态含义，不必预写代码声明；具体表达由实现阶段的 Agent 决定。
- 主 Agent 不为搜索断言、凑决策记录或假设将来复用而拆文件。文件拆分应有职责、依赖边界或现行规范依据；局部实现选择不单独包装成方案决策，已确认决定不重复展开选择与放弃。
- 主 Agent 在风险中写清失败信号、处理边界、停止条件与撤回办法，不要求预先设计第二套实现。若承诺备用实现，主 Agent 必须说明它如何保持原有协作约定和验收条件，不能以“等价替换”代替依据。

判断是否写到这里为止：实现阶段的 Agent 能否在不改变需求、方案、协作约定和验收条件的前提下自行选择写法？能够自行选择的局部写法，主 Agent 不再提前冻结。发现已有设计过细时，主 Agent 应删去无必要的限制，而不是补齐更多编码细节。

## 写作与格式

- Agent 应先让人读懂全文，再考虑 Agent 如何执行。Agent 在持久文档中用“用户”“Agent”“系统”明确责任，一句话说一件事。每份文档首次出现术语或阶段代号时，Agent 写出完整名称并解释用途；后文可以使用简称。相隔较远时可以再次使用全称，不要求每处重复。
- 正文用中文，路径、标识符、命令保持原样。例子用导入文件、生成报告等通用场景，不绑定特定项目、业务或框架。
- 文档不用表格。头部用 `- 字段：值`；同类记录用 `#### 记录标题` 分块，块内每个字段独立成行。字段名按模板固定，不重复，不把命令里的 `|` 当结构分隔符。
- 默认做法写清即可，不为凑决策记录虚构备选方案。需要用户选择的事项才写选项、放弃项和理由。

## 输入与前置校验

每次使用时，主 Agent 先读 `AGENTS.md`、`steering.md` 和本文件，再读取目标 spec。lint 是检查格式和部分规则的脚本；独立核查则由未参与写作的新 Agent 或新会话判断内容是否一致。

1. 主 Agent 检查 spec 的 `Status` 是否为 `approved`，第 7 节是否还有待用户决定的问题。不满足条件时，主 Agent 停止并回到需求阶段。
2. 主 Agent 读取 `grill.md` 的“事实收集”和“决策”，不重复调查已有可靠事实。
3. 已有计划时，主 Agent 保留已确认内容，只处理本次允许修改的部分。spec 实质变化后，主 Agent 将计划标为 `stale`，先解决上游批准问题。
4. 主 Agent 在头部记录 spec 编号和版本：`- Spec：` 后接反引号包裹的编号，以及 `（spec vN / approved）`。不使用 tag、commit 或专用批准凭据。

## 阶段 1：预研与约束

主 Agent 先扫描索引，决定哪些规范、源码、依赖和配置与本次有关，再读取原文。项目自述、README 和进度记录只作背景，不作为约束。

预研工具预算：`new` 14 次（扫描最多 6 次，精读 8 次起步）；`extend` 18 次（6 / 12）；`fix` 10 次（4 / 6）。扫描余额可以用于精读，反过来不行。主 Agent 无法读完必要材料时，报告未读内容及受影响的判断，不假装已经核实。

约束来自已生效规范、spec 第 4/6 节及需求访谈决定。Agent 按用途分开：

- 第 2.1 节列需要用户确认的例外：`覆盖`、`仅本次`、`回 spec`、`先补约定`。没有例外写“无”。
- 第 2.2 节列照做的既有规范，按主题合并，给出处、条款及适用范围。
- 需要改变需求，标 `回 spec` 并停止。影响后续所有 spec 却没有标准，标 `先补约定` 并中断本 spec。

技术做法按本次实现特例、spec 约束、长期规范的顺序处理。覆盖通用做法是允许的，但只能在 A 中提出并经用户确认：写明文档、条款、理由和可判断的失效条件。不能覆盖需求行为或 spec 第 6 节取舍。第 2.2 节引用被部分覆盖的条款时，明确仅沿用哪部分，不能又整体引用。

主 Agent 在 B 中发现遗漏的规范冲突时停止，不自行增加覆盖项，也不自行缩窄规范来绕过冲突。

## 阶段 2：设计访谈

主 Agent 按 [rules/dimensions.md](rules/dimensions.md) 选择确实需要用户决定的问题，一次一问。这里的“维度”是需要检查的一类设计问题。主 Agent 给出具体选项和后果，可以推荐实现方式，但必须说明代价。

- 答案只能收窄做法，不能新增用户可见行为。新增需求回需求阶段。
- 主 Agent 在访谈时不写文档，先与用户形成决定，再整理方案。
- 问题上限为 `new` 8、`extend` 7、`fix` 6。达到上限仍有问题，请用户决定拆分或追加 `+4`，最多追加两次。
- spec 已确定或没有选择空间的维度不重复询问，说明不问的原因。不要求为机械命名等默认做法编造取舍。
- A 中把影响方案的决定写入第 1–2 节；B 只能在第 3.2 节展开这些决定的实现细节，不重新决策。

## 阶段 3：方案摘要与方案确认（A）

主 Agent 使用 [templates/plan.md](templates/plan.md)，只写第 1–2 节，将 Status 保持为 `draft`，让第 3–6 节为空。

第 1 节说明：用户会看到的变化、怎么做到、为什么这么切、代价。摘要正文最多 30 行，“覆盖核对”记录不计入。用户可见结果按状态或主题分条，不用文件名、类名或维度 ID 代替结果；需求本身讨论这些对象时除外。

- “需要用户决定的事项”给出具体问题和选项，或直接指向 2.1；无需决定时明确说明。
- “覆盖核对”逐条对应 spec 第 4 节的 R。`落点` 照抄可见变化中的 6–20 字；纯内部要求写“无 —— 见「X」段”，不把内部检查硬塞进用户画面。
- 第 2 节按例外与既有规范分开，每条一个主题，理由一句话，首次缩写写明含义。

主 Agent 完成自检和首次 lint 后，按下文“有限核查循环”执行。V1–V8 是核查规则中八项检查内容的编号。核查者在 A 中只检查 V1–V5；`new` / `extend` 必须核查，`fix` 可以说明理由后跳过。结果放在回复，不写入第 3–6 节。

独立核查按规则通过或允许跳过，且所需 lint 通过后，主 Agent 请用户决定是否接受方案。用户明确同意后，主 Agent 才将 Status 改为 `design-ok`。`design-ok` 只表示 A 已确认，不代表完整计划已就绪。

## 阶段 4：设计与任务及开工确认（B）

主 Agent 先确认冻结边界，再一次写完第 3–6 节，不重新访谈或改写第 1–2 节。

1. **第 3 节设计**：结构与数据流、已定方案的细化决策、影响文件和不碰范围。3.3 是实现时允许修改的文件清单，每个文件一个职责。
2. **第 4 节任务**：标题采用 `- [ ] **T1** ...`，下设 `改动`、`验证`、`覆盖`、`依赖` 四行。勾选仅表示续做位置，不证明任务完成。创建目录、依赖和入口等前置工作也须安排任务。
3. **第 5 节验证**：每条 R 一个记录，写对应任务、自动验证和手工步骤。写清命令或检查动作及预期，不只写“成功”。不能自动证明的要求给出手工方法。
4. **第 6 节风险与回滚**：风险、触发信号、应对分别成行。说明撤销哪些文件、保留哪些产物，不假设依赖版本控制。记录本轮核查次数、结果和遗留问题。

任务依赖只能指向前面的任务。手工检查须有数据及准备方法、实际入口、环境、操作和预期；测试夹具不是桌面入口的数据。无法从允许入口到达的手工状态，要在现有方案内找到验证方法；需要新增功能或改变方案才能验证时停止。验证方法不承担新增交付要求的职责。

主 Agent 只为已确认的验收条件安排必要检查：用户可观察行为用测试或手工检查，输入来源和依赖边界可通过调用关系、代码检查和替换输入核对。若要求报告内容来自传入记录而非远程查询，计划只需安排核对输入路径及替换记录后的输出，不自行建设网络监控器、流量审计或通用验证框架。用户明确要求的监控或审计除外。证据只能支持其实际检查的结论；证据有限不自动意味着应增加验证系统，也不意味着可以声称更强保证。

若符合需求的实现也会被断言拒绝，主 Agent 应修正验证方法，不通过改名、拆文件或隐藏关键词迁就断言。项目规范明确要求的检查仍须执行。只有适用的明确要求确实无法同时满足，或完成任务必须改变已确认方案时，主 Agent 才按冻结边界停止；存在另一种写法、术语解释或潜在疑虑，不足以要求返回上游。

所有改动路径在 3.3 逐个用反引号标记，采用仓库相对 POSIX 路径（用 `/` 分隔目录）。任务采用相同路径，不支持目录、通配符或绝对路径。根文件、点文件、空格、Unicode 和无扩展文件同等处理。

主 Agent 完成首次 lint 后，按有限核查循环执行 V1–V8。首轮必须完整核查，后续只复核问题及修订影响。核查者不能改文件、跑 lint 或另开核查任务。

## 有限核查循环（A、B 分别执行）

lint 是机械校验，不需要独立视角。只有主 Agent 运行：

```bash
python3 .agents/skills/sdd-plan/tools/plan_lint.py specs/pNN-NNN-<slug>
```

退出码 `0` 通过、`1` 有失败、`2` 用法错误或文件缺失。它不证明语义正确或用户已批准。

1. 主 Agent 编写本阶段完整内容，自检后运行首次 lint。格式错误在本次编写内修正，不提交半成品核查；相同错误修复无进展时停止报告，不原样重复。疑似校验规则错误也停止，不能改脚本或绕过失败。
2. lint 通过后，主 Agent 冻结当前稿，交独立上下文核查。核查期间不继续修改。核查者完成全部检查后一次提交完整问题清单和最终结论，并结束本轮任务；中间消息不能作为通过依据。主 Agent 只有收到正式完成结果后，才能记录结论、标记核查任务完成或安排修订；结果不完整时请求补齐，不自行推断通过。后台核查支持完成通知时，主 Agent 完成必要的冻结边界核对后等待通知，不反复查询状态、差异或环境版本。没有完成通知时，主 Agent 使用阻塞等待或结果获取方式；任务异常时才定向检查。核查规则见 [rules/crosscheck.md](rules/crosscheck.md)。
3. 核查报告存在阻塞问题，或包含必须改变需求、已确认方案才能解决的问题时，主 Agent 立即停止，交用户决定，不自行改上游。没有阻塞且所有一般问题均已修复并核查通过时，主 Agent 结束独立核查；轻微问题可以处理或忽略，不因此再开一轮。
4. 没有阻塞但存在一般问题时，B 的主 Agent 必须在剩余修改轮次内修复，再安排定向复核。一般问题限于“仅设计与任务”的内部问题，不是可选优化。A 发现需求或方案问题即停止；三次是上限，不是必须用满的轮数，用户允许修正后继续时仍累计原轮次。修改前核对旧内容和拟改内容，不执行空替换；失败后读取工具反馈，不原样重试。
5. 主 Agent 修复问题时，同时检查该改动直接关联的设计、文件清单、任务前置条件、验证数据与风险记录，不只修改核查者引用的句子。例如，数据提供位置变化时，主 Agent 同时核对创建任务、使用任务及其验证；布局变化时，主 Agent 同时核对受影响状态和布局验收。主 Agent 不借此全量重写无关内容。主 Agent 修改后不运行 lint，而是将计划交给下一位独立核查者定向复核。主 Agent 在输入中提供上轮完整问题清单及稳定编号、逐项处理结果、本轮改动位置及连带影响。主 Agent 最多安排三次核查，不得自动追加第四次。
6. 首次核查通过且正文未改时，主 Agent 沿用首次 lint 结果。在 B 中，主 Agent 只填入核查记录时不必重复运行 lint；记录以外有修订时，主 Agent 在核查通过后先记录结果，再运行最终 lint。核查者不运行任何 lint。
7. 第三次核查返回后，主 Agent 不论结果如何都停止自动修改。核查通过时，主 Agent 仅补充核查记录，并在此前有正文修订时运行最终 lint。第三次核查仍有阻塞或一般问题未解决时，主 Agent 记录未解决的问题，不再修补或运行最终 lint，也不得宣称核查通过。最终 lint 失败时，主 Agent 也停止，不开启新循环。

问题级别决定处理方式：“阻塞”须停止并交用户决定；“一般问题”是 B 内部必须修复并再次核查的问题；“轻微问题”可以处理或忽略，不因此再次核查。问题性质为“需求”“方案”“仅设计与任务”。定义和输出字段见核查规则。核查通过要求没有阻塞，且所有一般问题均已修复并核查通过。未通过时允许报告当前草稿与失败情况，但不得宣称计划就绪或请用户直接批准实现。

## 收尾与用户决定

- A 的独立核查按规则通过或允许跳过，且 lint 通过：请用户确认方案。未批准不写后半段。
- B 无阻塞、所有一般问题均已修复并核查通过，且所需 lint 通过：保持 `design-ok`，请用户决定是否进入实现。用户明确允许后才改为 `approved`。
- 达上限、上游存疑、事实无法核实或 lint 失败：报告停止原因、轮次和遗留问题，请用户决定返回上游或继续修订。未完成、未核查通过或未批准时不进入实现。
- 用户要求继续修改时，以原问题清单为起点，只有用户明确允许才追加轮次。用户要改需求或方案时，明确退出 B，回相应阶段重新确认，不在 B 中直接修改冻结内容。

主 Agent 在交付回复中先说明做完会看到什么，再说明当前状态、任务与 R 数、lint 结果、核查轮次及遗留问题，最后明确请用户决定什么。主 Agent 将未运行的检查写为“未运行”，如实列出一般问题和轻微问题，不伪写“无缺口”。

## 下游契约

计划提供任务清单、允许修改的文件、验证方法及预期、不碰范围、风险与回滚。实际执行及验证留给实现阶段。实现需要改变需求或方案时返回对应阶段；需要扩展文件范围时先修订计划，不能顺手增加。
