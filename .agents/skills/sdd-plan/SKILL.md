# sdd-plan

## 它解决什么问题

先说明几个名称：

- `spec.md` 是需求说明，`R1`、`R2` 等是逐条需求的编号。
- `plan.md` 是执行计划。
- 持久文档正文用「用户」「Agent」「系统」明确角色，不使用指代不明的「你」「我」「自己」。用户作决定，Agent 编写计划、检查并执行，系统提供运行时行为；直接对话和原文引语可保留人称。
- lint 是检查格式和部分内容的脚本，不能代替人工判断。
- 「独立上下文」指没参与写作的新 Agent 或新会话。核查者只读收到的材料，不靠作者的想法补读文档没写出的内容。

计划阶段的两类失败，成因和需求阶段不一样：

- **方案没被想过就被拆成任务**：照着模板把「架构」「数据模型」「错误处理」填满，每节都写了，但没有任何一处是"在两个可行做法里选了哪一个"。这种 plan 读起来完整，执行时处处要临时决定。
- **设计在半路改了需求**：为了绕开某个约束，顺手加了 spec 里没有的行为；或者用户的技术取向（用哪个组件库、多紧凑）只活在这次对话里，下个 spec 又要重说一遍。

所以这里做三件事，顺序不能换：

1. **按需加载**：先扫 `steering.md` 索引判断哪些规范和代码需要读，再精读。正式项目的规范目录很大，全量读会把预算烧在无关条款上。
2. **访谈式设计**：把 spec 装不下的取向问出来——密度、结构归属、失败呈现、选型。一次一问，层层递进，而不是先写一份长设计再让人从头审。
3. **两段交付**：先只写方案摘要，用户确认后 Agent 才写设计与任务。用户的注意力只花在"走哪条路"上，不花在核对任务清单。

**整份 `plan.md` 都必须让人读懂。** 第 1–2 节帮助用户选择方案，第 3–6 节重点指导 Agent 执行。重点不同，不代表执行部分可以只堆术语。每段都要写清谁做什么、怎样判断完成。一句话说一件事，条件多就拆句或列项，不写没有主语的长句。编号只帮助定位，不能代替意思；第一次使用术语时给出解释。

计划有两次确认，Agent 必须先检查，再请用户决定：

- **方案确认（A）**：完成第 1–2 节，先跑 lint，再按类型完成独立核查。用户明确同意后，才写第 3–6 节。`fix` 可跳过这次独立核查，但必须说明理由。
- **开工确认（B）**：整份计划写完后，所有类型都必须完成独立核查、记录结果并重跑 lint。用户明确允许后，才进入实现。

独立核查在下文也称「对证」：由没参与写作的新上下文，对照需求、计划和必要事实检查是否一致。lint 只检查格式和部分内容，不能代替核查或用户批准。

## 在流程里的位置

```text
sdd-grill   →  spec.md（approved） + grill.md
     ↓
sdd-plan    →  plan.md               方案摘要经用户确认；plan_lint 退出码 0
     ↓
sdd-impl    →  代码 + 测试 + 证据
     ↓
sdd-review  →  review.md
```

本 skill 只负责第二格。上游契约见 `sdd-grill` 的「下游契约」；本 skill 自己的下游契约见文末。

## 边界

**负责**：前置校验、预研与按需加载、约束收集、设计访谈、方案摘要、设计、任务拆分、`R → 验证` 映射、`R → 可见句` 核对、自检与 `plan_lint.py`、lint 之后的 spec/plan 对证。

**不做**：

- 不改需求。访谈答案只能**收窄**实现，不能新增 spec 未定义的、用户可见的行为。
- 不写 `spec.md` / `grill.md`。要改需求就停下，回 `sdd-grill`。
- 不写实现代码，不跑项目的构建、测试或启动命令（那是 `sdd-impl`）。`Bash` 仅用于计划校验命令，`Agent` 仅用于独立上下文的只读对证；不得借此执行项目构建、测试或实现。
- 不生成 `research.md` / `design.md` / `tasks.md` 这类中间文档。研究结论进第 2 节，设计进第 3 节，任务进第 4 节——三处写必然漂移。
- 不做项目级排期：多个 spec 之间怎么排，不是这一层的事。

**七条硬规则**：

1. **需求不许在 plan 里变形。** 访谈中出现"顺便也让它……"就停：那是一条新 R，回 `sdd-grill`。
2. **先摘要，后设计。** 第 1–2 节没经用户确认，Agent 不写第 3–6 节。这条靠 Status 机检：`draft` 状态下第 3–6 节必须为空。
3. **按需加载。** 先扫索引再读原文；跳过了高相关文档，必须在第 6 节写一行"未读 → 哪条决策未验证"。
4. **越具体越优先，但行为不许被覆盖。** 技术手段上：本次实现特例 > 本 spec 的约束 > 项目长期规范。用更具体的来源覆盖更一般的来源是**正常做法**，但必须在第 2.1 节标 `覆盖`、写清覆盖了哪一条，并在第 3.2 节给出理由与失效条件。可以覆盖的是做法（用什么库、放哪层、怎么验），不是 spec 定义的可见行为与第 6 节决策。
5. **长效约定不许只活在 plan 里。** 已有标准照做；缺标准就先补约定并**中断本 spec**；局部约定回 spec 或标 `仅本次`。
6. **验证以命令为准。** 每个任务有可执行命令与预期结果；不能自动验证的写 `手工：` + 步骤，由 `sdd-impl` 在实现阶段实际执行一次。
7. **全文让人读懂。** 第 1–2 节帮助用户选方案，第 3–6 节把做法、验证与撤回步骤说清。检查时不能只凭「读起来顺」：
   - 第 1 节开头是「用户会看到的变化」——用户视角的画面，读完能说出"就是个 XXX"，而不是结构分解。
   - 描述同一件事只用一个名字。术语第一次出现给解释，例如「分片处理（把大文件分成小批次依次处理）」。
   - 一条约束一句话。写不进一句话，说明它其实是两条，或者属于第 3 节。
   - 第 2 节只把**需要用户决定的例外**放前面（2.1），Agent 遵循的既有规范放后面（2.2）。用户的阅读量和需要作出的决定数成正比。
   - 写完自检：把第 1 节读给没参与访谈的人听，他能复述出要做什么，才算过。

## 输入

- `specs/pNN-NNN-<slug>/spec.md`：必须 `Status: approved`，第 7 节无待决项。
- 同目录 `grill.md`：**只读两节**——「事实收集」（已有 file:line 事实，省掉重复调查）与「决策」（被放弃的选项与理由）。成本表、覆盖矩阵与 plan 无关。
- `steering.md`：知识索引。**先读它，不要先读 `docs/`。**
- 按索引加载的规范、设计与技术专题；依赖白名单、目录归属这类条款通常写在代码规范里，是选型冲突的高发处。
- 既有代码：相似实现、可复用件、依赖清单与构建配置的现状。

**什么不算约束**：项目自述、README、进度记录、对话里提到过的文档，都不构成约束，不进第 2 节。约束只有三种来源——已生效的规范文档、spec 第 4/6 节、`grill.md` 的决策。

## 阶段 0：前置校验

三件事，任一不过就停，不产出文件：

| 检查 | 不过怎么办 |
|---|---|
| `spec.md` 的 `Status` 是 `approved` | 停，说明当前状态，回 `sdd-grill` |
| spec 第 7 节没有需要用户决定的编号项 | 停，把问题原文摆出来，等 `sdd-grill` 解决 |
| 同目录没有 `plan.md`，或已有 `plan.md` 是 `stale` | 已有且非 stale 时进入合并模式：保留已确认的第 1–2 节，只重写受影响的部分 |

`spec.md` 的 `版本` 要记进 plan 头部（`（spec vN / approved）`）。spec 一改，plan 就是 `stale`。

## 阶段 1：预研（扫描，不精读）

**目标是决定读什么，不是读懂什么。** 输出一张清单，不落盘。

1. 打开 `steering.md`，逐行看索引表：哪些文档与本次触碰面相关？「状态」是「待建」的直接划掉。
2. 用 Glob/Grep 定位本次会改到的目录与相似实现（源码目录、测试目录、依赖清单、构建与配置文件）。
3. 产出**待加载清单**：

```text
必读（影响选型或结构）
- docs/standards/coding.md  → 依赖白名单、文件头、层归属
- src/jobs/import_runner    → 既有批量任务入口，判断复用还是另写

选读（只在触发条件下读）
- docs/design/architecture.md → 若要新增一层，才看分层约定

不读（说明理由）
- docs/standards/testing.md（待建）
```

4. 预算：`new` 14 次工具调用（扫描 ≤6 / 精读 ≤8 起步）、`extend` 18（6 / 12）、`fix` 10（4 / 6）。

**先扫完索引，再读第一份原文。** 扫描没用完的次数可以转给精读，精读次数不能转给扫描。这样既保证先找全相关文档，也能把剩余次数用于必要阅读。精读次数用完仍不够，优先合并同源文档的读取，不要跳过应读内容；确实读不完，按「预研预算用尽」写进第 6 节。

## 阶段 2：约束与事实

按清单精读，产出第 2 节。**先分拣，再落笔。** 分拣标准不是约束来自哪里，而是**谁需要看它**：

| 约束 | 例子 | 写到哪 |
|---|---|---|
| 做法与现有规范不同，或只对本 spec 成立 | 这次不用规定的组件库；这套装配不推广成通用件 | `2.1 需要用户确认的例外`，一条一个决定 |
| 既有规范，照做即可 | 文件头三行、分层与依赖方向、单文件 250 行 | `2.2 Agent 遵循的既有规范`，按主题合并，用户可以跳读 |
| 属于需求但 spec 没写 | 访谈里冒出来的新可见行为 | `2.1` 标 `回 spec`，停下 |
| 长效约定，但还没有标准文档 | 「以后所有列表页都用这套列定义」 | `2.1` 标 `先补约定`，**中断本 spec** |
| 谁都说过、但没写下来，且只影响本次 | 用户这次口头说的「产物用 TSV」 | `2.1` 标 `仅本次`，理由写清 |

分拣错了的后果是不对称的：既有规范错放 2.1，用户多读几行，会开始跳过整节；需要用户决定的例外错放 2.2，用户根本没看见，闸门漏掉一次覆盖。

### 冲突按层解决，不要绕

三层，越具体越优先：

| 层 | 出处 | 能覆盖谁 | 不能覆盖谁 |
|---|---|---|---|
| 实现层 | `plan.md` 第 2/3.2 节 | 项目规范 | spec 的 R 与第 6 节决策 |
| 需求层 | `spec.md` 第 4/6 节 | 项目规范 | — |
| 项目层 | `docs/standards/*` | — | 上两层 |

**覆盖是正常做法，绕开才是有害的做法。** 通用规范写的是"一般情况"，具体 spec 写了"这次例外"，本来就该以具体为准。区别在于有没有留痕：

1. 第 2.1 节该行写明覆盖了哪一条：`覆盖 docs/standards/report.md REPORT-01`。
2. 第 3.2 节必须有一条决策，`来源` 列填 `覆盖`，写清理由与「何时重评」。
3. 失效条件要可判断：写"本 spec 结束后回到标准"或"下个 spec 需要同类控件时重议"，不写"以后再看"。

反方向不允许：plan 想推翻 spec 定义的可见行为或第 6 节决策，那是改需求，回 `sdd-grill`。一条约束既没标 `覆盖`、又没标 `仅本次`，却在设计里被丢掉了——这不是覆盖，是漏读。

### 口头约定必须落盘

影响面决定去处：

- 影响所有后续 spec（组件库、密度规范、命名）→ `先补约定`：**中断本 spec**，输出一句"需要先补 `<docs/standards/xxx.md>`（或改某条白名单）"，停。补完再回来重跑阶段 2。
  另开一次 `sdd-grill` 或单开会话都可以，但不要在本 spec 里边做边补——那会把两个变更搅成一次 diff。
- 只影响本 spec（某个接口的分层归属、一次性的目录安排）→ 记在第 2.1 节，标 `仅本次`，并在第 3.2 节写理由。
- 实际上改了需求（新增可见行为、放宽边界）→ `回 spec`：停，等 spec 升版。

## 阶段 3：设计访谈

按 [rules/dimensions.md](rules/dimensions.md) 推进，**一次一问**，问题格式：

```text
Q: 失败的行怎么处理？
   推荐 A：整批失败并回滚，报错带行号
   A. 整批失败 —— 结果可预期，但一行脏数据阻断全部
   B. 跳过并写入错误报告 —— 能继续，但要多产出一个文件
```

- **plan 的问答允许给推荐**（spec 访谈里"范围/成本/不可逆不给推荐"的规则不适用于实现方式），但推荐必须写明代价。
- 答案只能是**收窄**：在两个可行做法里选一个，或确认某个取值。出现"再加一个功能"就回阶段 2 的判定。
- 每个答案进第 3.2 节决策表：`选择` / `放弃` / `理由` / `来源`（维度 ID，或覆盖规范时填 `覆盖`）。**写不出"放弃"的，说明它本来就不需要问。**
- 上限：`new` 8、`extend` 7、`fix` 6（候选维度数 + 2）。撞上限就停下问用户：拆，还是追加 `+4`（最多两次）。
- **候选维度不是每个都得问。** spec 已经定死、或仓库里没有既有实现的，问了只是占用户的注意力。不问的维度在第 3.2 节记一行原因；没记原因的空缺按漏问处理。

**访谈期间不写文档。** 与 `sdd-grill` 同一条：一旦开始起草第 3 节，提问就会停。

## 阶段 4：方案摘要 + 方案确认

落笔前先答一句话：**这次做完，用户打开会看到什么变化？**

答不出来，说明方案还没成形——回阶段 3 继续问，不要用"结构上更合理"来替代这句话。这句话就是第 1 节的第一段，也是交付时 Agent 回复的第一句。

只写第 1、2 节，然后**停**：

1. 第 1 节四段：用户会看到的变化 / 怎么做到 / 为什么这么切 / 代价。≤ 30 行。
   - 「用户会看到的变化」用用户视角：看到什么、点什么、发生什么。不提文件名、类名、模块名、维度 ID，除非 spec 本身就是讨论如何编写文件、类或模块。
   - 这一段写成 `- ` 列表，一态或一主题一条，别写成一整段：Markdown 会把相邻行并成一段，源码分了行、人看到的是一整块。
   - 「为什么这么切」跟被放弃的做法比，写具体后果（"Agent 要单独实现表头点击处理"），不写"更清晰""更灵活"。
   - 「代价」要包括哪部分测不到、只能人眼看。
2. 第 1 节末尾列「需要用户决定的事项」：1–3 条，每条带 `维度：<ID>`。每条必须是**问题**（给出两个可选动作），或者一句指向 2.1 的指针；写成「确认……。」的结论句时，用户只有"同意"一个动作，闸门退化成确认框。没有需要拍板的就写「无需用户决定」，2.1 有条目时就写「需要用户决定的事项：见 2.1」，别换一套措辞把 2.1 复述一遍。**在方案摘要中，维度 ID 只用作拍板项的标签**，不代替结论。第 3.2 节的决策表仍在「来源」列记录维度 ID，方便查找问题来源。
3. 第 1 节再追加「**覆盖核对**」表：spec 每条 R 一行，落点照抄「用户会看到的变化」里的片段（6–20 字），或写「无 —— 见「X」段」。
   - **对照 spec 第 4 节每条 R 的「可观察证据」，不是第 2 节那句摘要。** 摘要只有几个分句，第 4 节有十几条要求，照摘要写下来必然漏掉验收面。
   - 界面上真看不见的 R 才写「无」，并说明在哪一节交代。写不出落点的 R，要么补进第 1 节，要么回阶段 3 想清楚它到底有没有可见面。
   - 这张表不计入 30 行。用户可以不读它，它拦的是漏写。
4. 第 2 节两张表：`2.1 需要用户确认的例外`（覆盖 / 仅本次 / 阻断态，一条一个决定）、`2.2 Agent 遵循的既有规范`（既有规范，按主题合并）。
5. 自检第 1–2 节：
   - 把第 1 节念一遍，凡是需要停下来想"这词指什么"的地方，改写或加括号解释。
   - 对照 spec 第 4 节逐条念「可观察证据」：哪条在人读的画面上看不到，就是第 1 节漏了它。
   - 检查第 2.1 节每行：「为什么」是不是一句话？有没有分号串起两件事？有就拆。
   - 检查第 2.2 节：有没有混进需要用户决定的例外？有就移到 2.1。
   - 检查 2.2 与 2.1 的条款 ID 有没有重叠：同一条款被 2.1 覆盖了一部分时，2.2 那行必须限定只沿用哪一部分（「仅三条交付命令」「除顶部工具栏高度外」），否则读者不知道这条还生不生效，Agent 也可能按 2.2 把被覆盖的部分做回去。
6. 跑 `plan_lint.py`：`draft` 状态下跳过任务与覆盖（L05 / L06），其余照查（含 L10 人读区、L11 可见面）。
7. 保持 Status 为 `draft`，按 `rules/crosscheck.md` 完成方案确认前的独立核查：
   - 仅检查 V1–V5，输入只有 spec、plan、规则三份。`new` / `extend` 必跑，`fix` 可跳但须说明理由。
   - 结果只在交付回复中列出缺口与计数，不写第 3–6 节。
   - 需要核查时，修补缺口后重新跑 lint、重新核查，直到通过。然后重跑 lint，再交付。
   - 请用户决定：**「是否同意这个方案？同意后我再写设计与任务；如果不同意，要改哪一条？」**

**不确认就到此为止。** 不写任务，不预估工时，不"顺手把结构也列一下"。

用户确认后：Status 改为 `design-ok`，进入阶段 5。这个状态表示方案已确认、正在准备完整计划，不表示检查已通过。写作中可未完成，但交付前第 3–6 节必须齐全并通过检查，不能等到 `approved` 才检查。

## 阶段 5：设计与任务

这一段**不再问用户**，一次写完第 3–6 节。写完后以没参与讨论的人为读者检查：每项都应能说清做什么、怎么验、出问题怎么撤回。不要用编号或压缩术语代替说明：

1. **第 3 节设计**：结构、决策表、影响文件、边界。影响文件清单同时是 `sdd-impl` 的 允许修改的文件范围——"每个文件一个职责"。
2. **第 4 节任务**：每个任务四行固定格式（`改动` / `验证` / `覆盖` / `依赖`），用 `- [ ]` 开头。
   - **checkbox 只标断点位置，不是完成证据。** 它存在的理由是执行可能中断，第二天从第一个未勾选处继续；完成与否由 `sdd-review` 的命令输出判定。
   - 任务粒度以"一次验证能通过"为准，不以工时为准。基础设施类工作（创建目录骨架、加依赖、改构建或依赖清单）必须显式成任务，不许假设它已经存在。
   - **依赖只写前面的任务号。** 所需文件、入口或数据必须先准备好。例如 T4 依赖 T5，就应调整任务顺序，不能让执行者做到一半才发现缺少产物。
   - **改动里的路径必须在 3.3 清单内。** 3.3 是 允许修改的文件范围；任务里顺手写一个清单外的文件，实现时就会静默扩张。两处都列具体文件，使用仓库相对 POSIX 路径（以仓库根为起点，用 `/` 分隔目录）。每个路径单独用反引号标记，不支持目录、通配符或绝对路径。根文件、点文件、Unicode、空格及无扩展文件都必须识别，不按特定目录区别处理。例如：`AGENTS.md`、`.config`、`资料/验收 说明.md`、`Makefile`。
3. **第 5 节 `R → 验证`**：spec 每条 R 恰好一行。自动验证写命令或测试文件及预期结果，说明如何证明这条需求的全部可观察证据，不能只写「命令成功」。手工检查给出可重现的数据、入口、环境、步骤和预期结果，不为验收添加 spec 外的调试功能。
4. **第 6 节风险**：会怎么坏、怎么发现、怎么退；回滚须与任务依赖产物和第 3.3/3.4 节边界一致。预研漏读的文档在这里补一行，覆盖决策在第 3.2 节补齐。
5. **核实验证能执行**：Agent 从实际入口逐项检查手工验证需要的数据和状态是否可达，不能把自动测试夹具当成手工入口的数据。Agent 同时把沿用规范要求的验证动作安排到任务中；规范指定的截图尺寸、标注或证据不能省略。具体设计若触犯未覆盖的规范，Agent 修改设计或明确记录覆盖，不自行解释成豁免。
6. **对证记录**：第 6 节必须有记录，首次 lint 前可写「未运行」，不得伪写通过。lint 不证明语义已过；实际交付必须完成独立上下文对证、更新记录并重跑 lint。

在 `design-ok` 状态写完第 3–6 节（含决策、风险、对证记录）后跑 `plan_lint.py`，退出码 0，再进入开工确认。

跑：

```bash

```

退出码 `0` 全过 / `1` 有 FAIL / `2` 用法错误或文件缺失。**有 FAIL 不许交付，也不许用文字解释绕开。** 文档不符合规则时，修正文档。怀疑检查规则有误时，暂停交付，说明冲突并请用户决定是否调整流程；不要为了通过检查而自行修改脚本。

### lint 全过后，换一个上下文做对证

lint 能核对有没有写，不能判断是否准确表达需求。例如需求要求导入错误提示包含行号和原因，计划却只写「显示错误提示」，引文存在也不足以证明写全。独立核查见 [rules/crosscheck.md](rules/crosscheck.md)，遵守三条硬规则：

1. **换上下文。** 新开 subagent 或新会话。方案确认只提供 `spec.md`、`plan.md` 和规则表三份材料，检查 V1–V5。开工确认检查 V1–V8；除三份基础材料外，按需只读加载已生效规范、源码和配置，核实事实，不能只凭计划中的说法判断。两次核查都不提供访谈记录、前一版计划或作者的思考过程，也不运行项目构建、测试或启动命令。
2. **每条结论有原文依据。** 逐项对照 spec 行号及原文、plan 行号及原文。涉及规范或源码事实时，再补来源路径、行号与原文。通过项不展开；缺口必须附引文。交不出必要引文，判 `UNVERIFIABLE`（无法核实），按不通过处理。
3. **只报缺口，附一行计数。** 全过也只写一行；方案确认带 V1–V5，开工确认带 V1–V8。零项写 0 并说明不适用，不得省略。例如：`开工确认（B）对证无缺口：V1 11 条、V2 5 条覆盖、V3 4 态、V4 7 条、V5 6 项、V6 11 条 R、V7 2 项手工、V8 4 项任务`。有缺口也附各项计数与缺口数，不列通过清单，不新增用户必读报告。核查者不改文件，由写计划的一方修补。

按变更类型执行：方案确认的 `new` / `extend` 必跑，`fix` 可跳但须说明理由；开工确认的所有类型都必跑。

- 方案确认结果或跳过理由只放交付回复，`draft` 第 3–6 节仍为空。
- 开工确认结果写第 6 节一行。首次 lint 前可记「未运行」，实际交付不得保留；核查通过后更新记录，再重跑 lint。
- 有缺口时，修改计划、跑 lint、换独立上下文重新核查。无缺口后记录结果、重跑 lint，最后交付。

**状态收尾**：

- 交付时 Status 为 `design-ok`：第 3–6 节完整，开工确认的独立核查通过、第 6 节已记录且最终 lint 为 0，再请用户判断"是否可以进入实现"。写作中、仅 lint 通过或对证「未运行」都不等于可交付。
- 用户明确说"审核通过，可以下一步"后，把 Status 改为 `approved`。不要求 tag、commit 或其它凭据。
- 含糊表达（"看起来不错"）不算批准；问一次"是否可以进入实现"。
- 用户要改方案：改完回 `design-ok`，重跑 lint、开工确认的独立核查、记录及最终 lint；若改动触及 spec，回 `sdd-grill`，本文件标 `stale`。

## 输出说明

给用户看的五行，不要长。**第一行必须是「用户会看到的变化」**——这一行决定了用户接着读还是直接点同意：

1. **用户会看到的变化**：一句话，用第 1 节的话讲。不许出现文件名、类名、维度 ID。
2. **结论**：`plan.md` 已就绪 / 只写到方案摘要 + 任务数 + 覆盖 R 数
3. **检查**：`plan_lint.py` 退出码与通过项数；未确认的拍板项数
4. **成本**：工具调用 / 预算；问题数 / 上限
5. **下一步**：请用户确认（摘要阶段）或确认可进入实现（定稿阶段）

第 1 行不是复述流程状态，是替用户先描述一遍成品。写不出来，说明第 1 节没写清，回去补。

## 异常与兜底

- **spec 未批准**：停，回 `sdd-grill`。不要"先做着，反正会批"。
- **spec 第 7 节有遗留**：停，把问题摆出来。Agent 不得替用户选择。
- **用户不想被访谈**（"你直接定"）：允许，但必须可见——第 3.2 节决策的 `来源` 写 `Agent 自定`，并在输出里逐条列出。不得伪装成访谈结论。
- **预研预算用尽**：不静默收工。把未读文档与"哪条决策因此未验证"写进第 6 节风险表，并在输出里说明。
- **发现 spec 不可实现**：停，回 `sdd-grill`。不要在 plan 里改需求来迁就实现。
- **访谈暴露新范围**：停，回 `sdd-grill`。一条 spec 只解决一个问题。
- **口头长效约定**：中断，先补 `docs/standards/`（或改依赖白名单），再回来。见阶段 2「口头约定必须落盘」。
- **规范与 spec 打架**：按层解决——spec 写的特例优先于通用规范，标 `覆盖` 并写理由；plan 想推翻 spec 的行为才回 `sdd-grill`。见阶段 2「冲突按层解决」。
- **lint 与判断冲突**：先核对文档和规则。文档有误就修正文档；怀疑规则有误就暂停交付，引用冲突原文并提出修改建议。流程变更须按 `AGENTS.md` 第 6 节取得用户明确确认，不能在本次计划任务中自行改脚本或忽略失败。

## 下游契约（给 sdd-impl）

`plan.md` 必须提供下面五样，否则实现阶段会重新开始设计：

1. **任务清单**：`- [ ]` + 编号 + 四行（改动 / 验证 / 覆盖 / 依赖）。断点续做靠它。
2. **影响文件清单**：只允许修改清单内的文件。需要改其他文件时，先回 plan 补齐，不许顺手加。
3. **验证命令与预期**：每个任务一条；不能自动验证的有 `手工：` 步骤。实现阶段的证据直接取这里。
4. **边界**：不碰什么。它是"顺手改"的拦截线。
5. **风险与回滚**：出问题撤销哪些改动、还原哪些文件。默认不假设有版本控制，不写"退回到某次提交"。

反过来说，下面这些**不属于** `plan.md`：需求定义与验收判据（spec）、命令输出与结论（review）。
