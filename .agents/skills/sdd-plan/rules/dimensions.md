# 设计访谈维度（sdd-plan）

需求访谈问"要什么"，设计访谈问"**怎么建**"。这里只列 spec 装不下、又必须由用户决定的部分：取向、边界、代价。

维度 ID 与 `tools/plan_lint.py` 顶部的规则常量逐字对应，改一处必须同步另一处。

示例使用导入文件、生成报告、提交表单等通用场景，不绑定语言、框架或业务领域。维度是设计访谈中需要检查的一类问题；ID 只用于定位，不能代替结论本身。

## 两种维度

| 类 | 前缀 | 问的是 | 例子 |
|---|---|---|---|
| **构建** | `S` | 结构、依赖、失败、测试与检查安排、产物形态 | 用标准库解析还是引第三方；排序放展示层还是数据层 |
| **关系** | `U` | 与既有代码和未来 spec 的关系 | 这段逻辑已有实现要不要复用；接口要不要给下个 spec 留口 |

## 构建维度

| ID | 维度 | 必问什么 | 典型问题 |
|---|---|---|---|
| `S1` | 结构归属 | 逻辑放哪一层、哪个目录、新建还是改既有文件 | 文件名的规整逻辑放 `core/` 还是各功能目录？ |
| `S2` | 数据流与状态 | 谁持有数据、谁传参、何时重算 | 分片进度由调用方传入还是循环内部持有？ |
| `S3` | 依赖与选型 | 新增包了吗、版本、与依赖白名单是否冲突 | 用标准库的解析器还是引第三方？ |
| `S4` | 失败路径 | 异常怎么映射、错误从哪来、要不要重试 | 单行失败记成哪一类错误，退出码是多少？ |
| `S5` | 测试与检查安排 | 要不要安排测试或其他检查；需要时选自动测试、手工检查或组合；放在末尾还是任务中途；已有结果是否允许复用；多项检查的顺序与依赖；是否要求证据文件 | 导入报告需要测试吗？若需要，用自动测试还是手工核对，何时检查？ |
| `S6` | 产物形态与观感 | 有界面时问布局、密度、间距、字号；无界面时问产物格式、字段顺序、精度 | 列表行高多少？一屏目标多少条？报告保留几位小数？ |

`S5` 适用于三类变更。Agent 先核对 spec 和适用规范已确定的检查要求；未确定且存在实质选择时，才按需要问用户。上述六项是检查清单，不是六个必须逐项提出的问题。访谈决定计划要写的检查安排、结果复用限制及证据要求，不规定实现阶段的具体执行方式。若证据文件会新增需求交付物，而 spec 未授权，Agent 回到需求阶段，不在设计访谈中补需求。

`S6` 是唯一一个 spec 通常不写、但用户一定有偏好的维度。**Agent 不得自行决定**：密度或产物格式错了会整块返工，而且返工发生在用户已经看过之后。

## 关系维度

| ID | 维度 | 必问什么 | 典型问题 |
|---|---|---|---|
| `U1` | 既有模式复用 | 仓库里有没有同类实现、要不要抽公共件 | 已有导出模块，这次复用还是另写一份？ |
| `U2` | 后续修改与撤回 | 后续可能改什么，这次是否需要预留接口、怎样撤回 | 这次只读本地文件，下次接在线数据时要不要预留接口？ |
| `U3` | 不碰清单 | 哪些文件、模块、配置明确不动 | 要不要顺手改流水线配置？ |

## 按变更类型选择问题

| 型 | 候选维度 | 问题上限 |
|---|---|---|
| `new` | `S1` `S2` `S3` `S4` `S5` `S6` `U1` | 7 + 2 = **9** |
| `extend` | `S1` `S2` `S4` `S5` `U1` `U2` | 6 + 2 = **8** |
| `fix` | `S1` `S4` `S5` `U1` | 4 + 2 = **6** |

上限 = 候选维度数 + 2 次派生追问。撞上限就停下问用户：**拆**，还是**追加 +4**（最多两次）。

**候选不等于必问。** spec 已经把这件事定死、或者仓库里根本没有可复用的既有实现时，问了只是占用户的注意力，答案必定是"按 spec 来"。不问的维度在第 3.2 节记一行原因，例如：

```text
S4 不问：spec R6 已规定失败呈现为消息加错误码，没有可选空间。
U1 不问：仓库只有脚手架，没有同类实现可比。
```

没记原因的空缺按漏问处理——数字本身不说明什么，交代才说明什么。

`U3` 不必单列问题：它由第 3.4 节「边界」直接写出，由 Agent 填写，用户只需否决。

## 工具预算

| 型 | 工具调用 | 分配 |
|---|---|---|
| `new` | 14 | 索引扫描 ≤6，精读 ≤8 起步 |
| `extend` | 18 | 索引扫描 ≤6，精读 ≤12 |
| `fix` | 10 | 索引扫描 ≤4，精读 ≤6 |

扫描和精读分别计数：扫描先找出相关文档，必须完成；精读只阅读本次需要的原文，通常消耗更多上下文。

**扫描没用完的次数可以转给精读，反过来不行。** 先完成索引扫描，再把剩余次数用于必要阅读：

1. 先把 `steering.md` 逐行扫完，再动第一份原文。
2. 扫描消耗低于额度时，余额单向并入精读。
3. 精读打满仍不够，优先合并同源文档的读取（同一份规范只读一次，分段看），不要跳读；仍然不够就按「预研预算用尽」处理，把未读文档与因此未验证的决策写进第 6 节。

## 什么不问

- **能查的事实**：某文件是否已有实现、某个包在不在依赖清单里。Agent 自行查询。
- **spec 已定的行为**：问了就是要把需求改成访谈结论，回 `sdd-requirement`。
- **纯机械选择**：变量名、文件内顺序。Agent 定，写进第 3.2 节即可，不必占问题预算。
