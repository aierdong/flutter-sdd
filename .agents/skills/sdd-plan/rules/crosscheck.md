# 独立核查：对照需求与计划

独立核查用于发现内容矛盾和执行缺口，不代替用户选择，也不重复机械校验。核查者是未参与本轮写作的新 Agent 或新会话，只读检查，不修改文件、不运行 lint、不运行项目构建、测试或启动命令，不再委派核查。

## 依据和冻结边界

本文件中，`spec.md`（简称 spec）是需求说明，`plan.md`（简称 plan）是执行计划。lint 是检查格式和部分规则的脚本；V1–V8 是下文八项核查内容的编号。

- **方案确认（A）**：用户决定是否接受 plan 第 1–2 节中的方案。核查者在用户确认前检查这些内容与需求是否一致，使用 V1–V5。主 Agent 提供 spec、plan 和本规则，核查者必要时只读核实直接相关事实。
- **开工确认（B）**：用户决定是否允许按完整计划进入实现。核查者在用户确认前检查设计与任务，首轮使用 V1–V8。核查者依据已确认的 plan 第 1–2 节和 spec 第 4 节，同时检查计划是否遵守需求边界、取舍和已确认适用的规范。
- B 不得修改 spec，也不得修改 A 的执行结果（plan 第 1–2 节）。主 Agent 与核查者都只能细化和检查已定方案，不新增功能、验收要求、截图交付或其他产物。
- 核查者发现需求、方案或规范适用范围需要重新决定时，报告原文与影响。主 Agent 随即停止并交用户决定。核查者不能建议主 Agent 在 B 中改写上游。
- 核实既定命令、路径或入口有实际错误是允许的；仅因未见某种命令示例而怀疑其不可用，不构成已证实的阻塞。无法核实关键可行性时，写明缺少什么事实及影响，不能伪装成确定错误。

## 核查范围

### V1：需求与摘要一致

核查者逐条检查计划是否准确表达需求的可观察结果。纯内部要求可以指向其他段落，不强制重复进用户画面。引文逐字存在不等于语义正确。

### V2：例外的后果清楚

第 2.1 节的例外须有理由、范围和失效条件。存在用户可见差别时摘要说明后果；确无差别时说明理由，不虚构可见影响。

### V3：状态分得清

需求要求的不同状态各有明确描述，互不矛盾；没有多态要求时不增加状态。

### V4：用户要决定的事项对得上

摘要的决定事项与 2.1 对应，不遗漏，也不重复要求用户批准同一件事。

### V5：不越出需求边界

计划没有把明确不做的内容写成承诺，没有增加未经确认的交付和验收要求。

### V6：每条需求都有实现与验证安排

核查者逐条检查需求（R）是否有对应的设计、任务、验证方法及预期结果。验证方法应证明需求得到满足，而非只证明命令退出成功。核查者检查计划是否安排了既定验证要求，不重新引入上游未决定的验证交付。

### V7：验证能照做

手工步骤有数据及准备方法、入口、环境、操作与预期，允许的入口能够到达所需状态；不把测试夹具当成手工入口的数据。自动验证须说明检查对象和结果，不要求计划阶段实际执行。

### V8：任务、范围与回滚一致

前置文件、数据或入口已存在或由前序任务提供。任务路径在允许修改清单中，依赖不倒置。风险与撤回办法不破坏声称保留的产物。设计遵守已确认方案及适用约束，发现冻结边界内无法解决的冲突就报告停止。

## 问题级别与性质

核查者为每个问题分别标明级别和性质，不能用其中一个字段代替另一个。

级别：

- **阻塞**：Agent 无法在当前阶段的授权范围内解决的问题，例如需求或已确认方案存在冲突、必须改变冻结内容才能解决，或影响关键可行性的事实无法确认。核查者须给出具体依据和后果；主 Agent 停止当前流程，交用户决定。
- **一般问题**：开工确认（B）内部必须修复并再次核查的问题，不是可选建议。例如设计遗漏既定要求、任务无法照做、验证不能证明需求，但主 Agent 可以在不改变需求、已确认方案和验收范围的前提下，通过修改第 3–6 节解决。此级别只用于“仅设计与任务”的问题；主 Agent 必须修复并经定向复核通过，才能请求开工确认。
- **轻微问题**：不影响理解、执行和验证结论的措辞、排版或笔误。主 Agent 可以处理或忽略，并记录处理情况；不因此开启下一轮独立核查。

性质：

- **需求**：必须改变 spec 的行为、边界、取舍或验收要求才能解决。
- **方案**：必须改变 plan 第 1–2 节的决定才能解决。
- **仅设计与任务**：在不改变需求和已定方案的情况下，可以通过第 3–6 节修正。A 尚无设计与任务，不使用此分类；发现需求或方案问题就交用户决定，三次是上限，不是必须用满的轮数。

任何真正属于需求或方案的问题都交用户决定，不能包装为设计修订。单纯发现措辞偏好不等于需要重开方案。依据不足时写“无法核实”，说明具体缺失；只有影响关键可行性且无法继续时才标阻塞，不因未找到引文就自动阻塞。

## 一次完整核查，后续定向复核

A、B 各自最多三次独立核查。主 Agent 的首次编写后最多修改两轮。核查者一次返回完整结果，不把同一轮意见分批追加。核查期间主 Agent 不修改稿件。

核查者在首轮检查本阶段的全部适用项。主 Agent 在后续核查的输入中增加以下材料：

- 上轮完整问题清单及稳定编号，例如 `Q1`。
- 主 Agent 的逐项处理结果：已修正、轻微问题未处理及理由、待用户决定。一般问题不得作为可选意见直接忽略；无法在授权范围内修复时，主 Agent 停止并交用户决定。
- 本轮改动位置与受影响的任务、验证、依赖及回滚。

后续核查者独立判断处理是否有效，只检查原问题和修订的连带影响。作者解释不能代替计划正文，核查者可核实声明的影响范围。不重新全量遍历无关部分，不新增无关建议；偶然发现新的明确阻塞可以报告并给新编号，不得自行扩大为完整重审。修订需要大范围重审时报告原因并停止，由用户决定。

## 返回格式

核查者不新增报告文件。每项问题使用固定字段，不使用表格：

```text
#### Q1：验证不能证明顺序要求
- 级别：一般问题
- 性质：仅设计与任务
- 核查项：V6
- 依据：spec:42 要求保持输入顺序；plan:130 只检查输出文件存在。
- 影响：乱序输出也会被判通过。
- 修正目标：在现有验证安排中检查输出顺序，不新增交付物。
```

核查者引用来源路径、行号和必要原文。计划内部有矛盾时，核查者引用两处内容；计划缺少内容时，核查者引用相关要求和应补的位置。核查者只输出问题，不展开通过清单，并在结尾报告本次轮次、完整或定向范围、各级别问题数量、未核实事实及总体结论。复核时，核查者保留原问题编号与处理结论，不用计数代替实际检查。

发现阻塞或必须改变需求、已确认方案才能解决的问题时，主 Agent 立即停止并交用户决定。没有阻塞但存在一般问题时，主 Agent 在剩余修改轮次内修复，并安排下一次定向复核。没有阻塞且所有一般问题均已修复并核查通过时，主 Agent 结束独立核查；轻微问题可以处理或忽略，不因此继续循环。第三次核查仍有阻塞或一般问题未解决时，主 Agent 停止自动修改，报告未完成事项，不生成第四轮任务，也不宣称核查通过。主 Agent 记录结果和遗留问题，按技能规定决定是否需要最终 lint，最后交用户决定。
