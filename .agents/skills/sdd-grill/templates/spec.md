# Spec 模板（审阅区）

<!--
模板文件：不要直接使用本文件本身，复制一份到目标规格目录再写。

用法：
- 尖括号 <> 是占位，写完删掉。
- HTML 注释是写作提示，定稿前删掉。
- 只写第 1–7 节。用户指定的产品行为、技术/质量约束和测试要求都可以作为需求；文件清单、接口签名、任务拆分、执行命令默认属于 plan，除非用户明确指定它们作为验收约束。
- 正文用中文。代码标识符、命令、字段名保持原样。
-->

> 本文件供人类审阅。只读第 1–6 节，就能判断这条需求该不该做、做成什么样、代价是什么。

| 字段 | 值 |
|---|---|
| Spec | `pNN-NNN-<slug>` |
| 类型 | `new` / `extend` / `fix` |
| 上游 | `—` 或 `pNN-NNN-<slug>`（增量/修正时必填） |
| 附带交付 | `—` 或 `R7`（超出本 spec 主类型的条目，如规范变更；多条用「、」分隔） |
| Status | `draft` / `approved` / `stale` |
| 版本 | `v1`（实质修改需求、边界或决策时递增；纯排版和勘误不递增） |

> 批准方式：用户明确确认需求可以进入下一步后，Agent 将 `Status` 记为 `approved`。不要求批准 tag、专用 commit 或其它凭据；状态仅用于标记流程位置。

**为什么现在做**：<不做的代价，或它挡住了什么>

## 4. 必须做到

<!--
每条一个 R#，编号在本 spec 内唯一且稳定，后续 plan.md、测试、完成定义都用它引用。
每条必须能说出反例：什么情况下它会被违反。说不出来的，不要写进这一节。
"可观察证据"写人能观察到什么，不写测试名和命令。
增量/修正：若改变了上游的某条 R，加一行 **取代** 写明上游编号。
条目超出本 spec 主类型时（如 UI spec 里夹一条改规范的），加 **范畴**：standard / doc / data / contract，
并在头部「附带交付」里登记该编号——plan 据此把两类验证分开。
-->

- [ ] **R1** <一句"条件 + 行为 + 结果"，不要求固定句式，但要可测试>

  - **可观察证据**：<用户或操作者能看到/查到什么>

- [ ] **R2** <……>
  - **范畴**：standard（仅当条目不属于本 spec 主类型时）
  - **反例**：<……>
  - **可观察证据**：<……>
  - **取代**：`pNN-NNN R5`（仅当改变上游已批准条目时）
