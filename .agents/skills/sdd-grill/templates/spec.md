# Spec 模板（供人审阅）

<!--
Agent 先把模板复制到目标需求目录，再填写内容。

用法：
- Agent 替换尖括号 <> 内的占位文字，并删除尖括号。
- HTML 注释是写作提示，Agent 在定稿前删除。
- Agent 只写第 1–7 节。用户指定的产品行为、技术约束、质量要求和测试要求都可作为需求。
- 文件清单、接口签名、任务拆分和执行命令默认属于 plan。用户明确指定为验收约束时，Agent 仍须写入 spec。
- 全文都要让人读懂。写清谁做什么，一句话说一件事。条件多就拆开，首次出现的术语要解释。
- 编号只帮助定位，不代替意思。使用简单、通用的例子，不借用 Demo 的业务，不写技能的修改经过。
- Agent 用中文写正文，保留代码标识符、命令和字段名。
- spec 指需求文档；R 指必须满足的需求条目；上游指本次扩展或修正的已有 spec。
-->

> 本文件供人类审阅。第 1–6 节说明这条需求该不该做、做成什么样、代价是什么。第 7 节列出仍需你决定的问题；这些问题解决后，才能批准进入下一步。

| 字段 | 值 |
|---|---|
| Spec | `pNN-NNN-<slug>` |
| 类型 | `new` / `extend` / `fix` |
| 上游 | `—` 或 `pNN-NNN-<slug>`（增量/修正时必填） |
| 附带交付 | `—` 或 `R7`（超出本 spec 主类型的条目，如规范变更；多条用「、」分隔） |
| Status | `draft` / `approved` / `stale` |
| 版本 | `v1`（实质修改需求、边界或决策时递增；纯排版和勘误不递增） |

> 批准方式：用户明确确认需求可以进入下一步后，Agent 将 `Status` 记为 `approved`。不要求批准 tag、专用 commit 或其它凭据；状态仅用于标记流程位置。

## 1. 背景与问题

<!--
Agent 先用一段话说明现状、后果和现在要做的原因，再按需列条目。
- 新建：Agent 说明用户目前怎样替代这项能力。
- 增量：Agent 写明上游 spec 编号，以及本次涉及的已有行为。
- 修正：Agent 写清当前错误行为，尽量提供复现步骤。
-->

**现状**：<用户/系统目前是怎么做的，具体到操作步骤或代码事实>

**问题**：<这个现状造成了什么后果，最好带一个具体场景>

**为什么现在做**：<不做的代价，或它挡住了什么>

## 2. 目标

<!-- 每条目标都要能对应到第 4 节的某个 R#。对不上的，说明它是顺带收益，不是目标。 -->

- <我们要让用户能够……>
- <我们要让系统……>

**成功后，你能看到/做到**：<一句可观察的验收描述，不用术语>

## 3. 用户场景

<!--
写成完整过程（谁、想做什么、看到什么、然后怎样），不要写成条款的另一种排列。至少一个异常场景。
新建：主场景 + 第一个异常场景。
增量：从既有场景出发，说明多出来那一两步。
修正：异常场景就是重点，写清"现在会怎样、应该怎样"。
-->

### 场景 A：<名称>

1. <用户从哪里进入>
2. <看到什么>
3. <执行什么操作>
4. <系统做什么>
5. <用户得到什么>

### 场景 B：<异常或边界情况>

1. <触发条件>
2. <系统应该怎样>
3. <用户应看到什么>

## 4. 必须做到

<!--
Agent 为每条需求分配唯一且稳定的 R#，供 plan.md、测试和完成检查引用。
Agent 为每条需求写反例，说明什么情况会违反该需求。Agent 写不出反例时，不将其列入本节。
Agent 在「可观察证据」说明用户或操作者能看到什么，不写测试名和命令。
增量或修正改变上游 R 时，Agent 用 **取代** 写明上游编号。
条目超出本次主要需求类型时，例如新增报告功能同时修改规范，Agent 添加 **范畴**。
范畴值为 standard（规范）、doc（文档）、data（数据）或 contract（对外约定）。
Agent 同时在头部「附带交付」登记编号，供 plan 分开安排两类验证。
-->

- [ ] **R1** <一句"条件 + 行为 + 结果"，不要求固定句式，但要可测试>
  - **反例**：<什么情况下这条会被违反>
  - **可观察证据**：<用户或操作者能看到/查到什么>

- [ ] **R2** <……>
  - **范畴**：standard（仅当条目不属于本 spec 主类型时）
  - **反例**：<……>
  - **可观察证据**：<……>
  - **取代**：`pNN-NNN R5`（仅当改变上游已批准条目时）

> 数量上限 12 条。超过，说明这条需求该拆。
