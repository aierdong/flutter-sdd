# 访谈维度

## 用法

维度不是一张"完整性清单"，而是**按返工产出率排序**的清单。不同需求类型，必做维度不同：

| 类型 | 必做维度 | 可少问 |
|---|---|---|
| 新建 | 通用 1–6 + 新建专属 3 个 | 回归面 |
| 增量 | 通用 1–6 + 增量专属 5 个 | 用户与场景 |
| 修正 | 通用 1（失败语义）、6（可逆）+ 修正专属 4 个 | 首版边界、用户与场景 |

每轮访谈按顺序推进，每个维度问 1–2 个问题；答完在覆盖矩阵里落一格（已覆盖 / 不适用 + 理由）。

## 通用维度

### 1. 失败与部分失败

**防的返工**：实现到一半才发现"失败了但已经改了一半"，于是设计被迫改、契约被迫改。

**问什么**：

- 这个流程里，哪一步可能失败？
- 失败之后，已经做成的部分留不留？谁来清理？
- 用户看到什么？能不能重试？重试会不会重复执行？

**例子**：

- 连接删除已提交，但随后刷新列表失败
- 清空目标表成功，但写入中途连接断开
- 列表分页请求成功，但详情批量拉取失败

**坏答案与追问**：

- "失败了就报错" → 追问：报错之后那半截数据还在吗？下次进来会看到什么？
- "重试就行" → 追问：重试会不会删两次、写两遍？

### 2. 边界与既有行为

**防的返工**：改动本身没错，但把别处的行为改了，测试红了才发现。

**问什么**：

- 这次会改变哪些**现有**行为？不只是新增。
- 谁依赖这些行为（自动化夹具、文档、已有 UI 流程）？
- 老数据 / 老配置怎么办？

**例子**：

- 已有列表页的分页与筛选行为
- 旧配置里没有新字段时读出来是什么
- CLI 输出格式被自动化夹具依赖，改字段就断

### 3. 空与极值

**防的返工**：测试阶段补边界，任务表重排。

**问什么**：

- 0 条、1 条、上限时分别是什么行为？
- 重复、超长、非 ASCII、空字符串？

**例子**：

- 0 个连接时的空状态是空白、空提示，还是引导创建
- 1000 个连接时是否分页、是否虚拟滚动
- 连接名为空、超长、重名

### 4. 并发与顺序

**防的返工**：实现阶段才讨论锁，接口被迫改成带版本号。

**问什么**：

- 两个入口同时操作同一份数据会怎样？
- 重复提交、乱序到达、取消与重试交错呢？

**例子**：

- 两个窗口同时删除同一条连接
- 删除请求还在路上，用户又刷新了列表
- 同一连接被扫描与执行同时使用

### 5. 权限与密钥

**防的返工**：评审阶段被打回，安全项回头补设计。

**问什么**：

- 谁能看见、谁能执行？
- 错误信息、日志、导出里会不会带敏感值？脱敏在哪一层做？

**例子**：

- 连接密码走 `secret://` 引用，不得出现在日志/错误/导出里
- 列表里展示的连接信息是否包含主机、用户名等敏感字段

### 6. 可逆性

**防的返工**：批准了一个自己以为能回退的操作，事后无法恢复。

**问什么**：

- 哪一步不可逆？
- 做错了能恢复到什么程度？靠备份、预览，还是二次确认？
- 用户需要提前知道这是不可逆的吗？

**例子**：

- 删除连接会级联删除相关的 schema 缓存与配置
- truncate 目标表、向目标库写入

## 型专属维度

### 新建专属

**N1. 首版边界**

- v1 做什么、明确不做什么？剩下的为什么现在不做？
- 判断标准：**没有首版边界的"新需求"会一路长成平台。**

**N2. 用户与场景**

- 谁用、多久用一次、现在他们怎么凑合解决？
- 如果现在有替代路径（手动、命令行、别的工具），新页面要赢在哪里？

**N3. 与既有能力的关系**

- 是要复用已有组件/接口，还是另起一套？
- 如果另起，说清楚为什么不复用。（重复造是新建最常见的隐性成本）

### 增量专属

**E1. 与既有 R 的关系**

- 这次改的是上游第 4 节的哪几条 R？是扩展、修改，还是取代？
- 被取代的条目要写明编号，不能只写"调整了一下"。

**E2. 上游"不做"清单是否被推翻**

- 上游第 5 节里有没有一条正是这次要做的？
- 如果有，必须由人显式推翻并给出理由（为什么当时不做、为什么现在做）。
- **这条是防止两个 spec 互相打脸的主要机制。**

**E3. 边界是否外扩**

- 新能力是否需要跨出上游 spec 的边界？
- 如果需要，新的边界写清楚；不要让"顺手加的一点"悄悄扩大责任范围。

**E4. 老数据与老用户**

- 已有的连接、项目、执行历史要不要补字段或迁移？
- 用户升级后第一次打开会看到什么？

**E5. 回归面**

- 哪些既有行为**必须保持不变**？（写进第 5 节"不改变……"）
- 哪些既有测试会因为这次改动而需要调整？调整它们算不算改变契约？

### 修正专属

**F1. 正确行为的一句话定义**

- "当 X 时，应该 Y。"一句话说不出来，说明还没定位到问题。

**F2. 同源入口**

- 同样的错在别的地方是不是也有？（同一个接口的其他调用方、同一段逻辑的另一个入口）
- 修一处还是修一类，必须明确。

**F3. 已产生的错误数据**

- 之前跑出来的错误结果要不要修？不修的话用户会怎么遇到它？

**F4. 谁在依赖现状**

- 有没有测试断言了错误行为？有没有文档描述了错误行为？
- 修行为会打破哪些既有预期？

## 次级维度（按需）

| 维度 | 一句话问题 | 什么时候值得问 |
|---|---|---|
| 触发者与入口 | 除了你，还有谁能触发它（CLI、桌面、自动化、定时） | 新增能力时必问 |
| 数据留存与清理 | 这些记录保留多久？谁清理？ | 新增持久化或历史记录时 |
| 对外契约 | 有没有改接口、CLI 输出、事件载荷 | 改动跨进程边界时必问 |
| 时间与外部依赖 | 超时、重试、外部服务不可用时的表现 | 涉及网络、LLM、目标库时 |
| 观测与文案 | 用户看到的那句话是什么？日志里留什么 | 有明显失败路径时 |
| 多目标差异 | MySQL 与 PostgreSQL 行为不同吗 | 触及 dbx 适配层时 |

## 覆盖矩阵

访谈结束前填完，跟着 `spec.md` 一起交给人看（可放在 `grill.md` 末尾）。

**只填本型必做的维度**，其余留空并注明"本型不要求"：

| 维度 | 状态 | 依据 |
|---|---|---|
| 失败与部分失败 | 已覆盖 | R2、R4 |
| 边界与既有行为 | 已覆盖 | R1、§5 |
| 空与极值 | 已覆盖 | R3 |
| 并发与顺序 | 不适用 | 单窗口串行操作，无并发入口 |
| 权限与密钥 | 已覆盖 | 复用既有脱敏层，无新增暴露面 |
| 可逆性 | 不适用 | 只读列表，无持久化写入 |
| E1 与既有 R 的关系 | 已覆盖 | 取代 p00-001 R5 |
| E2 上游"不做" | 已推翻并说明 | p00-001 §5 第 2 条 |

**"不适用"必须带理由。** 写不出理由，就是没想过。

## 追问话术

当回答含糊时，不要重复原问题，换一种问法：

1. **给场景二选一**："删除成功后列表刷新失败，界面显示成功还是失败？"
2. **用历史锚定现实**："上一次遇到这种情况是怎么处理的？"——已有做法往往就是真实规则。
3. **反着问**："如果反过来做，最坏会怎样？"——把隐藏代价逼出来。
4. **问误解**："如果这条不写进 R，实现时最可能被理解成什么？"——把歧义逼出来。
5. **（增量专用）问上游**："如果上一个 spec 的作者看到这次改动，他会说哪一句被推翻了？"

**三类回答不能接受**：

- "应该没问题" —— 没有信息量，换成场景二选一。
- "看情况" —— 追问：哪两种情况的处理不同？
- "你决定" —— 这是把审阅权让出去。停下，请对方至少给出偏好和理由；否则这条进第 7 节，不写进 R。

## 不该在访谈里问的（属于执行区）

- 用什么库、什么字段类型、文件放哪
- 测试怎么写、跑哪条命令
- 任务怎么拆、要多久
- 代码结构怎么组织

这些留给 `plan.md`。在访谈里问它们，会把人的注意力从"要不要做、做成什么样"转移到"怎么实现"，而那正是最容易没想透的地方。
