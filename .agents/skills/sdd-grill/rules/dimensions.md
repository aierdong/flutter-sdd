# 访谈维度

## 用法

维度是一类需要问清的问题。下面的清单优先检查容易造成返工的情况。不同需求类型必须检查不同维度：

| 类型 | 必做维度 | 可少问 |
|---|---|---|
| 新建 | D1–D6 + N1、N2、N3（共 9） | 哪些已有行为必须保持不变 |
| 增量 | D1–D6 + E1–E5（共 11） | 用户与场景 |
| 修正 | D1、D6 + F1–F4（共 6） | 首版边界、用户与场景 |

维度 ID 是固定编号。日志的覆盖矩阵、spec 第 7 节的 `维度：` 和校验脚本都使用它。Agent 不得增加或修改 ID，否则脚本会报告维度缺失或多余。

Agent 每轮按顺序检查，每个维度问 1–2 个问题。回答明确后，Agent 在覆盖矩阵记录状态；不适用时写明理由。下文所有业务例子均为虚构。

## 通用维度

### D1 失败与部分失败

**为什么问**：流程可能已经完成一部分才失败。Agent 必须提前问清系统保留什么、用户看到什么，避免实现后重做。

**问什么**：

- 系统在哪一步可能失败？
- 系统是否保留已完成的部分？谁负责清理？
- 用户会看到什么？用户能否重试？系统会不会重复处理？

**例子**：

- 系统导入前 20 行成功，第 21 行失败。
- 系统已生成报告，但刷新报告列表失败。
- 用户提交表单成功，但系统发送通知失败。

**回答含糊时怎么追问**：

- 用户说“失败就报错”时，Agent 问：“用户再次打开页面时，还能看到已导入的 20 行吗？”
- 用户说“重试就行”时，Agent 问：“系统会不会把已成功的行再导入一次？”

### D2 边界与既有行为

**为什么问**：新增功能可能改变已有行为。Agent 应在实现前查清谁依赖这些行为。

**问什么**：

- 本次除了新增能力，还会改变哪些已有行为？
- 哪些测试、文档或用户操作依赖这些行为？
- 系统如何处理旧数据和旧配置？

**例子**：

- 用户仍需按原来的方式筛选报告列表。
- 旧表单没有新字段，系统需要确定显示什么。
- 自动化程序读取报告中的固定字段，字段改名后会读取失败。

### D3 空与极值

**为什么问**：Agent 应提前确认空数据和极端输入，避免测试时才补需求。

**问什么**：

- 数据为 0 条、1 条或达到上限时，系统分别怎样处理？
- 用户输入重复值、超长文字、中文或其他非英文字符、空字符串时，系统怎样处理？

**例子**：

- 没有报告时，页面显示空白、提示，还是创建入口？
- 系统有 1000 份报告时，列表是否分页，或只绘制当前可见的行？
- 用户填写的表单名称为空、过长或与已有名称相同时，系统怎样处理？

### D4 并发与顺序

**为什么问**：多个操作可能同时发生或先后顺序不同。Agent 应先问清结果，避免实现时临时改变接口。

**问什么**：

- 两个入口同时修改同一份数据时，系统怎样处理？
- 用户重复提交，或系统收到请求的顺序与发送顺序不同时，结果是什么？
- 用户取消后又重试时，系统怎样区分这些操作？

**例子**：

- 两个窗口同时编辑同一份表单。
- 用户提交导入后，又立即点击取消。
- 用户连续生成两份报告，较早提交的报告反而较晚完成。

### D5 权限与密钥

**为什么问**：Agent 应先确认访问范围和敏感信息处理方式，避免审查时补安全设计。

**问什么**：

- 哪些用户能查看数据？哪些用户能执行操作？
- 错误信息、日志或导出文件是否含有敏感值？系统在哪里遮蔽或移除这些值？

**例子**：

- 报告包含联系方式，系统是否只显示部分号码？
- 系统导出报告时，访问外部服务所用的密钥不能出现在文件、日志或错误提示中。

### D6 可逆性

**为什么问**：用户应知道操作能否撤销，不能在批准后才发现数据无法恢复。

**问什么**：

- 哪一步操作不能撤销？
- 用户操作错误后，系统能恢复哪些内容？是否需要备份、预览或二次确认？
- 系统是否需要提前提示操作不可撤销？

**例子**：

- 用户删除报告时，系统同时删除其附件。
- 用户用新文件覆盖已导入的数据，旧数据没有备份。

## 类型专属维度

### 新建专属

**N1. 首版边界**

- 首版做什么、明确不做什么？用户为什么暂时不需要其余能力？
- Agent 必须问清首版范围，避免一个需求不断增加新目标。

**N2. 用户与场景**

- 谁使用这项能力？用户多久使用一次？用户目前怎样解决问题？
- 用户已有手工操作或其他工具时，新能力需要改善哪一步？

**N3. 与既有能力的关系**

- 本次复用已有组件或接口，还是新增一套？
- 用户要求新增一套时，Agent 必须问清为什么不能复用，避免重复维护。

### 增量专属

**E1. 与既有 R 的关系**

- 本次扩展、修改或取代上游第 4 节的哪几条 R？
- Agent 必须写明被取代的编号，不能只写“调整了一下”。

**E2. 上游“不做”清单是否被推翻**

- 本次是否要做上游第 5 节明确不做的事项？
- 如果要做，用户必须明确推翻原决定，并说明当时不做、现在要做的原因。
- Agent 用这一检查避免两份 spec 的要求互相矛盾。

**E3. 边界是否外扩**

- 新能力是否超出上游 spec 的范围？
- 如果超出，Agent 必须写清新范围，不能把它当作顺手改动。

**E4. 老数据与老用户**

- 已有表单、导入记录或报告是否需要补字段或迁移？
- 用户升级后第一次打开页面会看到什么？

**E5. 回归面**

“回归面”指本次改动可能影响的已有行为。

- 哪些已有行为必须保持不变？Agent 将它们写进第 5 节“不改变……”条目。
- 哪些已有测试需要调整？调整是否意味着改变原来承诺的行为？

### 修正专属

**F1. 正确行为的一句话定义**

- 用户能否用“当 X 时，系统应该 Y”说清正确行为？Agent 说不清时应继续定位问题。

**F2. 同源入口**

“同源入口”指调用相同接口或使用相同逻辑的其他入口。

- 其他入口是否存在同样的错误？
- 本次只修当前入口，还是修复所有同类入口？用户必须明确范围。

**F3. 已产生的错误数据**

- 系统是否要修复此前生成的错误结果？
- 如果不修，用户会在哪里遇到这些结果？

**F4. 谁在依赖现状**

- 已有测试是否把错误行为当作预期？文档是否描述了错误行为？
- 本次修正会改变哪些已有预期？

## 次级维度（按需）

| 维度 | 问题 | 什么时候问 |
|---|---|---|
| 触发者与入口 | 除当前用户外，命令行、自动化程序或定时任务能否触发操作？ | 新增能力时必问 |
| 数据留存与清理 | 系统保留记录多久？谁负责清理？ | 新增长期保存的数据或历史记录时 |
| 对外契约 | 本次是否改变接口、命令行输出或事件中传递的数据？ | 不同程序需要交换数据时必问；“对外契约”指双方约定的数据和行为 |
| 时间与外部依赖 | 系统超时、重试或外部服务不可用时，用户看到什么？ | 系统需要调用网络服务或外部存储时 |
| 观测与文案 | 用户看到什么提示？系统记录什么日志？ | 操作可能明显失败时 |
| 多目标差异 | 系统导入不同文件格式时，处理方式是否不同？ | 本次能力需要兼容多个目标时 |

次级维度不计入必做集合，也不进入覆盖矩阵。Agent 只在明显适用时询问，并在 `grill.md` 决策区记录答案。

## 覆盖矩阵

Agent 在访谈结束前填写 `grill.md` 的「覆盖矩阵」。矩阵格式固定，脚本按维度检查：

- 矩阵必须恰好包含本类型的必做维度，多一条或少一条记录都会 FAIL。
- 新生成的覆盖矩阵必须使用记录块，不使用表格。每块以 `#### 维度 D2` 等唯一标题开始，下设 `- 维度：D2 边界与既有行为`、`- 状态：已覆盖`、`- 依据：R1、§5` 三个字段。维度值必须以固定 ID 开头；字段与维度记录不得重复，值中的 `|` 不拆分。- 状态只能写 `已覆盖`、`不适用`、`已推翻并说明`、`待决`。
- `不适用` 必须有具体理由。只写“不适用”或“—”会 FAIL。
- spec 第 7 节涉及本类型必做维度的待决问题，矩阵对应记录必须标为 `待决`，不能用其他状态代替。依据写明对应问题，例如“§7 第 1 题：是否保留已导入的行”。
- 反过来，矩阵每个 `待决` 记录在 spec 第 7 节都必须有对应维度的问题。问题解决后，Agent 同步删除问题并更新矩阵状态与依据。
- 还有待决问题时，spec 只能保留为未批准状态，不能记为 `approved`。

下面是 `extend` 类型的完整格式示例。`§5` 表示第 5 节；示例中的需求和依据均为虚构，不可直接当成项目事实。

#### 维度 D1
- 维度：D1 失败与部分失败
- 状态：已覆盖
- 依据：R2 规定报告生成后刷新失败的提示

#### 维度 D2
- 维度：D2 边界与既有行为
- 状态：已覆盖
- 依据：§5 规定保留原有筛选行为

#### 维度 D3
- 维度：D3 空与极值
- 状态：已覆盖
- 依据：R3 规定空列表和最大条数

#### 维度 D4
- 维度：D4 并发与顺序
- 状态：已覆盖
- 依据：R4 规定重复生成报告的处理方式

#### 维度 D5
- 维度：D5 权限与密钥
- 状态：已覆盖
- 依据：R5 规定日志不含访问密钥

#### 维度 D6
- 维度：D6 可逆性
- 状态：不适用
- 依据：本次只新增查看入口，不修改或删除已保存的数据

#### 维度 E1
- 维度：E1 与既有 R 的关系
- 状态：已覆盖
- 依据：R1 写明扩展 pNN-NNN R5

#### 维度 E2
- 维度：E2 上游「不做」
- 状态：已推翻并说明
- 依据：§6 说明本次为何允许查看历史报告

#### 维度 E3
- 维度：E3 边界是否外扩
- 状态：已覆盖
- 依据：§5 排除报告编辑能力

#### 维度 E4
- 维度：E4 老数据与老用户
- 状态：已覆盖
- 依据：R6 规定旧报告的显示方式

#### 维度 E5
- 维度：E5 回归面
- 状态：已覆盖
- 依据：§5 规定原导出行为保持不变

Agent 写不出不适用理由时，必须继续检查该维度。Agent 标记已覆盖时，依据必须指向 R# 或具体小节，不能只写“已经讨论”。

## 追问示例

用户回答含糊时，Agent 应换一种问法，不重复原问题：

1. **给具体场景**：“报告生成后刷新列表失败，界面显示成功还是失败？”
2. **问已有做法**：“上一次导入失败时，你们保留了已成功的行吗？”
3. **问相反选择**：“如果系统撤销已成功的行，用户会失去什么？”
4. **问可能的误解**：“如果不写进 R，实现者最可能怎样理解？”
5. **增量时问上游**：“这次决定会改变上游的哪条要求？”

以下回答还不足以形成需求：

- 用户说“应该没问题”时，Agent 改问具体场景。
- 用户说“看情况”时，Agent 追问哪两种情况需要不同处理。
- 用户说“你决定”时，Agent 停下，请用户至少给出偏好和理由。用户仍未决定时，该条进入第 7 节，不写进 R。

## 不该主动在访谈中决定的实现细节

以下内容默认留给 `plan.md`：

- 实现者选择什么库和字段类型、把文件放在哪里。
- 实现者如何编写测试、运行哪条命令。
- 实现者如何拆任务和组织代码。
- 项目如何安排工作量与耗时。

访谈应先明确用户需要什么行为。用户已经明确指定的技术约束、测试要求或命令仍必须保留在 spec，不能因其属于实现细节而删除或移到 plan。
