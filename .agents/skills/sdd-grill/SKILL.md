# sdd-grill

## 它解决什么问题

需求阶段的两类返工，成因不一样：

- **维度没被打开**：部分失败、空值、并发、可逆性——不是问得不够深，而是整根枝从来没长出来。
- **上下文没接上**：不知道已有页面怎么工作，不知道上一个 spec 说过"不做"，于是新需求在暗处推翻了旧决定。

所以这里不做"更狠的追问"，而是三件事：

1. **先分型**：这条需求是新建、增量还是修正——决定要读什么、问什么、问到什么程度。
2. **强制开枝**：用按返工产出率排序的维度清单，把没想的维度逼出来。
3. **过了闸门再组装**：访谈期间不写文档，一次性写成 `spec.md`。

## 在流程里的位置

```text
sdd-grill   →  spec.md + grill.md   用户明确确认后进入下一步
     ↓
sdd-plan    →  plan.md              执行区，机器自检
     ↓
sdd-impl    →  代码与提交
     ↓
sdd-review  →  证据与结论
```

本 skill 只负责第一格。它的输出必须让后面三步有东西可依，见文末「下游契约」。

## 边界

**负责**：分型、启动时检查待办、只读调查、规范触碰扫描、访谈、组装审阅区（`spec.md` 第 1–7 节 + `grill.md`），以及把明确延期事项登记到仓库根 `FOLLOW.UPS.md`。

**不做**：

- 不擅自替用户作出尚未决定的产品或技术选择；用户明确指定的技术方案、约束、质量要求和测试要求，必须写进 spec，不能因为它“属于技术”就移到 plan
- 不写 `plan.md`，不拆实现任务
- 不改产品代码
- 不做项目级路线图拆分（多个需求之间怎么排期，不是这一层的事）

**项目无关**：本 Skill 与模板要能直接移植到其它项目；不得写死具体 spec 编号、旧流程兼容分支或历史决策，示例统一用 `pNN-NNN`。`FOLLOW.UPS.md` 是仓库根的通用待办文件名。

**四条硬规则**：

1. **访谈期间不写 spec。** 一旦开始起草，提问就会停——这是长会话里最稳定的退化模式。
2. **一次一问。** 一次抛多个问题等于让人扫读，等于没问。
3. **事实自己查，决定必须问人。** 能用文件和命令确认的，不许占用人的注意力。
4. **批准以用户明确确认作为唯一门槛。** lint 通过不等于批准；Agent 不得自行推断批准。用户明确说 spec 可以进入下一步后，Agent 更新 `Status: approved` 并继续；不要求 tag、专用 commit 或其它批准凭据。

## 输入

- 一句需求描述（可以是口语、可以不准）
- 相关代码路径或上游 spec 编号（不确定就先查）
- `steering.md`（知识索引；按索引加载相关规范、设计与专题）
- 已有 `spec.md`、`grill.md`（同领域的历史决策）
- 仓库根目录 `FOLLOW.UPS.md`（仍在生效的延期事项；启动检查时读取）

## 启动检查：延期事项

每次启动 `sdd-grill`，在分型和需求访谈前先检查仓库根目录 `FOLLOW.UPS.md`：

1. 文件存在时，读取全部行（表里只有 `待办` 与 `进行中`，没有已关闭项）；不存在时，创建包含表头与空列表说明的模板文件。
2. 对照当前请求检查每项的触发条件。向用户简要汇报已触发或相关事项；若触发条件已满足、当前需求可能覆盖该事项，或触发条件不明确，先问用户是并入当前 spec、另开 spec、明确延期到新的触发条件，还是取消。若所有待办都未触发且与当前请求无关，说明待办数量及“当前均未触发”。
3. 不因触发条件到期就自动把事项并入当前需求，也不得静默删除或改期。完成需有实现/验证证据，取消需用户明确决定；两者都成立后，**把该行从 `FOLLOW.UPS.md` 删掉**，完成证据写进对应 spec 的 `review.md`，取消理由写回该 spec 的「明确不做」或 `grill.md` 的决策。不保留已完成或已取消的行——那是活跃清单，不是历史记录。
4. 将本次已触发、相关或有用户处理决定的项写入 `grill.md` 的「待办登记」表；若没有这类事项，写明待办数量及均未触发/不相关。没有待办时写“FOLLOW.UPS 无待办项”。

表格字段：`ID`、`状态`（只有 `待办` / `进行中`）、`事项`、`来源 spec`、`触发条件`、`完成标准`。ID 使用 `FUP-NNN` 三位递增编号，从当前最大值 +1 生成；删除的编号永久作废、不复用，否则旧 spec 里的引用会指向另一件事。相同事项已存在时更新原记录，不重复新建。维持单一根目录文件，不引入 issue tracker、负责人、估时或截止日期。

## 阶段 0：分型

先判断这条需求的类型。**型判错，后面的问题就全问偏了。**

| 型 | 判定 | 典型说法 | 必读 |
|---|---|---|---|
| **新建** new | 系统里还没有这项能力 | "我要一个已有连接的列表页面" | 按 `steering.md` 查规范与设计、相似既有实现、可复用的组件 |
| **增量** extend | 在既有页面或 spec 上加能力 | "在 spec pNN-NNN 的基础上，给列表加删除" | 上游 `spec.md` 全文（R / 不做 / 边界）、相关代码与测试 |
| **修正** fix | 既有行为不对或不完整 | "删除应该显示成功，现在显示失败" | 当前实现、既有测试、谁在依赖现状 |

**判定护栏**：只要需求里提到了既有页面、既有功能或 spec 编号，**默认按增量处理**，除非人明确说要替换它。把增量当新建，会导致同一个能力被定义两遍。

### 增量/修正必问的一个问题

> 这次是**修订原 spec**，还是**在原 spec 之上的新交付**？
>
> A. **修订原 spec**：在原文件上改（`版本: v2`），将状态改回 `draft`；需求修订后由用户再次明确确认再进入下一步。
>   适合：原 spec 还没实现完，或这次只是补完遗漏。
> B. **新 spec + 引用上游**：新编号，头部写 `上游: pNN-NNN`，上游 spec 的 R 保持不变，本 spec 声明它取代/扩展了哪几条。
>   适合：上游 spec 已经实现并验收，这次是独立可验收的新能力。

这个选择的后果完全不同：A 会让旧批准失效，B 会让两个 spec 并存、需要维护引用关系。**不要替人决定。**

## 阶段 1：事实（有预算，不无限读）

| 型 | 预算 | 查什么 |
|---|---|---|
| 新建 | 8 次工具调用 | 按 `steering.md` 查相关规范与设计；相似能力怎么做的、有没有可复用的；本次会碰到的配置文件 |
| 增量 | 12 次工具调用 | 上游 spec 全文；相关代码与测试；上游的"不做"清单 |
| 修正 | 8 次工具调用 | 当前实现；覆盖该行为的测试；谁在依赖现状（夹具、文档、UI 入口） |

预算里**必须留出阶段 1.5 读规范条款的额度**。一次读不到的规范就分两次读；不要靠印象填写引用位置——`coding.md:163` 之类写错行号，比不写更糟。

产出两栏，**事实带出处**，写进 `grill.md` 的「## 事实收集」：

```text
已确认事实（file:line 或文档章节）
- 删除走 parentcascade 引擎，成功即提交（internal/app/connection/service.go:120）
- 已有列表页复用 shared/api/connections.ts 的分页封装

待定问题（必须由人决定）
- 部分失败时是否回滚
- 删完后列表是就地移除还是重新拉取
```

只列事实，不列方案。

**预算用尽 ≠ 阶段结束。** 用尽时不许把没查清的事塞进第 7 节——那是把 Agent 的工作丢给审阅人。必须做两件事：

1. 在「事实收集」里写「未读」清单：哪份文档 / 哪段代码没读、因此哪条结论**未验证**。
2. 只把**需要用户决定的行为或约束**留在「待定问题」；本可查清的事实（配置现状、字段取值范围、既有实现），要么继续查，要么明确标 `未验证` 并说明影响哪条 R。产品、技术、质量与测试方面的选择都可能需要用户决定，不因类别不同而自行挪到 plan。

**查不完时可以追加，但要人批。** 按阶段 2 的「撞上限怎么办」同样处理：说明还差哪几处、追加 4 次调用（`工具追加`），记进成本表；`+8` 是上限，再多就是 spec 边界没划清。

## 阶段 1.5：规范触碰扫描

**跳过这一步，冲突是否被发现就全看偶然。** 做一次清单，写进 `grill.md` 的「## 规范触碰」：

1. 按 `steering.md` 打开本 spec 会碰到的规范（`docs/standards/*.md`），逐条对：本 spec 的行为、文案、目录结构、依赖、命令，有没有和某条规范/约束冲突？
2. 每条给状态：`无冲突` / `冲突` / `不涉及`，并写规范原文位置。
3. **冲突项一律进访谈**，由人决定怎么处理（改规范 / 改需求 / 拆 spec），决策记进 `grill.md` 与 `spec.md` 第 6 节。

**规范冲突不许写进第 7 节。** 第 7 节是"需求本身有歧义"，规范冲突是"两处已写下的东西互相矛盾"——后者有答案，只是需要人拍板，属于访谈范畴。`tools/sdd_lint.py` 会拦住把冲突标成 §7 的写法。

若本 spec 完全不碰任何规范条款，在「规范触碰」里写一行 `无`。

## 阶段 2：访谈

按 [rules/dimensions.md](rules/dimensions.md) 推进，顺序**随型变化**：

| 型 | 先问 | 其次 | 可以少问 |
|---|---|---|---|
| 新建 | 用户与场景、首版边界、与既有能力的关系 | 失败语义、空与极值、权限、可逆 | 回归面 |
| 增量 | 与既有 R / 不做清单的关系、边界是否外扩 | 失败语义、老数据、回归面、可逆 | 用户与场景（通常已知） |
| 修正 | 正确行为的一句话定义、同源入口是否同样错 | 回归面、数据修复、失败语义 | 首版边界 |

**每个问题的格式**（不超过 3 行）：

```text
Q: 删除已提交，但随后刷新列表失败时，结果是成功还是失败？
   A. 成功，附一条警告 —— 用户不会去重试一个已经完成的删除
   B. 失败 —— 用户会重复删除，第二次报"不存在"
```

**规则**：

- 两个选项都必须是**具体行为**，不能是"更稳妥""更友好"这类形容词。
- **范围、数据影响、成本、不可逆**这四类问题不给推荐答案。推荐只用于实现方式。
- 回答含糊（"应该没问题""看情况"）→ 换成两个具体场景让人二选一。
- **每条候选 R 都要有反例，但反例不占问题预算**：浮现"必须做到"时，**Agent 自己先把反例写出来**，再请人否决——"这条会被这样违反吗？"。人只需要说"是/不是/还有一种"，不需要从零想。写不出反例，说明这条 R 本身没想清，回去重问这一条。
- **反向检查（每轮至少一次）**：列出 Agent 大概会顺手加的东西（配置项、重试层、二次确认弹窗），逐条问"要还是不要"。不要的写进第 5 节。
- **增量/修正专属**：逐条比对上游 spec 的第 4、5 节——"这次改的是哪条 R？上游'不做'里有没有一条正是你要做的？"后者必须由人显式推翻并给出理由。

**问题上限 = 本型必做维度数 + 3 次派生追问**：新建 12、增量 14、修正 9。

- 计数只算向人提的问题；**反例否决、事实核实、规范触碰扫描不计数**。
- 派生追问指访谈中途冒出的一次性澄清（拆分顺序、方案冲突），不算新维度。
- 数字必须写进 `grill.md` 成本表，`tools/sdd_lint.py` 会核对 `问题数 ≤ 上限 + 追加`。

### 撞上限怎么办（弹性，但不是自动放行）

上限是**停下**的触发点，不是**闭嘴**的触发点。问完第 12 个问题还没收敛时，做三件事：

1. **停。** 不要再问，也不要自己判断"再多三个就够了"。
2. **把这一问摆到人面前**（这一问本身不占预算）：
   > 预算用完了：必做维度已问完，还剩 N 个具体问题（列出它们）。
   > A. **拆**：这条需求本身就是两件事，按 <切法> 拆成两个 spec，各自重新起预算。
   > B. **追加**：这条确实是一件事，追加 4 问（`+4`），继续问完。
   拆与追加都是范围决定，**不给推荐答案**，让人选。
3. **记账。** 人选 B，就把追加额度写进 `grill.md` 成本表 `问题追加`，并把追加理由（谁批的、为什么不是两件事）写进 `追加理由`。

追加的硬约束（`sdd_lint.py` 全部核对）：

- 一次 `+4`，最多两次（`+8`）。**第三次必须拆**——`+12` 不是一个选项。
- 追加额度必须是一个确定的数，不能写"按需"、"视情况"。
- 有追加就必须有 `追加理由`；没有理由的追加等于静默放宽上限。

同样的机制适用于阶段 1 的工具预算（`工具追加`，同样 `+4` / `+8`）。事实查不清是常态，别让它变成"把问题丢进第 7 节"的理由。

### 决策日志

写 `grill.md`，追加式，一行一条：

```text
Q: 部分失败时，已删的连接要不要回滚？
A: 不回滚。删除已提交，跨库回滚不可行。
   放弃：事务回滚。
   何时重新评估：将来支持同库事务时。
→ R2 / §5
```

日志有两个用途：蒸馏出第 6 节；下一个 spec 碰到同一块领域时先读它，不重问。

### 延期事项登记

当用户明确决定把一项工作留到“下一个 spec”“下一次代码交付”或其它未来触发点时：

1. 确认它是未来要做的工作，而不是单纯的明确不做；后者只留在 spec 第 5 节。
2. 把触发条件和可判断的完成标准问清楚。含糊的“以后”“有空再做”不直接落盘，先向用户澄清。
3. 在当前 `grill.md` 记录决定，并立即将待办追加到仓库根 `FOLLOW.UPS.md`，填入 ID、待办、来源 spec、触发条件、完成标准、状态。不要等用户手工抄写。
4. 若该待办由当前 spec 的第 6 节“何时重新评估”触发，在 lint 前同步更新 `FOLLOW.UPS.md`，并在 `grill.md` 的「待办登记」表中记录待办 ID、本次检查/处理结果、来源决定和后续触发条件。
5. 不确定待办是否未来承诺时，问用户；不得把所有“明确不做”条目批量加入待办。

## 阶段 3：闸门

进组装之前必须全过。**不过闸门不许写 spec，写完必须跑 lint 且退出码为 0。**

闸门分两类：**脚本判定**的（下表上半）和**人判断**的（下半）。脚本判不了的，不许写成"看起来没问题"就算过。

| 闸门 | 判据 | 谁来判 | 不通过怎么办 |
|---|---|---|---|
| 头字段 | Spec / 类型 / 上游 / 附带交付 / Status / 版本六项齐全且取值合法；Spec 与目录名一致；不得残留批准凭据字段 | `sdd_lint.py` | 补齐、修正目录/编号或删除旧批准字段 |
| 结构 | 第 1–7 节标题齐全 | `sdd_lint.py` | 补齐 |
| 规模 | R 编号连续、1 ≤ 数量 ≤ 12 | `sdd_lint.py` | 拆需求 |
| 可测条目 | 每条 R 有 `**反例**` 与 `**可观察证据**` 且非空 | `sdd_lint.py` | 回去问 |
| 范围 | 每条「不做」带 `理由：` | `sdd_lint.py` | 补理由或删条 |
| 覆盖面 | 覆盖矩阵的维度集合正好等于本型必做集合；`不适用` 带理由 | `sdd_lint.py` | 回去问 |
| 自证拦截 | 第 7 节列出的待决维度，矩阵不得写「已覆盖」 | `sdd_lint.py` | 回去问，或承认该维度没覆盖 |
| 第 7 节格式 | 每条待决问题带 `维度：<ID>` + A/B 两个具体选项 | `sdd_lint.py` | 补选项，或回访谈 |
| 规范触碰 | `grill.md` 有「规范触碰」清单；冲突项不得标成第 7 节 | `sdd_lint.py` | 回访谈解决冲突 |
| 成本基线 | 成本表十一项齐全；`问题数 ≤ 上限 + 追加`；追加是 `+4` / `+8` 且有理由；工具调用同理；类型与 spec 一致 | `sdd_lint.py` | 撞上限就停下问人：拆，或追加 +4 |
| 附带交付 | 头部登记的 R# 存在且带 `**范畴**`；标了范畴的 R 必须登记 | `sdd_lint.py` | 补登记或去掉标记 |
| 延期待办 | 启动时检查全部活跃项；本次明确延期到未来的工作已登记在根目录，用户处理结果写入「待办登记」；已关闭的行已删除 | 人 | 补登记或明确触发条件 |
| 尺寸 | `spec.md` 第 1–6 节读得完（约 200 行内），R 条数不靠堆 | 人 | 删废话，不动 R |
| 可测性 | 每条 R 能用一句"条件 + 行为 + 结果"说清 | 人 | 回去问 |
| 诚实 | 没有把可查的事实写成"待定问题"；没有为凑齐闸门而写空话 | 人 | 回阶段 1 补查 |

退出码 0 才算过。**lint 有 FAIL 时不许交付 spec，也不许用文字解释"这条其实没问题"绕过**——改文档，或改 lint 并说明为什么规则本身错了。

### 校验脚本怎么跑

脚本随本 skill 一起分发，是 `tools/sdd_lint.py` 一个文件，**不依赖被审项目的语言、框架或构建系统**：纯 Python 3.8+ 标准库，无第三方包，无需安装。文件内按「形状常量 / 解析 / 结果容器 / spec 检查 L01–L07 / grill 检查 L08–L10 / 入口」分段，改规则时按段找。

- 路径按 skill 自身位置引用，**不要拷进项目目录**：`python .agents/skills/sdd-grill/tools/sdd_lint.py <spec 目录>`。POSIX 上把 `python` 换成 `python3`。
- 退出码：`0` 全过 / `1` 有 FAIL / `2` 用法错误或 `spec.md`、`grill.md` 缺失。读退出码，不要靠读输出判断。
- 维度 ID、预算、上限是**本 skill 的规则**，写在 `rules/dimensions.md` 与脚本顶部的「形状常量」段两处，改一处必须同步另一处。

## 阶段 4：组装

1. 用 [templates/spec.md](templates/spec.md) 写 `spec.md`，用 [templates/grill.md](templates/grill.md) 写决策日志。
2. 路径约定：`specs/pNN-NNN-<英文短横线slug>/spec.md`。`pNN` 是两位阶段号（取 `specs/` 下现有目录中最大的阶段号），`NNN` 是该阶段内三位序号，从 `001` 起；新 spec 取当前阶段最大编号 +1。决策日志同目录 `grill.md`。
3. 第 7 节只写真正未决的问题，每个带两个选项与 `维度：<ID>`。
   **好的访谈之后第 7 节应该接近为空**——如果里面还有"这个需求是否完整""是否有风险"，说明访谈没发生。
4. 跑 `tools/sdd_lint.py`，退出码 0。不过就改，不许解释。
5. **停。** 不写 `plan.md`，不生成任务，不改代码；简要汇报 lint 结果与未决问题，并问用户是否确认需求、可以进入下一步。

### 批准怎么记

批准的唯一门槛是**用户明确确认需求可以进入下一步**：

1. Agent 交付时 `Status` 为 `draft`。Lint 通过只说明文档结构合格，不能推断用户已批准。
2. 用户明确回答“需求 OK，可以进入 plan/下一步”后，Agent 将 `Status` 改为 `approved`，再继续流程。不要求用户编辑文件、创建 tag、制作专用 commit 或提供其它批准证据。
3. 含糊表达不算批准；若用户只说“看起来不错”但未表达是否继续，简短询问一次。用户明确拒绝或要求修改时保持 `draft`。
4. `approved` 后需求内容视为冻结。若用户之后要求实质修改需求、边界或决策，版本 +1、状态回到 `draft`；用户再次确认后再设为 `approved`。纯排版或不改变意思的勘误不重开批准。若已有 plan 受影响，将其标记为 `stale`。
5. `Status` 是流程状态，不是批准凭据；不需要核验 Git tag、commit 或 diff。

## 输出说明

给人看的四行，不要长：

1. **结论**：一句话需求描述 + 类型 + R 的条数（增量/修正附 `上游: pNN-NNN`）
2. **闸门**：`sdd_lint.py` 的退出码与通过项数 + 维度覆盖情况（覆盖 x / 不适用 y）+ 遗留问题数
3. **成本**：问题数 / 上限（有追加就写 `+4`）、工具调用 / 预算
4. **下一步**：请用户读第 1–6 节，并明确确认是否进入下一步；如有未决问题，只列出需要用户决定的那几条；同时报告本次新增或触发的 FOLLOW.UPS 项

lint 有 FAIL 时不发这段总结——先把 FAIL 改掉。

## 异常与兜底

- **人不想被访谈**（"你直接写吧"）：不假装完整。产出"已知 + 未知"清单，`spec.md` 标 `Status: draft`，顶部写明哪些维度没访谈。允许跳过，但必须可见。
- **事实查不到**：写进「待定问题」，标注"未验证"。不要用"常见做法"填空。
- **预算用尽**：不静默收工。在 `grill.md`「事实收集」写「未读」清单 + 它让哪条结论悬空，然后在输出里明说。可查的事实不许改道进第 7 节。
- **回答暴露新范围**：不擅自加进 R。写进第 5 节或"将来再说"，由人显式提升。
- **发现其实是两条需求**：停下，说明按什么切，等确认后再继续。一条 spec 里塞两个目标，第 7 节会立刻失控。人若坚持并成一个，交错的那些条目必须带 `**范畴**` 并登记进「附带交付」。
- **需求提出者自己也说不清**：允许退化成"只定义问题、不定义方案"的草稿，但必须在顶部标明它还不完整。
- **访谈超上限**：停下，把「拆」与「追加 +4」两个具体选项摆给人，不许自己决定，也不许把超出的问题挪进第 7 节。追加最多两次。
- **lint 与判断冲突**：先按 lint 改。若确认规则本身错了，改 `tools/sdd_lint.py` 里对应的检查函数（`check_spec` 判 spec，`check_grill` 判 grill）并在输出里说明改了什么——不许留一个"大家都知道的例外"。

## 下游契约（给 sdd-plan）

`spec.md` 必须提供下面七样，否则 plan 阶段必然要靠猜：

1. **R 列表**：编号稳定、可观察、带反例——plan 用它造验收项与测试。
2. **明确不做**：plan 用它划边界，并据此判定"顺手加的功能"。
3. **上游与影响面**：plan 据此安排回归测试；若无上游则写明"无"。
4. **第 6 节决策**：plan 不得推翻。必须推翻时回 spec 重开，不允许在 plan 里改主意。
5. **第 7 节遗留问题**：plan 遇到这些必须停下问人，不得自行选择。
6. **附带交付**：头部登记的 R# 与它们的 `**范畴**`。plan 据此把"改代码"和"改规范 / 文档 / 契约"分成两组任务与两组验证——它们不是一件事，不许混在一个任务块里。
7. **成本基线**：`grill.md` 成本表。后续所有"更轻""更快"的判断都要跟它比，没有基线就没有优化。

反过来说，文件清单、接口签名、任务拆分、具体测试命令和验收脚本默认属于 `plan.md`；但用户明确指定某项命令、测试行为或实现约束作为必须满足的要求时，必须保留在 `spec.md`，plan 负责执行它。
