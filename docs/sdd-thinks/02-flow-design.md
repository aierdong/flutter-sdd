# 自建流程的设计

## 三条原则

1. **人批准意图，Agent 用证据证明没有越界。**
   人判断"做什么、为什么、做成什么样、不做什么、代价是什么"；技术选择与实现细节归 Agent，但技术选择的**重大后果**（数据、成本、不可逆、外部调用）必须回到人面前。
2. **一个 spec 只解决一个可独立验收的问题。**
   发现是两件事，先拆。这条一破，后面的审阅区就没法用一句话说清。
3. **审阅区与服务区分开。**
   审阅区给人读，执行区给 Agent 用；两者用同一套 `R#` 编号互指。

## 两个产物，为什么是两个文件

早期方案是"一个文件、两个区（第 1–7 节审阅区 + 第 8–13 节执行区），批准只绑定审阅区"。**这个方案后来被推翻了**，理由有三：

- **会自己长胖。** 执行区写全了通常 150–400 行，加上审阅区就是 300–500 行，恰好毁掉"在一个地方读一件事"的初衷。
- **diff 难读。** 执行区每次更新，审阅区的 diff 上下文都被撑开，人眼很难确认"审阅区没被动过"。
- **token 成本。** 如果同文件，每个任务都要重读整个审阅区。

所以改成：

```text
specs/pNN-NNN-<slug>/
├── spec.md      审阅区：第 1–7 节
├── plan.md      执行区：第 8 节起
└── grill.md     决策日志（可选，不进入审批必需物）
```

`spec.md` 头部写 `Approved: <sha>`，`plan.md` 头部写 `Based-on: <sha>`；两个值相等，说明执行版对应当前批准。

## 批准怎么绑定内容

**批准动作 = 人提交一个只改审阅区的 commit。**

```text
Agent 写完审阅区 → 停下
人读完、改完、自己 commit（只包含 spec.md 的审阅区）
该 commit 的 SHA 就是批准的版本
Agent 生成执行区前先校验：该 commit 之后审阅区内容未变
```

为什么用 git 而不是自己算内容指纹：

- 天然带作者、时间、内容三元组；
- 失效判定是现成的（`git diff <approved_rev> -- spec.md`），不需要设计哈希算法，也绕开"空白字符算不算改动"；
- **不可伪造**：Agent 可以写文件，但"人读过并认可"只在人真的提交时成立。

配套硬规则：

- **Agent 不得创建、不得修改、不得代签批准 commit。**
- 审阅区内容一变，旧批准立即失效，旧 `plan.md` 标 `stale`，实现入口拒绝执行。
- 改的是原 spec 还是新开一个 spec，必须问人，不替人决定（见 `03-sdd-grill.md`）。

## `R#` 编号：规格里唯一强制结构

第 4 节"必须做到"用 `R1`…`Rn`，每条三行：

```markdown
- [ ] **R1** 删除实际成功后，确认结果必须报告成功。
  - **反例**：删除已提交，但后续读取已删父级失败时返回 BLOCKED。
  - **可观察证据**：界面显示成功，并附一条"刷新失败"的警告。
```

三条理由：

- **没有编号，"依据"指不到地址。** 任务要写"依据 R1、R2"、测试计划要写"验收项"、完成定义要逐条给证据。
- **反例是"想透了"的可见证据。** 审阅者不用问"这条想清楚了吗"，看反例就知道。说不反例的条目不算想清楚。
- **可观察证据把实现细节挡在外面。** 写"人能观察到什么"，不写测试名、不写命令。

增量/修正若改变了上游已批准的条目，加 `**取代**：001 R5`。

## 第 7 节为什么应该接近为空

第 7 节"审阅问题"只放**真正未决、需要人决定**的问题，每个带两个选项和各自后果。

好的需求访谈之后，它应该几乎为空。如果里面还堆着"这个需求是否完整""是否有风险"，说明访谈没有发生，只是被跳过。这是一个可以直接自查的质量信号。

## 三类暂停条件

执行阶段一旦命中，停下回到审阅区，**不许写进执行区就继续做**：

| 触发 | 例子 |
|---|---|
| 新增用户可见行为 | 顺手加了"删除前二次确认" |
| 新增代价 | 新依赖、新外部调用、新计费、数据迁移、不可逆删除 |
| 改变已批准的范围 | 原来"不做批量删除"，实现时发现需要 |

## 完成 = 证据矩阵，不是勾选

- 每条 `R#` 都有对应验证结果（命令 + 退出码，或人工步骤 + 观察结果）。
- 必需测试未运行 / 被跳过 / 环境不可用的，不得记为完成，如实报告"未验证"。
- 实际改动没有超出批准边界。
- 交付说明包含用户可以自己复核的步骤，而不是"已完成"三个字。

**任务勾选是进度记录，不是完成证明。**

## 四段流程与产物契约

| 阶段 | 输入 | 产出 | 通过条件 |
|---|---|---|---|
| `sdd-grill` | 一条需求描述 | `spec.md`（第 1–7 节）+ `grill.md` | 人批准，`Status: approved` + 批准凭据 |
| `sdd-plan` | 已批准的 `spec.md` | `plan.md` | 每条 R 都有设计、任务与验证；无待决问题；自检矩阵通过 |
| `sdd-impl` | 有效 `plan.md` | 代码、测试、命令输出 | plan 中每个任务的验证通过 |
| `sdd-review` | 全部产物 | `review.md` | 结论有证据；不通过则回到最靠前的失效步骤 |

`spec.md` 欠 `plan.md` 五样东西（访谈技能的下游契约）：R 列表、明确不做、上游与影响面、第 6 节决策、第 7 节遗留问题。

反过来的边界同样重要：文件清单、接口签名、任务拆分、测试命令、验收脚本**不属于** `spec.md`。

## 成本策略

### 成本结构是四个乘法器

```text
总消耗 ≈ Σ（每个 agent 的每一步 × 该步的上下文大小）
```

四个乘法器：**agent 数量**、**每 agent 步数**、**每个 agent 启动时的基线上下文**、**重试轮次**。

规则文本只影响第三项的一小块。所以排序是：

```text
删除重复验证 > 减少评审 agent > 压缩基线上下文 > 精简规则文本
```

（测量数据见 `04-decisions.md` 的"已核实事实"。）

### 关键发现：写在文档里的规则不生效

原仓库早有一份《执行效率》指导，明确写了"命令只发现一次、不重复跑、避免重复全文件读取、事件驱动等待"。慢和贵依然存在。

结论：

> 写在文档里的规则，只在被读到的那一次生效；写进脚本、模板和预算数字的规则，才一直生效。

根因是**验证指令是无条件的，效率指令是建议性的**。Agent 没法因为"这条命令已经跑过"而免责，但能因为"我又验了一遍"而免责。

### 证据按代码树指纹复用

```text
tree_stamp = HEAD + 工作区 diff 的 hash
```

1. stamp 未变 → 已有 PASS 证据对后续步骤继续有效，不重跑。
2. stamp 一变 → 全部证据作废。
3. **失败结果永不复用。**
4. 缓存键必须覆盖影响结论的全部参数（档位、边界、跳过项）。

"新鲜"的定义是"树变了没有"，不是"换了个评审者"。这一条把测试运行次数从"每任务 3 次"降到"每任务 1 次 + 规格末 1 次全量"，严格性不降。

### 验证只放在三个时刻

| 时刻 | 跑什么 | 成本 |
|---|---|---|
| 每次编辑后 | 受影响包的测试 | 秒级 |
| 每次提交前 | 构建 + 静态检查 + 受影响包测试（一个脚本） | 十几秒 |
| 每个 spec 结束 | 全量测试 + 运行时存活 | 分钟级，只一次 |

删掉"每个任务评审时跑全量"。

### 上下文包，不是文件路径

子代理拿到的不该是"去读三份文档"，而是一段 800 token 以内的上下文包：任务块 + 相关 R 原文 + 文件清单 + 检查命令。

**执行版本身就是上下文包。** 所以拆 `spec.md` / `plan.md` 不只是可读性问题，也是 token 问题。

### 评审按风险触发

| 改动内容 | 评审方式 |
|---|---|
| 迁移、数据模型、跨模块接口、并发、外部 IO、安全 | 逐任务评审 |
| 纯新增、UI、文案、测试补充、单文件内聚改动 | 批量终审一次 |

判定依据是 diff 的文件路径与符号，不是任务描述的自我申报。

### 进入实现前的预算

> 最多 5 次工具调用：读任务块 → 跑一次检查脚本 → 读 1–2 个关键文件 → 看 `git status`。
> 超出，说明任务切分或边界不清：回到拆分，不要在探索里追加预算。

### 不能砍的四项

1. 契约与边界检查
2. 错误路径测试
3. 数据安全（迁移、删除、覆盖）
4. 运行时能启动

设计评审也不砍——设计错了会让所有任务白做。

## 与 Kiro 的关系：只借机制，不借结构

| 保留 | 放松 | 新增 |
|---|---|---|
| 基于真实代码而不是想象；边界显式；复用已有能力；前置条件显式；任务有可验证交付物；独立评审；新鲜证据；失败归因上游；单一权威来源 | 固定英文验收句式；三份阶段文档；三次阶段审批；任务禁止写文件路径；机械套用"1–3 小时" | 双视角双文件；批准绑定 commit；`R#` + 反例；三类暂停条件；完成=证据矩阵；按 tree stamp 复用证据；风险触发评审 |

## 还没被验证的假设

诚实列出，避免当成结论：

- 一个人用"人批准意图"的模式，是否真的比三次审批更少出错——**未验证**。
- `R#` + 反例是否会让审阅区变得过长——**未验证**，12 条上限是拍脑袋的。
- 门禁分级（轻 / 标准 / 重）的判定是否可靠——**未设计完**，且新仓库 `AGENTS.md` 暂未采纳。
- Flutter 项目里 `flutter test` 的全量耗时是否支持"每 spec 一次"——**未测量**。
