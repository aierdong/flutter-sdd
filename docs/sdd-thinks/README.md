# SDD 流程改造：思考与交接

> **归属**：本目录属于「SDD 流程重建」这项工作，**不是 Flutter Demo 的项目知识**。
> 两个项目共用这个仓库：Flutter Demo 是验证本流程的载体，本目录是流程本身的设计与结论。
> 所以这里不登记进 `steering.md`，也不该在写 Flutter 代码时被当成项目规范引用。
>
> 这份目录是一次跨会话讨论的存档：为什么改、改成了什么、哪些还没定、下一步做什么。
> 历史材料（Kiro 译文、机制分析、早期提案）在 `../kiro-spec/`，只作参考，**不再维护**。
> 需要判断时，以本目录的结论为准。

## 十分钟速览

**起点**：Kiro 式 SDD 对个人开发者太重，三份文档（requirements / design / tasks）为 Agent 优化，人读不动，只能机械点同意。

**诊断**：问题不在文档数量，而在于——

- 产物按**工程阶段**切，不按**读者**切；
- 审批字段记的是"批准过"这个状态，不记"批准的是哪一版内容"，所以批准可以被继承，人就不必真的读；
- 质量机制保的是**文档形状合格**，没有机制保"人真的看懂了"。

**方案**（四段流程，一个 spec 只解决一个问题）：

```text
sdd-grill   →  spec.md + grill.md   审阅区，人批准
     ↓
sdd-plan    →  plan.md              执行区，机器自检
     ↓
sdd-impl    →  代码 + 测试 + 证据
     ↓
sdd-review  →  review.md            结论
```

**现状**：

| 部分 | 状态 |
|---|---|
| 四段流程的骨架 | 已定（`AGENTS.md`） |
| `sdd-grill` 设计 | 已定，草案在 `../kiro-spec/skills/sdd-grill/` |
| `spec.md` 模板 | 已定，草案在 `../kiro-spec/templates/spec.md` |
| `sdd-plan` / `sdd-impl` / `sdd-review` | 未设计 |
| 检查脚本（证据复用） | 有 Go 版原型，需移植到 Flutter |
| 第一个 spec | 未开始 |

**下一步**：先跑一次 `sdd-grill`，把「连接 → 树 → 表详情」拆成可独立验收的 spec，用真实访谈验证模板能不能支撑判断。

## 与 Flutter Demo 的关系

两个项目共用这个仓库，但不是一回事：

| | SDD 流程重建（本目录） | Flutter Demo |
|---|---|---|
| 是什么 | 流程本身：原则、技能、模板、审批与验证机制 | 流程的第一个使用者与验证载体 |
| 权威文档 | 本目录与 `.agents/skills/` | `AGENTS.md`、`project.md`、`steering.md` |
| 变更驱动 | 流程跑得不顺、判断失真 | 验证中发现流程问题 |

`AGENTS.md` 里的四段流程与通过条件，是**本目录设计的一次采用实例**，不是它的上游。流程设计的改动发生在这里，再由人同步到 `.agents/skills/` 与 `AGENTS.md`；反过来（为了 Flutter 跑得快而改流程定义）不成立，除非这个改动对流程本身也成立。

落到「本目录管什么、Flutter 管什么」，见 `05-next-steps.md`：那里写的迁移与适配动作，属于把流程产物放进第一个使用者，而不是把 Flutter 项目变成流程的主场。
