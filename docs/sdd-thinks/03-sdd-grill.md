# sdd-grill：把一条需求问透

> 草案：`../kiro-spec/skills/sdd-grill/SKILL.md`、`rules/dimensions.md`
> 模板：`../kiro-spec/templates/spec.md`
> 迁入新仓库前需要按 `AGENTS.md` 调整，清单见 `05-next-steps.md`。

## 为什么单独设计这一步

需求阶段的返工有两类，成因不同：

- **维度没被打开**：部分失败、空值、并发、可逆性——不是问得不够深，而是整根枝从来没长出来。
- **上下文没接上**：不知道已有页面怎么工作，不知道上一个 spec 说过"不做"，于是新需求在暗处推翻了旧决定。

所以这里不做"更狠的追问"，而是三件事：**先分型 → 强制开枝 → 过了闸门再组装**。

## 与已有 skill 的分工

| skill | 它做什么 | 为什么不能直接用 |
|---|---|---|
| `grilling` | 12 行的访谈引擎：一次一问、每问给建议、事实自己查、决定归人 | 没有产物、没有退出条件、没有覆盖面保证 |
| `grill-me` | `grilling` 的触发别名 | 同上 |
| `brainstorming` | 项目级设计：拆分、2–3 个方案、写设计文档 | 管"做成什么系统"，不管"这一条需求要什么" |

`sdd-grill` 的差异化不在提问风格，而在**产物契约**（`spec.md` 第 1–6 节 + `grill.md`）和**覆盖矩阵**。

## 三次演进

| 版本 | 范围 | 被改掉的原因 |
|---|---|---|
| v1 | "把一次改动问透" | 范围太窄：新需求（还没有既有页面）无处安放 |
| v2 | "把一条需求问透"，分新建/增量/修正 | 仍与 Kiro 流程绑定（保留了对应表、EARS 术语） |
| v3（当前） | 独立轻量 SDD 的第一段，四段流程之首，明确下游契约 | — |

## 三型判定

| 型 | 判定 | 典型说法 | 必读 |
|---|---|---|---|
| **新建** `new` | 系统里还没有这项能力 | "我要一个已有连接的列表页面" | 项目约定、相似既有实现、可复用组件 |
| **增量** `extend` | 在既有页面或 spec 上加能力 | "在 spec 001 的基础上，给列表加删除" | 上游 `spec.md` 全文（R / 不做 / 边界）、相关代码与测试 |
| **修正** `fix` | 既有行为不对或不完整 | "删除应该显示成功，现在显示失败" | 当前实现、既有测试、谁在依赖现状 |

**判定护栏**：需求里只要提到既有页面、既有功能或 spec 编号，**默认按增量处理**，除非人明确说要替换。把增量当新建，会让同一个能力被定义两遍。

### 增量/修正必问的一个问题

> 这次是**修订原 spec**，还是**在原 spec 之上的新交付**？
>
> A. 修订：在原文件上改，版本递增，旧批准立即作废，重新走一次批准。
> B. 新 spec + 上游引用：新编号，头部写 `上游: 001`，`001` 的 R 保持不变，本 spec 声明取代了哪几条。

两者后果完全不同（旧批准失效 vs 两个 spec 并存维护引用），**不替人决定**。

## 事实收集有预算，不无限读

| 型 | 预算 | 查什么 |
|---|---|---|
| 新建 | 5 次工具调用 | 相似能力、可复用组件、相关约定 |
| 增量 | 8 次 | 上游 spec 全文、相关代码与测试、上游"不做"清单 |
| 修正 | 5 次 | 当前实现、覆盖该行为的测试、谁在依赖现状 |

产出两栏：**已确认事实（带 file:line）** 与 **待定问题（必须由人决定）**。只列事实，不列方案。预算用完还没查清，把剩下的写进"待定问题"。

## 访谈规则

- **一次一问**，每问不超过 3 行。
- 每个问题给**两个具体行为**作为选项，不给"更稳妥""更友好"这类形容词。
- **范围、数据影响、成本、不可逆**四类问题**不给推荐答案**。推荐只用于实现方式。
  理由：原版 grilling 每问都给建议，在需求访谈里会制造新的机械同意——人还没想清楚，已经有个"专业答案"摆在面前。
- 回答含糊（"应该没问题""看情况"）→ 换成两个具体场景二选一。
- **每条候选 R 都要问反例**："什么情况下这条会被违反？"说不出来就是还没想清楚。
- **反向检查（每轮至少一次）**：列出 Agent 大概会顺手加的东西（配置项、重试层、二次确认弹窗），逐条问"要还是不要"。
- **增量/修正专属**：逐条比对上游第 4、5 节——改的是哪条 R？上游"不做"里有没有一条正是这次要做的？后者必须由人显式推翻并说明理由。

**问题上限**：新建 12 问、增量 8 问、修正 5 问。超限说明该拆需求，而不是继续问。

## 决策日志 `grill.md`

追加式，一行一条：

```text
Q: 部分失败时，已删的连接要不要回滚？
A: 不回滚。删除已提交，跨库回滚不可行。
   放弃：事务回滚。
   何时重新评估：将来支持同库事务时。
→ R2 / §5
```

两个用途：蒸馏出第 6 节；下一个 spec 碰到同一块领域时先读它，不重问。它**不进入审批必需物**——人审的是 `spec.md` 第 6 节的表格。

## 闸门

进组装之前必须全过，不过闸门不写 `spec.md`：

| 闸门 | 判据 |
|---|---|
| 覆盖面 | 本型要求的维度各有"已覆盖"或"不适用 + 理由" |
| 可测性 | 每条 R 有反例，且能用一句"条件 + 行为 + 结果"说清 |
| 范围 | 每个"明确不做"有一条理由 |
| 规模 | R 不超过 12 条 |
| 上游 | 增量/修正有 `上游` 字段与被取代条目；推翻上游"不做"有理由 |
| 遗留 | 未答问题要么有答案，要么明确进第 7 节 |

机械核对：把维度矩阵与 R 列表并排看一遍，任何一格空着就是漏。

## 组装

1. 用模板写 `spec.md`，路径 `specs/pNN-NNN-<slug>/spec.md`。
2. 第 7 节只放真正未决的问题。
3. **停。** 不写 `plan.md`，不生成任务，不改代码。等人批准。

## 三型的必问维度（摘要）

完整问题库见 `../kiro-spec/skills/sdd-grill/rules/dimensions.md`。

**通用六维度**：失败与部分失败、边界与既有行为、空与极值、并发与顺序、权限与密钥、可逆性。

**新建专属**：首版边界（没有边界的"新需求"会长成平台）、用户与场景、与既有能力的关系（复用还是另起）。

**增量专属**：与既有 R 的关系、上游"不做"是否被推翻、边界是否外扩、老数据与老用户、回归面。

**修正专属**：正确行为的一句话定义、同源入口、已产生的错误数据、谁在依赖现状。

**次级维度（按需）**：触发者与入口、数据留存、对外契约、时间与外部依赖、观测与文案、多目标差异。

## 已知风险

- **访谈疲劳**：问 12 个问题对小事是负担。缓解：型与预算挂钩；轻改动允许退化（但必须在 `spec.md` 顶部标注"未访谈维度"）。
- **锚定效应**：即使不给推荐答案，问题的措辞仍会引导。缓解：四类问题强制中立的两个选项。
- **模板膨胀**：`R#` + 反例 + 可观察证据会让第 4 节变长。缓解：12 条上限；反例不超过一行。
- **"不适用"被滥用**：填"不适用"比想清楚省事。缓解：不适用必须带理由，理由要具体到"为什么这个维度在本需求里不存在"。
