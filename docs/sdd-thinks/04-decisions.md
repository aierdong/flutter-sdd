| D1 | 审阅区与执行区分成两个文件（`spec.md` / `plan.md`） | 同文件会膨胀、diff 难读、每任务重读审阅区 | `02-flow-design.md` |

| D4 | 第 7 节应接近为空 | 好的访谈之后，剩下的问题应该很少 | 同上 |

| D16 | 四段流程：grill → plan → impl → review | 每段一个产物、一个通过条件 | `AGENTS.md` |

## 被推翻或改掉的方案

| 原方案 | 改成 | 为什么 |
|---|---|---|
| 一个文件、两个区（审阅区 + 执行区），批准绑定审阅区 | 两个文件 | 执行区会把文件撑到 300–500 行；diff 难确认审阅区没变；每任务重读审阅区 |
| 一次改动 → 一条需求，分三型 | 分三型 | 新需求没有"改动"可指，旧范围装不下 |
| 与 Kiro 流程的对应表 | 删除 | 新流程是独立的轻量 SDD，只借机制不借结构 |
| `grilling-spec-requirements` 命名 | `sdd-grill` | 名字里的 requirements 会让人以为它产出 `requirements.md` |
| 每问都给推荐答案 | 范围/数据/成本/不可逆四类不给 | 会给"人还没想清楚就先看到专业答案"的锚定 |
| 模板放仓库级 `templates/`，skill 用相对路径引用 | 按新仓库 `AGENTS.md`：模板放技能自己的 `templates/` 下 | 每个技能自包含，迁移不用改链接 |

## 已核实的事实

原仓库（`loomidbx-v3`）实测，用于支撑成本判断：

| 事实 | 数据 |
|---|---|
| Kiro skill 文本量 | 19 个 `SKILL.md` 共 155k 字符（≈39k token） |
| 共享规则文本量 | 17 个 `rules/*.md` 共 81k 字符（≈20k token） |
| 项目约定文本量 | 13 个 steering 文件共 123k 字符（≈31k token） |
| 一次 impl 开场开销 | ≈18–22k token |
| 一个 spec 的四份文档 | 16.9k 字符（≈4.2k token） |
| 测试规模 | 1079 个 `*_test.go`，仓库无 Makefile → 全量 `go test ./...` 是分钟级 |
| 任务规模示例 | 一个 spec 31 个子任务，另一个 15 个 |

检查脚本原型（Go 版）实测：

| 场景 | 结果 |
|---|---|
| 首次运行（冷编译） | `go build ./...` 61.9 秒，其余按需跳过 |
| 同一代码树再跑 | 命中缓存，< 1 秒 |
| 边界收窄 | 重新执行并正确报出"越界 2 个文件" |
| 仅文档改动 | build / vet / test 全部跳过，整次 < 1 秒 |

对照样本 p0-48（原仓库的一个小修复）：

- 事实：命名父级级联删除已提交，但后续读投影失败时，结果被报成 `BLOCKED`。
- 修法：提交成功后直接返回 `SUCCEEDED`，不再读投影；同时保留"提交前诊断仍为 BLOCKED"的测试。
- 规模：2 条验收条件、2 个子任务、`fast` 档位。
- 测试位置：`internal/app/schemaimpact/cascade_parent_branch_test.go`（断言"不得包含 IMPACT_PREREQUISITE_MISSING"）。
- 结论：这类问题适合做流程试点——小、纯错误路径、用户可观察、不碰持久化结构。

翻译工作核对：五个核心 skill 的中文译本与原文章节数一致（各多一节"技能元信息"）；所有相对链接可解析。

## 教训

1. **写在文档里的规则不生效。** 原仓库早有一份执行效率规范写得完全正确，慢和贵依然存在。规则必须落到脚本、模板字段或数字预算上。
2. **缓存键必须覆盖影响结论的全部参数。** 检查脚本第一版忘了把 `-Boundary` 纳入缓存键，结果"更窄的边界"复用了"更宽边界"的 PASS——比不缓存更危险。
3. **不要复述对话里的断言，去核实。** 早期文档里"两个 skill 副本已经漂移"的说法，核实后发现那个目录根本不存在。写进文档前先 `Test-Path` / `git log`。
4. **访谈期间不要起草文档。** 一旦开始写，提问就会停。这是长会话里最稳定的退化模式。
5. **表"完成"要区分证据与记录。** 勾选、状态字段、"已检查"的自我声明，都不是证据。
