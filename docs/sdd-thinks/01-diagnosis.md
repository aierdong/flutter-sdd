# 起点与诊断

## 当时的两个痛点

原话大意：

1. requirements / design / tasks 分成三份，对个人全栈开发者不友好。读一个地方总要关联另一个地方。
2. 这三份文档完全是为 Agent 准备的：精准，但术语密集、短句混杂着需求、契约、状态、边界和验证，不适合人评审。

后果说得很准：**开发者只提供初始需求，然后机械地点同意，最后发现代码失控。**

## Kiro 实际上是怎么运转的

读它的五个核心 skill 与共享规则后，机制可以概括成六层：

| 层 | 机制 | 作用 |
|---|---|---|
| 1 | 模板即 schema | 让"缺内容"变成可检测的形状（边界四节、File Structure Plan 等） |
| 2 | 机械检查先于判断 | 数字 ID、验收条件、实现词扫描、追溯覆盖、孤儿组件、测试档位 |
| 3 | 编号即契约 | 同一需求 ID 贯穿需求 → 设计 → 任务 → 校验，明令禁止自造别名 |
| 4 | 边界三段式 | Boundary Candidates → Commitments → `_Boundary:_` → Violations |
| 5 | 单一权威来源 | 同一事实只有一处可改，其余引用 |
| 6 | 新鲜证据 + 独立视角 | 只认结构化结论；评审者自己看 diff；证据必须来自当前代码 |

另外还有一条执行纪律很关键：**草稿只存在于工作记忆，门禁通过才落盘**。所以磁盘上永远只有"曾经合格"的版本。

这套机制在"文档质量"上是有效的，甚至可以说做得很好。

## 但它在为什么样的读者优化

四件事决定了它不适合一个人用：

**1. 产物按阶段切，不按读者切。**
判断一件事做得对不对，要同时打开三份文档，在编号之间跳。对多人团队有价值（需求给产品、设计给架构、任务给执行者），对一个人只是把同一件事拆成三个入口。

**2. 语言为机器压缩。**
固定英文句式 + 本地化变量，产出必然是中英混排的标准化条款。每条都对，读完不知道"用起来是什么感觉"。

**3. 门禁密度高，但批准不绑定内容。**
`spec.json` 里的审批只有布尔值：

```json
"approvals": { "requirements": { "generated": true, "approved": true } }
```

它记录"批准过"，不记录"批准的是哪一版"。文档改一版，旧的 `approved: true` 依然为真。**批准因此可以被继承，人自然不需要真的读。** 这是"机械同意"的机制根源，不是态度问题。

**4. 质量保障的对象是文档形状，不是人的理解。**
六层机制里，只有独立评审勉强触及"设计是否合理"，其余全部在保"完整、对齐、写全"。所以流程越跑越熟，人的参与感越弱。

## 结论

> Kiro 用一套组合拳把 spec 的**形式质量**做到了可重复、可判定、低争论。
> 它没有解决的是：产物服务的是阶段和 Agent，不是审阅者；审批记录的是状态，不是内容。

所以改造方向不是"减少文档"，而是两句话：

1. **从按阶段组织文档，改为按读者需要组织信息。**
2. **从人反复批准技术产物，改为：人批准意图，Agent 用证据证明没有越界。**

## 后来补上的第三个问题：成本

讨论进行到一半时浮现出来的问题：这套流程**太慢、太贵**。任务开始一小时还没改一行代码，一个完整 spec 消耗惊人数量的 token。

诊断见 `02-flow-design.md` 的"成本策略"一节。一句话版本：

> 验证的频率应该跟"缺陷发现得越晚、修复成本越高"的斜率走，而不是跟流程阶段的完整性走。

## 一个判断成功的标准

改造是否成功，不看"文档从三份变成一份"，而看：

> **你读完审阅区后，能主动说出一个 Agent 没想到的取舍。**

如果每次读完只想说"可以"，流程还要再改——问题不在文档长度，在你没有被要求做真正的判断。
