## 一、当前 Kiro 流程，哪些值得保留，哪些不适合你

目前三个 skill 的职责划分本身是合理的：

```text
Requirements：确定应该发生什么
Design：确定如何实现、如何划分责任
Tasks：确定实施顺序和验收方法
```

问题在于：**合理的工程分工，不一定是合理的人类阅读结构。**

### 1. requirements：严谨，但叙事被拆散了

当前 [requirements skill](<.agents/skills/kiro-spec-requirements/SKILL.md#L50-L68>) 要求所有验收条件使用 EARS，也就是“在什么条件下，系统必须做什么”的标准化句式。

这种逻辑结构值得保留，它可以减少歧义。但当前 [EARS 规则](<.agents/skills/kiro-spec-requirements/rules/ears-format.md#L4-L8>) 还要求固定短语保留英文，因此即使选择中文，也会出现中英混杂。

这带来的问题不只是语言生硬：

- 一个完整用户场景被拆成许多独立条款。
- 读者需要自己还原操作顺序和因果关系。
- 每条都可能很准确，但读完仍不知道“这个功能实际用起来是什么样”。

**建议保留条件、行为、结果的逻辑，取消强制展示 EARS 句式。**

例如：

> 当删除已经成功，但随后刷新列表失败时，系统仍应报告删除成功，不能把刷新失败当成删除失败。

这句话已经足够明确、可测试，不需要为了形式再改写成混合语言。

### 2. design：承担了太多种阅读任务

当前设计阶段实际上包含：

- 代码和依赖调查；
- 技术方案比较；
- 责任边界；
- 文件修改计划；
- 接口与状态契约；
- 测试策略。

这些工作都是有价值的。尤其是 [设计审查规则](<.agents/skills/kiro-spec-design/rules/design-review-gate.md#L12-L34>) 中的边界、隐藏前提、拒绝投机抽象等约束，很值得继承。

但 [设计模板](<.kiro/settings/templates/specs/design.md>) 同时面向方案审阅者、实现者和验证者。虽然允许裁剪，整体仍然容易变成一份“实现信息索引”，而不是适合人理解和判断的说明。

**这里需要改变的不是技术严谨性，而是把信息放到正确的阅读区。**

### 3. tasks：为了避免重复，制造了阅读跳转

这一点尤其符合你的感受。

当前 [任务生成规则](<.agents/skills/kiro-spec-tasks/rules/tasks-generation.md#L5-L22>) 明确要求任务避免写文件路径、函数、类型和接口，因为这些信息已经在设计文档中。

这能减少重复，但代价是：

> 阅读任务 → 查设计中的组件与文件 → 查需求中的验收条件 → 再回任务判断是否完整。

对于多人团队，这种分工有一定价值；对于一个全流程开发者，它经常只是把同一件事拆成几个阅读入口。

你提出的：

> 目的、修改、工作、验收、边界

比目前这种分散结构更适合个人开发。每个任务都能成为一个相对完整的执行单元。

### 一个实际例子

仓库中已有一个很小的修复：本地删除已经成功，却因为后续读取失败而被报告为失败。

它的 [需求文档](<.kiro/specs/p0-48-named-parent-cascade-terminal-result/requirements.md>) 只有两条验收条件，但仍然分别维护 [设计文档](<.kiro/specs/p0-48-named-parent-cascade-terminal-result/design.md>) 和 [任务文档](<.kiro/specs/p0-48-named-parent-cascade-terminal-result/tasks.md>)。

这不是说其中的技术信息没用，而是这个改动完全可以先让人读懂：

> 这次只修正“操作成功却报告失败”的问题。实际删除成功后，确认操作必须报告成功；后续刷新失败不能推翻这个结果。删除本身失败时，仍按原有方式报告失败。此次不改变删除范围、确认条件和接口格式。

然后再给 Agent 补充修改位置、状态值和测试要求。

**这就是你的双视角方案真正应该实现的效果。**

## 二、我如何评价你的方案

### 适用范围

你的方案适合：

- 个人开发者或很小的团队；
- 一个明确、可独立验收的问题；
- 希望 Agent 自主实现，但不希望 Agent 自主决定产品范围。

它不应该被理解为：

- 不再需要设计；
- 不再需要技术审阅；
- 只要用户批准一段文字，后续所有技术选择都自动合理；
- 用更短的文档掩盖仍未解决的问题。

**工程活动可以保留，人工审批点不必照搬工程阶段。**

我认为方案没有方向性问题，但建议补充下面四项规则。

### 建议 1：批准前可以调查，但不能提前编制执行方案

**依据：** 你把“现有实现与研究”放在执行版中，同时禁止批准前生成执行版。

**实际风险：** 如果把这理解成“批准前不能研究”，Agent 可能在不了解现有系统的情况下，先写出看似合理的目标和取舍。批准后才发现实现需要数据迁移、破坏兼容或改变用户行为。

**最小修正：**

批准前允许：

- 阅读代码和已有规范；
- 核对当前行为；
- 调查可行性；
- 识别会影响用户决定的风险；
- 提出澄清问题。

批准前禁止：

- 生成第 8～13 节的执行内容；
- 编制正式实施任务；
- 修改产品代码。

也就是：

> **禁止提前生成执行方案，不禁止为正确审阅提供事实依据。**

调查得到的关键结论，应该用普通语言进入审阅版的“背景”或“风险与取舍”。

### 建议 2：技术细节可以不审，但技术选择的重大后果必须审

**依据：** 你希望审阅版回答产品问题，执行版由 Agent 自检后直接使用。

这个分工成立，但要明确哪些决定不能藏进执行版。

例如：

- 是否会永久删除已有数据；
- 是否会把数据发送到外部服务；
- 是否会增加付费调用；
- 是否会停止支持原来的使用方式；
- 失败后是否还能恢复；
- 是否需要用户重新配置。

这些决定可能由技术方案触发，但后果属于人需要判断的内容。

**最小修正：**

> 执行版可以自主决定实现方法，但不得自主决定审阅版未批准的用户行为、数据影响、成本和风险。

如果后来发现必须增加这些代价，应返回审阅版，而不是把它写进技术方案就继续实施。

### 建议 3：批准必须绑定具体内容，不能只有一个“已批准”

**依据：** 你要求审阅版修改后执行版同步更新。

**实际风险：** 如果只是保留一个 `approved: true`，正文变了，旧执行版和旧批准仍然可能看起来有效。

**最小修正：**

记录三件事：

1. 人批准的是哪个审阅修订；
2. 执行版依据哪个已批准修订生成；
3. 执行版当前是否通过自检。

审阅内容改变后：

```text
原批准失效
→ 原执行版标记为过期、停止使用
→ 人重新批准新修订
→ Agent 更新执行版并重新自检
```

注意这里不是“人一改审阅版，Agent 立即同步生成新执行版”。

**新修订尚未批准时，不得生成对应的新执行内容。** 旧执行稿可以保留作历史记录，但不能继续实施。

### 建议 4：执行版自检必须既检查遗漏，也检查多做

**依据：** 你的完成定义已经要求“必须做到均实现”和“不新增明确不做范围内的行为”。

还需要把这件事提前到实施前。

自检应该同时回答：

- **正向覆盖：** 每个“必须做到”，是否都有实施任务和验证方法？
- **反向约束：** 每个任务，是否都服务于已批准的目标，或属于实现它所必需的基础工作？

否则很容易出现：

> 所有需求都覆盖了，但任务中额外增加了一套缓存、重试框架或新的产品行为。

建议沿用现有 Kiro 的有限修复循环，并把执行版检查结果分成：

```text
PASS：可以执行
NEEDS_FIXES：执行计划自身存在问题，可在已批准范围内修复
RETURN_TO_REVIEW：需要改变目标、行为或取舍，暂停并返回人类审阅
```

有条件时，可以由独立审阅 Agent 直接读取批准原文和执行版检查，而不是只相信生成者给出的覆盖总结。这不增加人工审批。

## 三、文件应该怎么组织

**我建议第一版默认采用：一个规格文件，两个先后生成的阅读区。**

以下是建议结构，尚未创建：

```text
.kiro/specs/<single-task>/
├── spec.md
│   ├── 审阅区：第 1～7 节
│   └── 执行区：批准后才追加第 8～13 节
└── spec.json
    └── 格式版本、批准记录、执行自检和进度
```

这样最贴近你希望“在一个地方理解一件事”的目标。

但要明确两点。

### 1. 合并的是规格，不是把原来的四份模板拼接起来

不能变成：

```text
一份人类摘要
＋ 原 requirements 全文
＋ 原 research 全文
＋ 原 design 全文
＋ 原 tasks 全文
```

这样只是把多份长文档变成一份更长的文档。

应该重新组织和去重：

- 产品行为在审阅区定义一次；
- 执行区引用验收项，不再重新定义产品行为；
- 技术契约在执行区定义一次；
- 任务引用契约，不重复抄写；
- 研究保留结论、依据和影响，不保留冗长调查流水账；
- 已有项目规则引用原始权威来源，不在每个规格中重建一份。

这也符合仓库已有的 [唯一权威来源原则](<CLAUDE.md#L70-L77>)。

### 2. 同文件时，批准只绑定审阅区

这是实现上很重要的一点：

> 第 8～13 节的追加、任务勾选和验证结果更新，不应该使第 1～7 节的批准失效。

因此，内容指纹或修订判断应该针对**审阅区**，不能简单绑定整份文件。

执行内容确实较长时，可以移到你提出的 `spec-execute.md`。两种形式的审批语义必须相同。但第一版不必同时支持两套存放方式，先把一种做可靠。

## 四、你的模板，建议怎样微调

整体结构我赞成，**不建议再增加一套复杂模板**。只需要补充写作要求和少量执行字段。

### 审阅版：保留你的七节

建议增加以下写作规则：

- **背景先用一个短段落讲清因果，再按需列条目。** 不要求所有内容都写成短句。
- **场景写完整过程，而不是条款的另一种排列。**
- **“必须做到”使用简单、稳定的编号。** 后续任务和测试引用编号即可。
- **“明确不做”写容易被误认为包含的相邻能力。** 不必列出所有不相关功能。
- **风险写具体后果。** “引入一致性风险”不如“保存失败时，页面可能显示新值，但重新打开后仍是旧值”。
- **审阅问题只问真实需要决定的问题。** 不要每次都生成“是否完整、是否合理、是否有风险”这种泛泛确认。

可读性标准可以是：

> 审阅者不需要理解内部组件名，就能复述这次改动，以及它的主要代价。

此外，你关心的是中文阅读体验。新规范应该明确允许审阅版以中文作为权威原文，而不是先生成英文工程文档，再附一个可能失真的中文摘要。代码标识符保持原样即可。

### 执行版：保留你的第 8～13 节，补三个连接点

**第一，实施任务增加“依据”。**

例如：

```markdown
- [ ] 1. 在操作实际成功后保留成功结果。
  - **依据**：审阅版验收项 1、2。
  - **目的**：避免后续刷新失败推翻已经完成的操作结果。
  - **修改**：列出经过核实的相关文件和职责。
  - **工作**：说明需要改变的处理逻辑。
  - **验收**：说明可观察结果及验证方法。
  - **边界**：不改变确认条件、删除范围和既有失败处理。
```

确有依赖时再增加依赖字段，不必所有任务都填一套空白元数据。

**第二，测试计划增加验收项对应关系和实际验证方法。**

建议变成：

| 验收项 | 场景 | 操作／验证方法 | 期望结果 |
|---|---|---|---|
| 1、2 | 操作成功，后续刷新失败 | 指定自动化测试或人工操作步骤 | 操作结果仍为成功 |
| 3 | 操作本身失败 | 指定测试 | 保留原有失败处理 |

实际执行命令、测试环境要求放在执行区，人不需要在初审时理解它们。

**第三，完成定义要求证据，而不只是勾选。**

建议补充：

- 每个“必须做到”都有对应验证结果。
- 必要测试未运行、被跳过或环境不可用时，不得记为通过。
- 已完成任务经过适用的独立审阅。
- 实际改动没有越过批准范围。
- 交付说明包含用户可以复核的结果或操作步骤。

**任务勾选代表进度记录，不是完成证明本身。**

## 五、新流程应该长什么样

我建议把新流程定义为：

```text
提出一个问题
    ↓
必要的只读调查与澄清
    ↓
编写审阅版
    ↓
【人类批准具体修订】
    ↓
生成执行版
    ↓
Agent 自检／独立一致性检查
    ├── 执行计划局部问题 → 修复后重检
    ├── 需要改变已批准内容 → 暂停，返回审阅
    └── 通过
          ↓
实施 → 任务审阅 → 验证 → 交付证据
```

这里有两个必须区别的状态：

- **人类已批准**：认可这次改动的意图、行为、范围和代价。
- **执行版已自检通过**：Agent 已确认计划可执行且没有偏离批准内容。

不要把第二个状态命名为“人类已批准设计／任务”。

另外，建议明确授权用语：

- “批准，可生成执行版”：只授权进入执行规划。
- “批准，并按此实施”：同时授权自检通过后开始实施。

这样可以只批准一次，也不会把“同意方案”自动扩大为提交、部署或执行破坏性操作的授权。

交付时，人仍然可以体验和抽验结果；但这不是要求再审一遍技术执行文档。

## 六、怎么与原有 skills 结合

**建议保留 Kiro 的工程机制，重写文档入口和审批语义，而不是彻底重造实施流程。**

可以收敛成三个主要入口。下面是建议名称，当前尚未实现：

| 新入口 | 职责 | 主要继承来源 |
|---|---|---|
| `sdd-spec` | 调查、澄清、编写或修改审阅区，然后停下等待批准 | init、requirements，以及必要的轻量调查 |
| `sdd-plan` | 检查真实批准记录，生成执行区并自检 | design、tasks、设计与任务审查规则 |
| `sdd-impl` | 检查批准和执行版有效性，实施、审阅、验证 | impl、review、debug、verify-completion、validate-impl |

重点不是命令名称，而是：

> **requirements、design、tasks 可以继续作为 Agent 内部的思考步骤，但不再要求人分别阅读和批准三份工程产物。**

值得保留的机制包括：

- 根据现有代码而不是想象设计；
- 明确职责和不做范围；
- 复用已有能力；
- 显式处理必要前置条件；
- 任务具备可验证交付物；
- 独立任务审阅；
- 基于当前代码状态的新鲜验证证据；
- 冲突暂停和有限修复循环。

可以放松或取消的形式约束包括：

- 强制展示 EARS 英文句式；
- 三个独立文档；
- 三次常规人工审批；
- 任务中不允许出现文件路径；
- 对所有任务机械套用“1～3 小时”的粒度。

任务大小更适合按“能否独立验证、能否清楚限定范围”判断。**一个问题也不等于只改一个模块：完整的小型前后端改动，仍然可以属于同一个规格。**

## 七、仓库落地时，不能只改三个生成 skill

这是调查中最需要提醒你的地方。

当前 [实施入口](<.agents/skills/kiro-impl/SKILL.md#L26-L46>) 仍固定读取旧文档并检查任务审批；[实现与审阅子代理的派发](<.agents/skills/kiro-impl/SKILL.md#L83-L108>) 也传递旧文件和章节编号。

[状态查询](<.agents/skills/kiro-spec-status/SKILL.md#L19-L35>) 按三个阶段统计；[最终验证](<.agents/skills/kiro-validate-impl/SKILL.md#L116-L139>) 同样按旧需求、设计和任务结构检查。

所以，最小迁移范围应该包括：

1. 新规格初始化与生成；
2. 批准记录和状态定义；
3. 实施入口及其子代理提示词；
4. 任务审阅；
5. 最终验证；
6. 状态查询。

另外还有三个现有问题需要一并处理。

### 1. 旧快捷入口不能绕过新批准点

当前 [quick 流程](<.agents/skills/kiro-spec-quick/SKILL.md#L121-L141>) 会使用自动批准参数；[batch 流程](<.agents/skills/kiro-spec-batch/SKILL.md#L64-L76>) 会将全部审批设为通过。

新格式必须明确禁止这些入口绕过人类审阅。第一版个人流程可以暂不支持 batch。

### 2. 项目总规则也要同步

[AGENTS 中的三阶段审批规则](<AGENTS.md#L55-L57>) 和 [P0 规格规则](<.kiro/steering/p0-implementation.md#L145-L157>) 仍要求分阶段批准。

如果只改 skill，项目级指令和技能级指令就会互相矛盾。

建议新增明确的格式版本，例如 `human-first-v1`：

- 旧规格继续走 legacy；
- 新规格走双视角流程；
- 不批量重写历史规格；
- 不把旧三阶段审批字段全部置真来伪装兼容。

### 3. 先确定唯一技能来源

当前运行时加载的是 `.agents/skills`，但 `.claude/skills` 是独立副本，已经存在行为差异。

例如：

- [.agents 的实施入口](<.agents/skills/kiro-impl/SKILL.md#L43-L46>) 明确检查任务审批；
- [.claude 的对应位置](<.claude/skills/kiro-impl/SKILL.md#L44-L51>) 是测试配置和完整环境门禁。

另外，[AGENTS 的技能路径](<AGENTS.md#L44-L45>) 和部分 batch 指令仍指向不存在的 `.Codex`。

改造前应确定一个权威来源，其他入口由它同步或生成。**不要直接拿其中一套覆盖另一套，否则可能修好新审批，却丢失原有测试安全门禁。**

## 八、我建议的实际推进顺序

### 第一步：先写流程规则，不急着改所有 skill

先固定这些不可违反的规则：

1. 一个规格解决一个可独立验收的问题。
2. 审阅区首先为人写，执行区首先为 Agent 写。
3. 未获真实人工批准，不生成执行内容。
4. 批准绑定审阅内容的具体修订。
5. 执行版只能细化实现，不得扩大产品范围或隐藏新增代价。
6. 审阅内容变更后，旧批准和旧执行版失效。
7. 执行版自检通过不再要求常规人工审批。
8. 完成声明必须有证据，不能只靠任务勾选。

### 第二步：拿一个很小的真实改动试写

不要一开始就迁移整套流程。

先检查：

- 人是否能只读审阅区就作出判断；
- Agent 是否能据此生成明确的执行区；
- 执行区是否偷偷引入了产品决定；
- 测试是否真正验证了人批准的内容。

像前面提到的“小型结果误报修复”，就适合做试点。

### 第三步：改最小消费链，并验证门禁

至少验证以下场景：

| 场景 | 必须发生的结果 |
|---|---|
| 未批准就请求生成执行版 | 停止，不产生执行内容 |
| 已批准后修改审阅区 | 旧执行版不可继续使用 |
| 执行计划需要新增用户行为或重大代价 | 返回审阅，不自行决定 |
| 执行版自检通过且已有实施授权 | 无需再次人工审批即可实施 |
| 必要验证环境不可用 | 如实报告未验证，不能宣称完成 |

如果这些规则只写在提示词里，却没有在入口处可靠检查，仍然容易重新变成“Agent 自己宣布获得批准”。

## 最后结论

**我赞成你的方案，属于“可推进，建议补齐关键约束”，而不是需要推翻重来。**

你要建立的原则可以浓缩成：

> **人类批准目标、行为、范围和代价；Agent 在这个批准范围内自主规划和实施，并用证据证明没有遗漏、没有越界。**

所以，最重要的改造不是“三个文件变成一个文件”，而是：

- 从**按工程阶段组织文档**，改为**按阅读者需要组织信息**；
- 从**人类反复批准技术产物**，改为**人类批准明确意图，Agent 验证执行一致性**；
- 从**任务全部勾选就是完成**，改为**已批准的行为有证据成立，才是完成**。




这样才能真正减少机械的“同意”，而不是把三次机械审批压缩成一次。
