# 对你的改造方案的思考

先给结论：**方向对，方案基本可用，但有一处关键机制缺失、四处需要收紧、一处我建议反过来做。**

你抓住的不是"文档太多"，而是"流程把人的判断和 Agent 的约束混在一个产物里"。这个诊断比我看到的任何"精简 Kiro"的提议都更接近根因。下面按"同意什么、补什么、改什么"来说，每一条都尽量落到可执行的规则上。

## 一、我完全同意的部分

| 你的主张 | 我的判断 | 原因 |
|---|---|---|
| 一个 spec 只解决一个可独立验收的问题 | 同意，且这是全局前提 | 规格一旦"多目标"，审阅区就无法用一句话说清，后面的双视角全部失效 |

## 二、最关键的一处缺失：批准由谁写、凭什么算数

你的四条建议里，建议 3 说"记录三件事"：批准的是哪个修订、执行版基于哪个修订、执行版是否通过自检。

**但没写这三件事由谁写，以及 Agent 为什么不能自己写。**

这是整个方案唯一的致命漏洞。如果 `spec.json` 里的 `approved_revision` 由 Agent 在生成执行版的同一个流程里写入，那么"人类批准"就退化成一句提示词约束——而提示词约束在长会话里是最先失效的东西。Kiro 现在的 `approvals.*.approved: true` 就是这个毛病：字段是真的，语义是假的。

### 我的建议：用 git 提交当批准载体

不上工具、不写服务，直接用仓库已有的东西：

**批准动作 = 人提交一个只包含审阅区的 commit。**

```text
1. Agent 写完审阅区（第 1–7 节），停在那里，不写执行区。
2. 人读完，改完，自己 commit：spec(<feature>): approve review v1
3. 该 commit 的 SHA 就是 approved_revision。
4. Agent 生成执行区前，先校验：
   - 存在一个由人提交的、只改审阅区的 commit；
   - 该 commit 之后审阅区内容未变（用 git diff 判断，不用重新计算哈希）。
5. 审阅区一旦再变，旧 commit 不再"覆盖当前内容"→ 批准自动失效。
```

为什么用 git 而不是内容指纹：

- **天然带作者、时间、内容三元组**，不需要自己算 canonical hash，也就绕开了"空白字符算不算改动"这类边界问题。
- **失效判定是现成的**：`git diff <approved_rev> -- <review-zone>` 非空就是失效，不需要设计指纹算法。
- **不可伪造**：Agent 可以写文件、可以提交，但"某个人读过并认可"这个事实，只有在人真的提交时成立。规范里可以加一句硬规则：**Agent 不得创建、不得修改、不得代签批准 commit**。
- **审阅区与执行区分开提交**，顺带解决"同文件时批准只绑定审阅区"的问题——执行区的追加是另一个 commit，不影响批准。

代价：要求人会用 `git commit`，且每次批准多一次提交。对个人开发者这个成本可以接受；如果嫌重，退一步的做法是人在审阅区末尾手写一行 `Approved: <date> <你的名字>` 并单独提交该行——语义一样，只是指纹换成"这行存在且在被批准的内容里"。

**这条如果你只接受一个改动，我建议就接受它。** 它决定了"人类批准"是机制还是口号。

## 三、需要收紧的四处

### 3.1 审阅区必须带稳定编号，否则"依据"指不到任何地方

你的模板第 4 节是：

```markdown
## 4. 必须做到
- [ ] ……
- [ ] ……
```

复选框没有编号。而执行版的任务要写"依据"，测试计划要写"验收项"，完成定义要写"每个必须做到都有验证结果"——这三件事都需要一个**可引用的地址**。

建议改成：

```markdown
## 4. 必须做到

- [ ] **R1** 删除实际成功后，确认结果必须报告成功。
- [ ] **R2** 后续刷新失败不得推翻已完成的删除结果。
- [ ] **R3** 删除本身失败时，保留原有失败报告方式。
```

用 `R1`–`Rn` 而不是 `4.1`–`4.n`，理由：读起来短、在表格里窄、和章节号不会混淆。代价是偏离 Kiro 的 `N.M` 数字约定，机械检查脚本要按新格式写——这是值得付的。

编号一旦确定：执行版任务写 `**依据**：R1、R2`；测试计划第一列写 `R1、R2`；完成定义逐条对 `R1..Rn` 给证据。**规格内部的引用全部靠这几个编号，这是新流程里唯一的强制结构。**

### 3.2 "自检"必须由另一个上下文做，且输出必须是矩阵

你写"Agent 自验证后无需再次审核"。我同意不再要人工审核，但自检的执行方式要定死，否则它会变成"Agent 说它检查过了"。

建议两条硬规则：

1. **自检由一个全新上下文执行**，只给它：批准的审阅区原文、执行区草稿、相关代码路径。不给生成者自己的覆盖度总结。这与 Kiro 任务图体检的做法一致（[tasks skill 第 3.5 步](<.claude/skills/kiro-spec-tasks/SKILL.md#L91-L109>)），已被证明能抓住"生成者自己看不见的洞"。
2. **输出必须是矩阵，不是散文**：

```text
正向：R1 → 任务 2、测试 T1      ✅
      R2 → 任务 2、测试 T2      ✅
      R3 → 任务 3、测试 T3      ✅
反向：任务 1 → 依据 R2（基础设施）  ✅
      任务 4 → 依据 ——              ❌ 无依据，删除或补批准
```

散文式的"已确认覆盖完整"没有信息量，也没法被下一个人复核。

### 3.3 三类"必须停下"的条件要写死，不能靠判断

你写了"执行版自检若发现与审阅版冲突，Agent 必须暂停并回报"。这方向对，但"冲突"太抽象。建议直接列成三个触发条件，命中任何一个就停，不许自行决定：

| 触发 | 例子 | 处理 |
|---|---|---|
| **新增用户可见行为** | 顺手加了个"删除前二次确认" | 停，回审阅区加 R 项并重新批准 |
| **新增代价** | 需要新依赖、新外部调用、新计费、需要数据迁移、不可逆删除 | 停，回审阅区写进"风险与取舍" |
| **改变已批准的范围** | 原来"不做批量删除"，实现时发现需要 | 停，回审阅区改"明确不做" |

关键在最后一句：**这些代价不允许写进执行区就继续做**。这正是你原文建议 2 的意思，但需要具体到"命中即停"，否则 Agent 会把它当成"注意事项"而不是"门禁"。

### 3.4 完成定义要落到证据，勾选只是进度

你的第 13 节写"所有执行版任务均已勾选"，这条要删掉或降级。理由与本仓库已有的 `kiro-verify-completion` 完全一致：勾选是**记录**，不是**证据**（[SKILL.md](<.claude/skills/kiro-verify-completion/SKILL.md#L111-L119>)）。

建议第 13 节改成：

```markdown
## 13. 完成定义

- R1–R3 每一条都有对应的验证结果（命令 + 退出码，或人工步骤 + 观察结果）。
- 必需测试未运行 / 被跳过 / 环境不可用时，不得记为完成；如实报告"未验证"。
- 实际改动没有超出批准的边界（附 `git diff --stat` 与边界对照）。
- 交付说明包含用户可以自己复核的步骤，而不是"已完成"三个字。
```

## 四、一处我建议反过来做

### 不要把执行区硬塞进同一个文件

你倾向"同文件、批准只绑定第 1–7 节"，Agent 的建议也是同文件优先。我建议**默认反过来：审阅区单独一个文件（`spec.md`），执行区单独一个文件（`plan.md`）**。

理由不是"实现更方便"，而是**同文件会自己长胖，最后毁掉你方案的初衷**：

- 执行区天然包含任务清单、契约表、测试矩阵，写全了通常 150–400 行。
- 加上审阅区的 100 行，同一份文件 300–500 行。而你的目标恰恰是"在一个地方读一件事"。
- 更麻烦的是评审 diff：每次执行区更新，审阅区的 diff 上下文都被撑开，人眼很难快速确认"审阅区没被动过"。

拆成两个文件的收益：

| 维度 | 同文件 | 拆文件（我的建议） |
|---|---|---|
| 人的阅读入口 | 一个文件，但要滚过执行区 | 只读 `spec.md`，读完即止 |
| 批准绑定 | 需要定义"哪个区"和指纹范围 | 文件级，天然清晰 |
| 执行区膨胀 | 拉长人类要打开的文件 | 不影响审阅体验 |
| 执行区过期标记 | 同文件内加横幅 | 文件头加 `status: stale` 即可 |
| 两个入口的关联 | 天然在同一文件 | 需要靠同一个 `R#` 编号互指（这点本来就要求了） |

你原文说"第一版不必同时支持两套存放方式"。我完全同意——**只支持拆文件这一种**。这比"只支持同文件"更容易实现，也更容易长期维持。

唯一要补的是关联性：两个文件都命名成 `<feature>/spec.md` + `<feature>/plan.md`，并且 `plan.md` 开头必须引用 `spec.md` 的批准 commit SHA。人在 `spec.md` 里看到 `Approved: <sha>`，在 `plan.md` 里看到 `Based-on: <sha>`，两个值一致就说明执行版对应当前批准。

## 五、执行成本与验证时机

前面四节讨论的是"文档怎么写、批准怎么算数"。这一节讨论另一个独立的问题：**这套流程跑起来太慢、太贵**。

现象：一个微不足道的小问题要花几个小时；任务开始一小时，Agent 一行代码没改；一个完整 spec 消耗掉惊人数量的 token。

我的判断是：**方向对，但"简化规则文本"是收益最小的一刀。** 先给测量结果，再说该怎么砍。

### 5.1 成本结构：四个乘法器，不是一个长度

我在本仓库量了流程资产（英文字符 ÷4 ≈ token）：

| 资产 | 体量 | 折算 token |
|---|---|---|
| 19 个 `SKILL.md` | 155k 字符 | ≈ 39k |
| 17 个 `rules/*.md` | 81k 字符 | ≈ 20k |
| 13 个 steering 文件 | 123k 字符 | ≈ 31k |
| 一次 `/kiro-impl` 开场（impl skill + 核心 steering + testing-profiles + spec 四文档） | — | ≈ 18–22k |
| 单个 spec 四份文档（p0-48） | 16.9k 字符 | ≈ 4.2k |

再叠加两个放大项：

- **1079 个 `*_test.go`，仓库没有 Makefile。** 全量 `go test ./...` 是分钟级的。p0-43 有 31 个子任务、p0-77 有 15 个——"每个任务跑一次全量"= 15–45 分钟纯等待，还没算需要 DSN 的集成测试。
- **同一个断言被验三次**：任务评审跑测试 → `verify-completion` 再跑一次取"新鲜证据" → `validate-impl` 再跑全量。三次跑的是同一棵代码树。

所以真实公式不是"文档有多长"，而是：

```text
总消耗 ≈ Σ（每个 agent 的每一步 × 该步的上下文大小）
```

它有四个乘法器：**agent 数量**、**每 agent 步数**、**每个 agent 启动时的基线上下文**、**重试轮次**。规则文本只影响第三项的一小块。

排序因此是：

```text
删除重复验证  >  减少评审 agent  >  压缩基线上下文  >  精简规则文本
```

"简化规则"排在最后。它最容易做，但收益最小。

### 5.2 一个反证：规则早就写了，但没生效

`.kiro/steering/kiro-execution-efficiency.md`（7.3k 字符）已经明确写了：命令只发现一次并复用、不重复跑已通过的命令、避免重复全文件读取、事件驱动等待而不是轮询。

慢和贵依然存在。这说明：

> **写进文档的规则，只在你恰好读到它的那一次生效；写进脚本、模板和预算数字的规则，才一直生效。**

根因不是缺规则，而是**验证指令是无条件的，效率指令是建议性的**。Agent 没法因为"这条命令已经跑过"而免责，但能因为"我又验了一遍"而免责。于是它选择多验证。

这一条直接决定新规范该怎么写：**凡是希望被执行的约束，都要变成脚本、模板字段或数字预算；留在散文里的，只能当解释。**

### 5.3 证据复用：按代码树指纹判新鲜，不按时钟、不按评审次数

这是收益最大的一刀。

现在"新鲜证据"被理解成"这次评审必须自己跑一遍"。改成：

```text
tree_stamp = HEAD + 工作区 diff 的 hash
```

规则三条：

1. **证据绑定 stamp，不绑定评审者。** stamp 未变时，已取得的 PASS 证据对后续步骤（任务评审、完成声明、提交）继续有效，不重跑。
2. **stamp 一变，全部证据立刻作废。** 这是"新鲜"的严格定义，比"每个评审者跑一遍"更严格，而不是更宽松。
3. **失败结果永不复用。** 只有 PASS 可以按 stamp 复用；一旦 FAIL，修完必须重跑。
4. **缓存键必须覆盖影响结论的全部参数**（档位、`-Boundary`、跳过项）。否则换一个更窄的边界，会直接复用宽边界的 PASS——这个坑我在原型第一版就踩到了，它比"不缓存"更危险。

`verify-completion` 的本意是"不要用陈旧证据"。而陈旧的定义应该是"树变了"，不是"换了个评审者"。这一条把测试运行次数从"每任务 3 次"降到"每任务 1 次 + 规格末 1 次全量"，严格性不降。

### 5.4 检查脚本化：一个命令、十几行输出

现在 `validate-impl` 里有 6 条独立机械检查：全量测试、grep TBD、grep 密钥、smoke、lint、迁移清单。它们各自产生一段输出，全部留在上下文里，而且每条都要 Agent 记住"该怎么跑"。

改成脚本后：一次调用、一段短输出、可复用、可缓存。原型见 [scripts/sdd-check.ps1](<scripts/sdd-check.ps1>)、[scripts/sdd-check.sh](<scripts/sdd-check.sh>)，输出形如：

```text
sdd-check  stamp 82965177+fe22813  dirty: 17 files  mode fast
build   SKIP  no go change
vet     SKIP  no go change
test    SKIP  no go change
front   SKIP  no frontend change
hygiene SKIP  no code change
bound   OK    17/17 inside boundary
result  PASS
```

这一段替代过去 6 条命令 + 6 段输出。失败时只打印失败项和最多 5 条命中行，成功时不打印细节——**上下文里只留结论**。

原型实测（当前仓库、纯文档改动）：

| 场景 | 结果 |
|---|---|
| 首次运行 | 冷编译 `go build ./...` 61.9 秒，其余检查按需 SKIP |
| 同一代码树再跑 | 打印 `reused (PASS)`，耗时 < 1 秒 |
| 边界收窄 | 重新执行并 `FAIL outside 2 -> scripts/sdd-check.ps1 ...` |
| 恢复宽边界 | 重新执行，`OK 17/17` |

"代码树没变就一秒返回"这件事，靠提示词是做不到的；写进脚本就成了默认行为。

脚本同时实现 5.3 的复用：把 `stamp + 参数键 + 结论` 写到 `.git/sdd-check-cache.json`（bash 版用 `.git/sdd-check-cache.tsv`），stamp 与参数键均未变且上次为 PASS 时直接打印 `reused` 并跳过执行。

### 5.5 验证只放在三个时刻

| 时刻 | 跑什么 | 成本 |
|---|---|---|
| 每次编辑后 | 受影响包的测试 | 秒级 |
| 每次提交前 | `build` + `vet` + 受影响包测试（即检查脚本） | 十几秒 |
| 每个 spec 结束 | 全量测试 + smoke | 分钟级，**只一次** |

删掉"每个任务评审时跑全量"。它没有提供任何新信息——只是把规格末要做的事在每个任务边界上重复了一遍。

### 5.6 给子代理"上下文包"，不给"文件路径"

现在实现者拿到的是"去读 `requirements.md`、`design.md`、`tasks.md`"，于是每个子代理都要加载约 4.2k token 的 spec + 约 6k 的 steering 基线，再从里面挑自己需要的那一段。

改成一个内联的上下文包，控制在 800 token 以内：

```text
任务块（目的 / 修改 / 工作 / 验收 / 边界）
+ 该任务直接相关的验收条文原文（R1、R2）
+ 需要改动的文件清单
+ 检查脚本的调用方式
```

评审者同理：**只给任务块 + `git diff` + 检查脚本输出**，不给三份文档。评审的关键输入是 diff，不是文档全量。

这里有一个对你方案的额外支撑：**执行版本身就是上下文包**。它把"读三份文档"压缩成"读一个任务块"。所以 `spec.md` / `plan.md` 的拆分不只是可读性问题，还是 token 问题——如果执行区塞进同一个文件，每个任务都要重读整个审阅区。

### 5.7 评审按风险触发，不按任务触发

按任务派评审 = 每个任务 2 个 agent 上下文（实现者 + 评审者）。对 15 个任务，这是 30 次基线加载。

改成机械判定，而不是让 Agent 自己评估风险（它会往轻了报）：

| 改动内容 | 评审方式 |
|---|---|
| 迁移文件、`docs/data-model/*`、跨包导出接口、并发原语、外部 IO、安全相关 | **逐任务评审**（保留现有严谨度） |
| 纯新增、UI、文案、测试补充、单文件内聚改动 | **批量终审一次**（整个 plan 的 diff） |

判定依据来自 diff 的文件路径与符号，不来自任务描述的自我申报。

### 5.8 进入实现前的工具调用预算

这条直接回答"一小时没改一行"：

> **进入实现前最多 5 次工具调用**：读任务块 → 跑一次检查脚本 → 读 1–2 个关键文件 → 看 `git status`。
> 超出 5 次，说明任务切分或边界不清：**停下来回到任务拆分**，不要在探索里追加预算。

原因很实际：preflight 阶段的每次调用都会进入后续所有步骤的上下文，而它买到的信息通常递减。5 次之后还找不到落点，问题不在信息不足，而在这件事被切得太大——继续读只会更贵，不会更清楚。

### 5.9 哪些验证不能砍

砍频率可以，砍存在性不行。这四项任何档位都保留：

1. **契约与边界检查**：改了对外接口或跨边界行为，必须有一次独立比对。这是 Kiro 最值钱的部分。
2. **错误路径测试**：只跑 happy path 的"通过"是假通过。
3. **数据安全**：迁移、删除、覆盖类操作，必须有一次可复核的证据，哪怕是人看一眼。
4. **运行时能启动**：类型检查通过不等于能跑。每个 spec 一次就够，但不能省。

反过来，**设计评审不要砍**。设计错了会让所有任务白做，那是唯一值得付高成本的地方。该省的是"任务级重复验证"，不是"设计级判断"。

### 5.10 一句原则

> 验证的频率应该跟"缺陷发现得越晚、修复成本越高"的斜率走，而不是跟流程阶段的完整性走。
> 每次验证都必须回答一个新问题；回答旧问题的验证，就是在重复支付。

现在这套流程的问题是：它在很多地方重复回答同一个问题（"这段代码现在对不对"），却只在少数地方回答真正的新问题（"这个契约变了，下游还成立吗"）。

## 六、你的模板，我建议的具体修订

### 6.1 审阅区（第 1–7 节）

| 节 | 修订 |

| 1 背景与问题 | 先用一段话说清因果，再列条目。禁止只列短句 |

> 审阅问题必须指向审阅区中一处具体的、有两种以上合理选择的决定，并说明两种选择各自的后果。写不出这样的问题，就写"本次无需你决定的事项"。

### 6.2 执行区（第 8–13 节）

保留六节，加三个连接点和一处删减：

**连接点 1：任务加"依据"**

```markdown
- [ ] 2. 在操作实际成功后保留成功结果。
  - **依据**：R1、R2
  - **目的**：避免后续刷新失败推翻已完成的删除。
  - **修改**：`internal/app/connection/service.go` — 结果聚合职责。
  - **工作**：把刷新错误与删除错误分开聚合，刷新失败只降级为警告。
  - **验收**：删除成功 + 刷新失败时，返回值仍为成功，警告随结果返回。
  - **边界**：不改删除范围、确认条件、既有失败路径。
```

依赖关系只在真有跨任务依赖时才加 `**依赖**：1.3`，不要给每个任务填一套空白元数据——那是模板病。

```markdown
| 验收项 | 场景 | 操作 / 验证方法 | 期望结果 |
|---|---|---|---|

| R3 | 删除本身失败 | `go test ./internal/app/connection -run TestDeleteFailure` | 保留原有失败报告 |
```

具体命令、环境变量、`_Test profile` 这类机器信息放执行区，人不看也不影响初审。

**连接点 3：完成定义改成证据（见 3.4）**

**删减：删掉"所有执行版任务均已勾选"作为完成条件的表述**

## 七、我建议再加的两个机制

### 7.1 门禁分级：按"可逆性 × 影响面"决定走多重

这是你方案里没有、但我认为必须有的一条。否则新流程会以另一种方式变重——比如给"改一个提示文案"也生成审阅区 + 执行区 + 全量测试。

建议三档，由 Agent 提议、人确认：

| 档位 | 判定条件 | 需要什么 |
|---|---|---|
| **轻**（light） | 单文件、无数据/契约/外部服务变化、可随时回退 | 一段变更说明 + 验证结果。不生成 spec |
| **标准**（normal） | 多文件、单一边界内、无不可逆代价 | `spec.md`（可精简到 1/2/4/5 节）+ `plan.md` |
| **重**（full） | 触及数据迁移、外部调用、契约变化、跨边界集成、不可逆操作 | 完整 `spec.md` + `plan.md` + 独立自检 + 特性级校验 |

判定规则要写死，比如"只要出现以下任一项，最低为 full：新增或改变持久化结构、改变对外契约、改变其他规格依赖的行为、不可逆数据操作"。

没有分级，你的流程会从"三次审批"变成"每次都完整走一遍"，只是审批从三次压成一次——这恰好是你原文最后一句警告的失败模式。

### 7.2 执行区的"过期"要能被工具看见

规则里写了"审阅区变更 → 旧执行版失效"，但要让它可见，否则没人执行：

- `plan.md` 头部固定三行：`Based-on: <sha>`、`Checked: <pass|needs-fixes>`、`Status: <active|stale>`。
- 任何实现入口（开始写代码前）必须校验 `Based-on` 是否等于 `spec.md` 当前批准 commit；不等就拒绝执行，并提示"执行版已过期，请重新生成"。
- `tasks.md` 那种"勾选即完成"的语义不要继承。任务状态放 `plan.md` 的执行日志里，或干脆不落盘。

## 八、怎么和现有 Kiro 流程结合

原则：**保留机制，替换入口，不动实现流水线。**

### 8.1 保留 / 放松 / 新增

| 类别 | 内容 |
|---|---|
| **保留** | 基于真实代码做设计；显式边界与不做范围；复用已有能力；前置条件显式化；任务可验证交付物；独立任务评审；新鲜证据；有限修复循环；失败归因（LOCAL/UPSTREAM）；单一权威来源 |
| **放松** | 强制 EARS 英文固定短语；三份独立文档；三次常规人工审批；任务禁止写文件路径；机械套用"1–3 小时" |
| **新增** | 审阅区/执行区双视角；批准绑定修订（git commit）；执行区自检矩阵；三类暂停条件；完成=证据矩阵；门禁分级；格式版本分流 |

关于 EARS：**保留条件-行为-结果的逻辑，取消强制展示固定英文句式**。你原文那句"当删除已经成功，但随后刷新失败时，系统仍应报告删除成功"本身就是合格的验收条件，不需要改写成 `When ... shall`。对应地，机械检查要改成语言中立的形式：检查"是否有可观察的响应"，而不是 grep 英文关键词。

### 8.2 三个入口（名字不重要，职责重要）

| 入口 | 职责 | 硬约束 |
|---|---|---|
| `sdd-spec` | 只读调查 → 写审阅区 → 停下 | **不得**写执行区、不得编任务、不得改产品代码；有疑问就问 |

## 九、对我自己这套建议的批评

我不能只挑你的方案的毛病，下面是我认为这套方案仍然脆弱的地方：

1. **"人批准一次"仍可能变成机械同意。** 机制只能保证"批准的是这一版内容"，保证不了"人真的读了"。唯一的缓解是让批准变贵一点点（一次 commit）+ 让审阅区变短。如果审阅区写到 300 行，人会跳过——所以要给它一个硬上限，超了就拆规格。
2. **拆文件削弱"一个地方读懂一件事"。** 我用"执行区会膨胀"来换"审阅区干净"，这确实是妥协。如果你坚持同文件，我建议加一条：执行区超过 120 行就必须拆出去，否则方案会自己腐烂。
3. **中文作为权威原文，会牺牲一部分机器可校验性。** 英文 EARS 能被正则检查，中文"当…时，应…"也能，但边界更模糊。可接受，但要把机械检查降级为"抽样 + 人工"，不要把希望寄托在正则上。
4. **门禁分级依赖 Agent 自我申报档位。** 一个想省事的 Agent 会把 full 报成 normal。缓解：档位由"命中规则"决定而不是"评估"决定（出现迁移/契约/外部调用就是 full），并且把档位写进执行区，供人一眼复核。
5. **单人流程省掉了很多为协作设计的机制**（并行 `(P)`、批次、多审阅者）。将来一旦有第二个人，这些要补回来。现在不做是对的，但要意识到这是主动欠债。
6. **最容易被忽略的一点**：改造完成后，`kiro-impl`、`kiro-spec-status`、`kiro-validate-impl` 仍在按旧结构读文件。只改生成 skill 是最常见的半途而废——流程会在实现阶段"读不到文件"而静默退回旧行为。

## 十、建议的第一步

1. **今天**：写一页规则文件（八条规则 + 分级表 + 暂停条件），不做任何代码改动。
2. **明天**：用 `p0-48` 试点手写一份 `spec.md`，不写执行区；你自己读一遍，判断"只读它能不能做决定"。这一步失败，说明模板还要改，不要急着做 skill。
