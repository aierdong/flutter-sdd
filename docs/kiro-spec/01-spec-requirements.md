# kiro-spec-requirements：把项目描述写成 EARS 需求

> 本文件是英文原文的中文译本，供阅读与评审。事实以 `.claude/skills/kiro-spec-requirements/SKILL.md` 为准。

| 项 | 内容 |
|---|---|
| name | `kiro-spec-requirements` |
| description | 依据项目描述和 steering 上下文，生成 EARS 格式的需求。需要从项目描述产出需求时使用。 |

## 核心任务

- **成功标准**：
  - 产出的需求文档完整，并与 steering 上下文对齐。
  - 所有验收条件遵守项目既定的 EARS 句式与约束。
  - 只描述核心功能，不掺实现细节。
  - 范围容易被误读时，把"包含什么、不包含什么"明确写出来。
  - 更新元数据，记录生成状态。

## 执行步骤

### 第 1 步：收集上下文

如果对话里已经带有 steering / spec 上下文，就不要重复读文件。否则加载全部必要上下文：

- 读 `.kiro/specs/{feature}/spec.json`，取语言设置和元数据。
- 如果存在 `.kiro/specs/{feature}/brief.md`，读它。里面是发现阶段的上下文：问题、做法、范围决策、边界候选。
- 读 `.kiro/specs/{feature}/requirements.md`，取项目描述。
- 核心 steering：`product.md`、`tech.md`、`structure.md`。
- 以下情况才读额外的 steering 文件：它与特性范围、用户画像、业务或领域规则、合规与安全约束、运行约束，或既有产品边界直接相关。
- 以下情况才读本地 agent skill 或 playbook：它明显匹配本特性的宿主环境或用例，并且包含会影响"用户可观察需求"的领域术语或工作流规则。

### 第 2 步：读规则文件

- 读本 skill 目录下的 `rules/ears-format.md`，取 EARS 句法规则。
- 读本 skill 目录下的 `rules/requirements-review-gate.md`，取落盘前的评审标准。
- 读 `.kiro/settings/templates/specs/requirements.md`，取文档结构。

#### 并行调研（派子代理）

下面几块调研彼此独立。具体怎么拆，由你按项目复杂度决定：可以拆开、合并、追加，也可以跳过。

**通过 Agent 工具派子代理**（把探索过程挡在主上下文之外）：

- **代码库线索**（棕地项目）：派一个子代理去摸清与需求范围相关的既有实现。提示词示例："在本代码库中探索与 [特性领域] 相关的既有功能。总结三件事：(1) 已经存在什么；(2) 相关接口/API；(3) 新需求应遵循的模式。返回 150 行以内的摘要。"
- **领域调研**（需要外部知识时）：派一个子代理，用 WebSearch/WebFetch 调研领域特定的需求、标准或最佳实践。返回简洁的结论摘要。
- **额外的 steering 与 playbook**：如果 steering 文件或本地 agent playbook 很多，派一个子代理扫一遍，只返回与本特性相关的章节。

绿地项目、代码库很小的情况下，跳过子代理，直接在主上下文加载。

所有调研返回后，先在主上下文里做综合，再开始写需求。

### 第 3 步：写需求草稿

- 依据项目描述写出需求初稿。
- 把相关功能归入逻辑需求域。
- 所有验收条件套用 EARS 格式。
- 使用 `spec.json` 里指定的语言。
- 跨阶段保持术语连续：
  - 发现阶段叫 `Boundary Candidates`
  - 需求阶段写成显式的"包含/排除"以及必要的相邻预期
  - 设计阶段叫 `Boundary Commitments`
  - 任务阶段用 `_Boundary:_`
- 范围可能被误读时，补一点轻量的边界说明。但不要引入实现或架构层面的权属细节。
- 在评审门禁通过之前，它一直是草稿：**此时还不要写 `requirements.md`**。

### 第 4 步：评审需求草稿

- 执行 `rules/requirements-review-gate.md` 里的 `Requirements Review Gate`。
- 定稿前，检查覆盖度、EARS 合规性、歧义、相邻预期和范围边界。
- 如果问题只出在草稿局部，就地修好，再评审一次。
- 修复循环最多 2 轮。
- 如果草稿暴露出真正的范围歧义或矛盾，停下来请用户澄清。不要靠猜把需求写下去。

### 第 5 步：定稿并更新元数据

- 只有在需求评审门禁通过后，才写 `.kiro/specs/{feature}/requirements.md`。
- 设置 `phase: "requirements-generated"`。
- 设置 `approvals.requirements.generated: true`。
- 更新 `updated_at` 时间戳。

## 重要约束

### 需求的范围：写 WHAT，不写 HOW

需求描述的是用户可观察的行为，不是实现。下面这张对照表，用来判断一段内容该放需求还是放设计。

**该问用户的（属于需求范围）：**

- 功能范围：包含什么、排除什么。
- 用户可观察的行为："发生 X 时，用户应该看到或经历什么？"
- 业务规则与边界情况：限制、错误条件、特殊情况。
- 用户能感知的非功能需求：响应时间预期、可用性、安全等级。
- 相邻预期：只在它改变用户可见行为或运维预期时才写。要说清本特性依赖什么、明确不负责什么。

**不该问的（属于设计范围，留到设计阶段）：**

- 技术栈选择（数据库、框架、语言）。
- 架构模式（微服务、单体、事件驱动）。
- API 设计、数据模型、内部组件结构。
- 非功能需求的实现手段（缓存策略、扩容方案）。
- 内部权属划分、组件接缝，或属于设计的实现边界。

**判断标准**：一条 EARS 验收条件，如果不用提任何技术就能写出来，它属于需求；如果必须落到某个技术选择上，它属于设计。

### 其他约束

- 每条需求都必须可测试、无歧义。如果项目描述在范围、行为或边界条件上留有多种解释，先请用户澄清，再写这条需求。需要问多少问题就问多少。**不要把自己脑补的假设写进需求。**
- EARS 语句的主语要选对。（软件项目用系统或服务名。）
- `requirements.md` 里的需求标题，**必须以数字编号开头**（例如 `Requirement 1`、`1.`、`2 Feature ...`）。不要用 `Requirement A` 这种字母编号。

## 输出说明

按 `spec.json` 指定的语言输出，包含：

1. **需求生成摘要**：主要需求域的简要概览（3–5 条）。
2. **文档状态**：确认 `requirements.md` 已更新、`spec.json` 元数据已更新。
3. **评审门禁**：确认需求评审门禁已通过。
4. **下一步**：告诉用户可以怎么继续（批准并前进，或要求修改）。

**格式要求**：

- 用 Markdown 标题分层，便于扫读。
- 文件路径放在代码块里。
- 摘要控制在 300 词以内。

## 异常与兜底

### 错误场景

- **缺项目描述**：`requirements.md` 里没有项目描述时，向用户询问特性细节。
- **模板缺失**：模板文件不存在时，用内置的兜底结构，并给出告警。
- **语言未定义**：`spec.json` 没指定语言时，默认英文（`en`）。
- **需求不完整**：生成后，明确问用户一句：这些需求是否覆盖了全部预期功能。
- **steering 目录为空**：提醒用户项目上下文缺失，可能影响需求质量。
- **需求标题非数字编号**：如果已有标题没有数字编号（比如用了 `Requirement A`），统一改成数字编号，并保持映射一致。**绝不混用数字和字母标签。**

### 下一阶段：生成设计

**需求已批准时：**

- **可选的需求评审**：
  - 跑 `/kiro-validate-requirements {feature}`，检查 `requirements.md` 的遗漏、矛盾和严谨性缺口。
  - 该命令一次只抛一个发现，不负责给阶段批准。
- **可选的差距分析**（已有代码库时）：
  - 跑 `/kiro-validate-gap {feature}`，分析实现差距。
  - 棕地项目建议做，绿地项目可跳过。
- 跑 `/kiro-spec-design {feature}` 进入设计阶段。
- 或者跑 `/kiro-spec-design {feature} -y`，自动批准需求并直接进设计。

**需要修改时：**

- 给出反馈，重跑 `/kiro-spec-requirements {feature}`。
