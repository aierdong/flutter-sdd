# 任务生成规则

> 本文件是英文原文的中文译本。事实以 `.claude/skills/kiro-spec-tasks/rules/tasks-generation.md` 为准。

## 核心原则

### 1. 用自然语言描述

关注能力和结果，不关注代码结构。

**要写**：

- 要达成的功能
- 业务逻辑与行为
- 特性与能力
- 领域语言与概念
- 数据关系与工作流

**不要写**：

- 文件路径与目录结构
- 函数/方法名与签名
- 类型定义与接口
- 类名与 API 契约
- 具体数据结构

**理由**：实现细节（文件、方法、类型）已经在 `design.md` 里定义。任务描述的是要做的功能工作。

### 2. 任务排序原则

**顺序即依赖**：任务 N 隐式依赖它之前的所有任务。这是主要的依赖机制。

**任务必须遵循这个阶段顺序**：

1. **地基**：环境搭建、测试基础设施、共享工具、数据库 schema、配置
2. **核心**：主体功能实现（可并行的任务集中在这一段）
3. **集成**：把组件接起来，打通跨边界连接
4. **校验**：E2E 测试、边界情况、回归检查

**理由**：地基工作解锁其余一切。把搭建任务放前面，可以避免下游被堵。核心任务常常能并行，因为地基已经完成。

### 3. 任务集成与推进

**每个任务必须**：

- 建立在前面产出之上（不留孤儿代码）
- 接入整体系统（不产出悬空功能）
- 增量推进（复杂度不跳跃）
- 遵守 `design.md` 里定义的架构边界（Architecture Pattern & Boundary Map）
- 遵守 `design.md` 里记录的接口契约
- 少用主任务摘要式的重复描述——细节已被子任务覆盖时，就不要再写一遍

**结尾要有集成任务**，把东西接起来。

### 4. 依赖声明

**默认**：顺序本身已经处理了大多数依赖（任务 N 依赖它前面的任务）。

**以下情况必须显式声明**：

- 任务依赖另一个主任务组里的特定任务（跨边界）
- 依赖关系从顺序上看不出来
- 任务可以提前执行（用 `(P)` 声明），但仍需要某个特定前置工作

**格式**：`_Depends: 1.2, 2.3_`，与 `_Requirements:_` 一起放在任务细节区。

**不要过度标注**：任务只是依赖紧邻的前一个任务时，顺序本身足够。

### 5. 边界范围

**每个任务都应声明自己的组件边界**，用 `design.md` 里的组件/模块名：

- `_Boundary: AuthService_` 或 `_Boundary: API Layer, UserRepository_`
- 便于判定并行安全：边界不重叠的任务是并行候选
- 便于 Agent 理解范围：该动什么、不该动什么

**何时使用**：标 `(P)` 的任务必须写，用于验证并行安全。顺序执行、范围从描述就能看出来的任务可省略。

**边界规则**：

- 每个可执行任务应留在单一责任边界内
- 工作必须跨边界时，做成显式的集成任务，而不是普通实现任务
- 不要把跨边界协作藏在一个看起来是本地的任务里

### 6. 灵活的粒度

**指引**：

- **主任务**：按内聚性组织，需要几个子任务就几个
- **子任务**：每个 1–3 小时，每个 3–10 条细节
- 在过细和过粗之间找平衡

**不要硬凑数字**——让逻辑分组决定结构。

### 7. 需求映射

**每个任务细节区结尾写**：

- `_Requirements: X.X, Y.Y_`，**只列数字需求 ID**（逗号分隔）。永远不要附加描述性文字、括号、翻译或自由标签。
- 横切需求要把所有相关需求 ID 都列上。`requirements.md` 里所有需求都必须有数字 ID。缺 ID 就停下先修 `requirements.md`，再生成任务。
- 有帮助时可引用 `design.md` 的组件/接口（例如 `_Contracts: AuthService API`）。

### 7.5 测试档位标注

每个可执行任务必须声明恰好一个最低验证档位：

```markdown
_Test profile: fast | local | integration | full | none_
```

- 按 `.kiro/steering/testing-profiles.md`，选能建立本任务所需信心的**最低**档位。
- `none` 只允许用于"按设计就没有可运行验证"的任务，且任务正文要写出可观察的非测试验证方式。
- `full` 任务还必须声明 `_Full environment:_`，写出所需 DSN 变量的确切变量名；目标夹具会被修改时还要加 `LOOMIDBX_SPIKE_ALLOW_MUTATION=1`。**永远不要写变量值或密钥。**
- 非 `full` 任务不得出现 `_Full environment:_`。
- 不要创建环境检查复选框任务，也不要为它建依赖。`kiro-impl` 会扫一遍选中的计划，在特性实现开始前做一次全有或全无的 `full` 门禁。

### 7.6 可观察的完成态

**每个可执行任务至少有一条细节条目描述可观察的完成状态**：

- 写成交付物、运行时行为、已持久化状态、UI 状态、端点行为、测试结果或集成结果
- 避免"实现支持""接一下""处理逻辑"这类含糊条目，除非同时给出具体的可观察结果
- 最好让其中一条细节条目清楚回答："这个任务做完时，什么会成立？"
- 这条要求写在既有任务正文里，不要新增记账字段

### 8. 只写代码相关

**只包含**：

- 编码任务（实现）
- 测试任务（单元、集成、E2E）
- 技术搭建任务（基础设施、配置）

**排除**：

- 部署任务
- 文档任务
- 用户测试
- 市场/商务活动

## 任务计划评审门禁

写 `tasks.md` 之前，评审任务计划草稿并修掉局部问题，直到计划通过；如果发现真正的规格缺口，则停下升级。

### 覆盖度评审

- `requirements.md` 里每个需求 ID 都必须出现在至少一个任务里。
- `design.md` 里每个组件、接口/契约、集成点、运行前置条件和验证关注点，都必须至少有一个任务承载。
- 如果覆盖不全是因为任务计划没写完，那就补写再评审。
- 如果覆盖补不上是因为需求或设计含糊、自相矛盾或没交代清楚，**停下来回到需求/设计阶段**，不要在 `tasks.md` 里把坑糊上。

### 可执行性评审

- 每个子任务都必须能按写法直接执行，通常 1–3 小时内完成。
- 每个子任务都必须产出可验证交付物（行为、工件、端点、UI 状态、配置、迁移、测试或集成结果）。
- 每个可执行子任务至少有一条细节条目写出可观察的完成条件。
- 拆掉那些把多个可独立验证结果揉在一起的任务。
- 拆掉那些把多个责任边界揉在一起的任务——除非它是显式集成任务。
- 如果大量任务需要很宽的 `_Boundary:_` 范围，或反复跨边界协调，**停下回到设计或路线图拆分**，不要硬推过任务生成。
- 合并或收掉那些太小、只是记账、不构成有意义执行单元的任务。
- 把隐含前置条件显式化成前置任务。
- 改动后重新核对 `_Depends:_`、`_Boundary:_`、`_Test profile:_`、`(P)` 标记，确保并发声明仍与设计边界和依赖图一致。
- 核实每个可执行任务恰好有一个合法测试档位；每个 `full` 任务有确切的、不含密钥的 `_Full environment:_` 标注；没有任何任务把实现控制器的全局环境门禁做成复选框。

### 评审循环

- 写 `tasks.md` 之前，对任务计划草稿跑评审门禁。
- 如果问题只出在计划局部，就地修好，重跑门禁。
- 循环要有边界：评审加修复不超过 2 轮，之后必须把真正的规格缺口升级。
- **只有在门禁通过后，才写 `tasks.md`。**

### 可选测试覆盖任务

- 设计已经保证功能覆盖、且优先快速交付 MVP 时，把纯测试导向的后续工作（例如基线渲染测试/单元测试）用 `- [ ]*` 标成**可选**。
- 只有子任务的细节条目直接引用了 `requirements.md` 的验收条件时，才允许加可选标记。
- 实现工作和集成关键校验**永远不能**标为可选。`*` 只留给辅助性、可延后、能在 MVP 之后补的测试覆盖。

## 任务层级规则

### 最多两层

- **第 1 层**：主任务（1、2、3、4…）
- **第 2 层**：子任务（1.1、1.2、2.1、2.2…）
- **不得更深嵌套**（不要 1.1.1）
- 如果某个主任务只包含一个可执行项，就把结构压平，把子任务提为主任务（例如把 `1.1` 换成 `1.`）。
- 主任务纯粹作为容器时，复选框描述要简洁，不要重复细节——细节留给它的子任务。

### 顺序编号

- 主任务必须递增：1、2、3、4、5…
- 子任务按主任务重新计数：1.1、1.2，然后 2.1、2.2…
- 主任务编号不得重复

### 并行分析（默认开启）

- 除非显式关闭（例如 `--sequential` 参数），默认启用并行分析。
- `(P)` 的含义：本任务不依赖紧邻的同级任务，可以与之并发执行。
- **全部**满足以下条件才算可并发：
  - 对其它待办任务没有数据依赖
  - 没有共享文件或资源争用
  - 不需要等待其它任务的评审/批准
  - `_Boundary:_` 标注确认组件范围不重叠
- 地基阶段任务很少是 `(P)`——它们建立共享前置条件。
- 核心阶段任务是 `(P)` 的主要候选，因为地基已完成。
- 核实被判定并行的任务，确实在 Architecture Pattern & Boundary Map 定义的独立边界内工作。
- 确认 `design.md` 里的 API/事件契约没有会引发冲突的重叠。
- 带跨边界依赖的 `(P)` 任务，必须显式声明 `_Depends: X.X_`。
- 在每个可并行任务编号后紧跟 `(P)`：
  - 示例：`- [ ] 2.1 (P) Build background worker`
  - 主任务和子任务在适用时都加。
- 请求顺序模式时，完全不加 `(P)`。
- 并行任务尽量按逻辑分组（同一个父任务下），并在细节条目里点出排序注意事项。
- 对"看起来相似、实际不能并行"的任务，明确写出阻止 `(P)` 的依赖。

### 复选框格式

```markdown
- [ ] 1. Foundation: environment and test infrastructure setup
- [ ] 1.1 Sub-task description
  - Detail item 1
  - Detail item 2
  - Observable completion condition
  - _Requirements: X.X_

- [ ] 2. Core feature A
- [ ] 2.1 (P) Sub-task description
  - Detail items...
  - Observable completion condition
  - _Requirements: Y.Y_
  - _Boundary: AuthService_

- [ ] 2.2 (P) Sub-task description
  - Detail items...
  - Observable completion condition
  - _Requirements: Z.Z_
  - _Boundary: UserRepository_

- [ ] 3. Integration and wiring
- [ ] 3.1 Sub-task description
  - Detail items...
  - Observable completion condition
  - _Depends: 2.1, 2.2_
  - _Requirements: W.W_
```

## 需求覆盖

**强制检查**：

- `requirements.md` 里的所有需求都必须被覆盖
- 逐个核对需求 ID 与任务映射
- 发现缺口：回到需求或设计阶段
- 不允许任何需求没有对应任务

需求 ID 用 `N.M` 格式，`N` 是 `requirements.md` 里的顶层需求编号（例如需求 1 → 1.1、1.2；需求 2 → 2.1、2.2），`M` 是该需求组内的局部序号。

有意延后的需求，要连同理由写清楚。
