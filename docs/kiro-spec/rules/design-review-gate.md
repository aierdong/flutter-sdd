# 设计评审门禁

写 `design.md` 之前，先评审设计草稿并修掉局部问题，直到设计通过；如果发现的是真正的规格缺口，则停下升级。

## 需求覆盖度评审

- `requirements.md` 里每个数字需求 ID，都必须出现在设计的追溯映射里，并且有一个或多个具体组件、契约、流程、数据模型或运维决策来承载。
- 凡是引入外部依赖、集成点、运行前置条件、迁移关注点、可观测性需求、安全约束或性能目标的需求，都必须在 `design.md` 里显式体现。
- 如果覆盖不全是因为设计草稿没写完，那就补写再评审。
- 如果覆盖不全是因为需求含糊、自相矛盾或没交代清楚，**停下来回到需求阶段**，不要靠编造设计细节糊过去。

## 架构就绪度评审

- 组件边界必须明确到"分配实现任务时不用猜归谁"。
- 接口、契约、状态迁移和集成边界，必须具体到足以实现和校验。
- 实质性影响架构的自建/采用（build-vs-adopt）决策，必须写进 `design.md`；更深的调查留在 `research.md`（如果存在）。
- 运行前置条件、迁移、上线约束、校验钩子和失败模式，在实质性影响实现顺序或风险时必须写出来。

## 边界就绪度评审

- 设计必须明确写出本规格负责什么。
- 设计必须明确写出什么在边界之外。
- 允许的依赖必须具体到"评审者之后能据此判定越界"。
- 如果数据、行为或集成责任看起来被多个领域共享却没有清晰接缝，停下修设计。
- 如果下游假设被"为了方便"塞进上游组件，停下修设计。
- 如果边界没法用几条直白的条目说清楚，那它对任务生成来说大概还是太虚。
- 如果设计暴露出多个可以各自独立移动的责任接缝，**停下拆规格，或回到路线图发现阶段**，不要硬塞进一个规格。

## 可执行性评审

- 设计必须能被拆成一串有界任务依次实现，且没有隐藏前置条件。
- 架构打算并发实现的地方，并行安全的边界应当可见。
- 避免投机式抽象：只服务假想未来范围的组件、适配器或接口，删掉。
- 如果某一节虚到任务无法直接引用，定稿前重写。

## 机械检查

在做判断之前，先用机械方式核实这几项：

- **需求追溯**：从 `requirements.md` 抽出全部数字需求 ID，逐个在草稿里搜索。报告找不到的 ID。
- **边界章节已填**：`Boundary Commitments`、`Out of Boundary`、`Allowed Dependencies`、`Revalidation Triggers` 不得为空或只有占位符。
- **File Structure Plan 已填**：该节必须包含具体文件路径（不能只有 `TBD` 或空白）。扫一遍占位文本。
- **边界与文件结构对齐**：File Structure Plan 必须体现所声明的责任边界。如果文件隐含的权属比边界章节声称的更宽，报告不一致。
- **没有孤儿组件**：设计里提到的每个组件，都必须在 File Structure Plan 里有对应文件路径。扫一遍没有文件条目的组件名。

## 评审循环

- 先跑机械检查，再做判断类评审。
- 如果问题只出在草稿局部，就地修好，重跑门禁。
- 循环要有边界：评审加修复不超过 2 轮，之后必须把真正的规格缺口升级。
- **只有在门禁通过后，才写 `design.md`。**
