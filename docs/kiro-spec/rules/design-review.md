# 设计评审流程

> 本文件是英文原文的中文译本。事实以 `.claude/skills/kiro-validate-design/rules/design-review.md` 为准。

## 目标

对技术设计文档做交互式质量评审，确认它在可接受风险下已经足够扎实，可以进入实现。

## 评审理念

- **做质量把关，不追求完美**
- **只抓关键**：最多 3 个最重要的担心
- **对话式**：和设计者交流，而不是单向打分
- **评价平衡**：优点和缺点都要说
- **结论明确**：给出确定性的 GO/NO-GO 和理由

## 范围与非目标

- 范围：对照项目上下文与标准，评估设计文档质量，决定 GO/NO-GO。
- 非目标：不做实现级设计，不做深度技术调研，不敲定技术选型。这些留给设计阶段的下一轮迭代。

## 核心评审准则

### 1. 与既有架构对齐（关键）

- 与既有系统边界和分层的集成是否合理
- 是否与既定架构模式一致
- 依赖方向和耦合管理是否正确
- 是否与当前模块组织方式一致

### 2. 设计一致性与标准

- 是否遵守项目命名约定与代码标准
- 错误处理与日志策略是否一致
- 配置与依赖管理是否统一
- 是否与既有的数据建模模式相符

### 3. 可扩展性与可维护性

- 面对未来需求，设计是否留有余地
- 关注点分离与单一职责是否清晰
- 是否考虑了可测试性和可调试性
- 复杂度与需求是否匹配

### 4. 类型安全与接口设计

- 类型定义与接口契约是否正确
- 是否避免了不安全写法（例如 TypeScript 里的 `any`）
- API 边界与数据结构是否清晰
- 输入校验与错误处理是否覆盖

## 评审流程

### 第 1 步：分析

对照全部评审准则分析设计，重点看影响集成、可维护性、复杂度与需求达成的关键问题。

### 第 2 步：找出关键问题（≤3 个）

每个问题按这个结构写：

```
🔴 **关键问题 [1-3]**：[简短标题]
**担心**：[具体问题]
**影响**：[为什么重要]
**建议**：[具体改进]
**追溯**：[requirements.md 里的需求 ID / 章节]
**证据**：[design.md 的章节 / 标题]
```

### 第 3 步：肯定优点

指出 1–2 个扎实的地方，保持反馈平衡。

### 第 4 步：给 GO/NO-GO

- **GO**：没有关键架构错位，需求已覆盖，实现路径清晰，风险可接受。
- **NO-GO**：存在根本性冲突、关键缺口、高失败风险，或复杂度与收益不成比例。

## 追溯与证据

- 每个关键问题都要关联到 `requirements.md` 里的相关需求（ID 或章节）。
- 引用设计文档中的证据位置（章节、标题、图或工件）支撑判断。
- 适用时引用 steering 上下文中的约束，作为问题成立的依据。

## 输出格式

### 设计评审摘要

2–3 句话，说明整体质量与就绪度。

### 关键问题（≤3）

每个问题写：问题、影响、建议、追溯（例如 1.1、1.2）、证据（`design.md` 章节）。

### 设计优点

1–2 条正面评价。

### 最终判定

结论（GO/NO-GO）、理由（1–2 句）、下一步。

### 交互讨论

就设计者的视角、替代方案、澄清事项和必要改动展开对话。

## 篇幅与聚焦

- 摘要：2–3 句
- 每个关键问题：总共 5–7 行（含问题/影响/建议/追溯/证据）
- 整体评审：保持简洁（约 400 词为宜）

## 评审指引

1. **只抓关键**：只标出显著影响成败的问题。
2. **建设性语气**：给方案，不只会挑毛病。
3. **交互式**：以对话方式进行，而不是单向评估。
4. **评价平衡**：优点和缺点都要说。
5. **结论明确**：给出确定的 GO/NO-GO 建议。
6. **反馈可执行**：所有建议都必须能落地。

## 最终检查清单

- **关键问题 ≤ 3 个**，每个都包含影响和建议。
- **追溯**：每个问题都引用了需求 ID/章节。
- **证据**：每个问题都指出了设计文档中的位置。
- **结论**：GO/NO-GO 明确，理由和下一步清晰。
